# M22.2 — the expert kernel: 52% of a decode step runs at 16% of VRAM bandwidth

Status: **open** (2026-10-25). Parent: [m22-tpot.md](m22-tpot.md) §12-§14.
One mechanism: **the expert GEMM** — replace the per-(row, expert) GEMV chain the resident path uses today with one
kernel that reads each distinct expert's weights once, at a bandwidth the card can actually sustain.

## 1. What M22 established, and what it left

| lever | result |
|---|---|
| speculative depth (fixed 4 -> automatic) | -15% TPOT, worst step 79 -> 57.7 ms |
| draft sampling (auto -> greedy) | -9.5% p50, -22% p90 |
| `--pcie-frac` / `--lookahead-swaps` / cache / promotion / KV | at their optimum, closed |
| **per-decode-step budget** | **the step is 95% device time; the ring is 4%, the CPU path 0.3%** |

Against strata (g25, 3 rounds): `doc` **-6.4% (a win)**, `long` +1.0%, `short` +3.1%, **`code` +14.6%**. The one class
that is still clearly behind is the short-context one, where attention is cheap and everything left is the per-layer
constant.

## 2. The measurement that opens this milestone

`NAIWA_STEP_BUDGET=1` now brackets each layer's expert submissions with CUDA events (`src/stats/budget.rs`, `dev`
module) and reads them at the next step boundary, so the device time of the expert kernels is separated from the rest
of the layer's device work (attention, norms, routing), which a host-side timer cannot do because the doorbell is
queued behind all of it.

```
STEP_BUDGET layers 48 total 63.3 ms expert_dev 33.0 ms (48 layers) | plan 55.2 spawn 0.9 ... staging_wait 3.4
STEP_BUDGET layers 48 total 60.0 ms expert_dev 32.1 ms (48 layers) | plan 52.1 ...
```

| | per step | per layer |
|---|---:|---:|
| **expert kernels** | **33.0 ms (52%)** | **0.69 ms** |
| everything else (attention, norms, routing, launches) | 30.3 ms (48%) | 0.63 ms |

Bytes moved by those kernels: `batch x topk = 2-5 x 10 = 20-50` (row, expert) pairs, each reading one expert's three
projections (1.88 MB at IQ1_M) - about 56 MB per layer, 2.7 GB per step. So:

```
2.7 GB / 33.0 ms = 82 GB/s
```

**A 4070 sustains ~500 GB/s.** The expert path runs at **16% of peak**, and it is 52% of every decode step. That is
the whole of the remaining TPOT gap, and it is a kernel fact, not a scheduling one.

## 3. Why it is that slow

`mistralrs_quant::indexed_moe_fused_decode` dispatches to `launch_moe_gemv_fused_gate_up_<dtype>_q8_1` and
`..._down_aggregate_...`: **GEMV** kernels, one per (row, expert) pair, i.e. `batch x topk` rows of a matrix-vector
product. Three consequences:

1. **A GEMV cannot saturate VRAM by construction** if its parallelism is one warp per row: with 1 row per pair there
   is not enough independent work in flight to hide the latency of a 1.88 MB read. This is the classic reason a
   batch-1 decode sits at 10-20% of peak bandwidth while a batched GEMM reaches 80%+.
2. **`batch x topk` pairs are separate GEMVs.** Splitting the 20-50 pairs into 4+4 kernel launches per layer means
   the dequantisation work of, say, 30 experts is spread over 30 independent GEMVs rather than one batched pass.
3. **The dequantisation is the ALU floor**: IQ1_M is 1.7 bits per weight with a lookup table, so each weight costs
   several instructions before it multiplies. A kernel that dequantises *once per expert* and then applies several
   rows amortises that - a GEMV per row does not.

## 4. What the fix is worth

| if the expert kernels reach | expert time per step | step time | TPOT (`doc`, 2.6 tokens/step) |
|---|---:|---:|---:|
| 82 GB/s (today) | 33.0 ms | 63 ms | 35.8 ms |
| 160 GB/s (2x, one expert = one pass) | 16.5 | 46 | 26 |
| 300 GB/s (grouped GEMM) | 9.0 | 39 | 22 |

Even the middle row would put every class at or better than strata and take `short`/`code` with it, because those two
classes spend *most* of their step in exactly this path.

## 5. Plan

1. **Confirm the traffic model** (§2) per layer: `experts per layer per step`, bytes, and the derived GB/s, logged
   next to `expert_dev`. If the pairs are 20-50 and the bytes 56 MB, the 82 GB/s number stands; if not, the model is
   wrong before the kernel is.
2. **Group the pairs by expert** in `decode.rs` (they arrive as `Vec<Vec<Hit>>`, one per row, with duplicates across
   rows) and hand the GPU path *distinct experts with their row lists*. This alone removes the duplicate reads when a
   step's rows share experts, and - more importantly - it is the shape a grouped kernel needs.
3. **Write the kernel** (fork, `mistralrs-quant/gguf/cuda` + its launcher): one launch per layer over
   `(distinct expert, its rows)` with the rows of an expert accumulated in registers, dequantising each weight block
   once. Target 160 GB/s first (2x), 300 GB/s second.
4. Gate: `expert_dev` per layer down and `code` TPOT <= 30 (strata's 30.1); no change to the oracle arm; the same
   answer bytes (the kernel is arithmetic, not sampling).

## 6. Non-goals

- Nothing in the prefill path: that is M23's subject and it already has its own picture (M21).
- No change to the speculation machinery (§14 says it is at its optimum).
- No cache or residency work: M20 closed it, and this kernel reads whatever the cache has already admitted.

## 7. Open questions

- **Is the 82 GB/s ALU-bound or latency-bound?** IQ1_M dequantisation is expensive per byte; if the kernel is ALU
  bound, a bandwidth target is the wrong goal and the fix is fewer dequantisation instructions (e.g. a smaller lookup
  table, or `__ldg` + vectorised loads). The first step's instrumentation should log both bytes and instructions if
  the profiler can be made to work - `ncu` did not run in this environment (it dies silently, exit 137), so the
  per-layer event timing above is the tool we have.
- **Does the resident bank layout help or hurt?** All of a layer's slots are one bank per projection, so expert
  `i`'s rows are contiguous - good. The staged ring is a second bank, which forces a second set of launches per
  layer; merging the two into one launch (if the kernel took two base pointers) would remove 4 of 8 launches.
- **How much of `58%` is attention?** At a 300-row context (the `code` class) attention should be small, yet the
  non-expert half is 0.63 ms/layer there too (the step time is context-independent across classes). That suggests the
  non-expert half is *not* attention but fixed per-layer work - worth its own probe once the expert kernel is done.

## 8. The kernel does not get faster with more rows: it is an efficiency floor, not a latency hole (2026-10-24)

`NAIWA_STEP_BUDGET=1` with the depth fixed, doc probe, median over 40 steps per arm:

| `--mtp-n-predict` | rows per step | step total | `expert_dev` | expert share | effective GB/s |
|---|---:|---:|---:|---:|---:|
| 2 | 3 | 67.0 ms | **35.8** | 53% | 75 |
| 4 | 5 | 95.9 | **46.5** | 48% | 97 |
| 6 | 7 | 116.2 | **59.0** | 51% | 120 |

Fitting the expert time: **`expert_dev ≈ 22 ms + 5.2 ms per extra row`** (37.6 / 48.0 / 58.4 predicted against 35.8 /
46.5 / 59.0 measured). Two readings, and they matter for the kernel design:

1. **Feeding it more rows barely improves throughput** (75 -> 97 -> 120 GB/s, still a quarter of the card). So the
   kernel is neither purely latency-starved (more work would fix that) nor purely ALU-bound at a fixed cost per byte
   (more rows would not help at all): it sits at an efficiency floor that only its own implementation can move.
2. **The first row costs 22 ms** (0.46 ms per layer for ~19 MB of experts = 41 GB/s) and every further row adds
   5.2 ms (0.11 ms per layer for another ~19 MB). The fixed part is the dequantise-read of the layer's distinct expert
   set; the marginal part is cheaper because those reads amortise over the extra rows.

So "batch the rows" (plan step 2) is **not** the lever by itself - the pairs are mostly distinct experts, so it saves
the collision fraction (a few percent) and nothing more. The lever is inside the kernel:

| target | what it needs |
|---|---|
| 160 GB/s (2x, TPOT -27%) | more CTAs per GEMV row: split-K over the 2560-wide K with a tree reduce, or 4-8 warps per row instead of one; vectorised 128-bit loads and a lookup-free dequant path where the format allows |
| 300 GB/s (3.6x, TPOT -38%) | the same plus keeping the dequantised block in shared memory once per expert and reusing it for that expert's rows (`batch >= 3` makes this pay), i.e. a genuine grouped GEMV over `(expert, rows)` |

Both live in the fork's `mistralrs-quant/src/gguf/cuda.rs` (`fused_gate_up_launcher`, `down_aggregate_launcher`) and the
CUDA sources they call. It is a self-contained kernel project with the acceptance test already built: `expert_dev`
per step, and the gate `code TPOT <= 30.1`.

### Where this leaves M22.2

Measured, modelled, and quantified; the remaining work is the kernel itself, which is a focused CUDA task rather than
something to start at the end of a measurement session. Recorded so the next session begins at the launcher, not at
"where do we lose the time".
