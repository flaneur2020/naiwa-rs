# M22.4 - rewriting `vec_dot` (the 43% of a step)

**Status:** **closed, negative** - three mechanisms measured out, one route left (aligned block repack) that belongs to
another kind of change. No shipped kernel change; the shipped TPOT configuration is untouched.
**Parent:** M22.3 (which decomposed the expert kernel: load <=42%, dequant+MAC 33%, reduction 18%, store 2%).
**Gate:** `expert_dev` at `--mtp-n-predict 3` from **38.3 ms to <=33 ms** (-14%), measured as the median of >=3 runs,
with the `frac 0 + --no-lookahead` oracle byte-identical and `cargo test` green.

## 1. Why <=33 ms is the only acceptable target

| measurement | value |
|---|---|
| step time | 70 ms, expert kernels 38.3 ms (55%) |
| instrument floor (same arm, same session) | **+-3-4 ms on a 38 ms measure (8-10%)** |
| TPOT `-14%` needed | step 70 -> 60.2 ms, i.e. expert 38.3 -> 33.0 ms |

A 4-5% kernel win is invisible at this floor. Either the change lands ~15% or it cannot be shown at all - which is why
M22.4 is scoped as "one rewrite, one gate", not as a series of micro-optimisations.

## 2. Finding: grouping duplicate `(row, expert)` pairs cannot deliver (closes §25's hope)

§25 measured 27-34% duplicate pairs per step and priced grouping at "~12% of the expert kernel". §26 then noticed the
marginal pair is cheap. This settles it numerically:

| depth | pairs | `expert_dev` | us per pair |
|---:|---:|---:|---:|
| 3 rows | 30 | 35.8 ms | **24.9** |
| 7 rows | 70 | 59.0 ms | **17.6** |

If every duplicate pair were *completely free* - the ideal, unreachable outcome of a per-expert row batch - the
7-row arm would cost `24.9 x (1 - 0.30) =` **17.4 us per pair**. Measured: **17.6**. The gap is **1%**.

So a per-expert column batch (`ncols`, strata's design) would buy ~1%: the duplicate pairs are already served from
L1/L2 *including* their dequantisation, because the same expert block is re-read within a few hundred blocks.
**Grouping is closed.**

## 3. Finding: an IQ block cannot be loaded wide - and that is the 82 GB/s

Every IQ block type in our model starts with `half d`:

```c
typedef struct { half d; uint8_t qs[3 * QK_K / 8]; } block_iq3_xxs;   // 98 B, qs at offset 2
typedef struct { half d; uint8_t qs[QK_K / 4]; uint8_t qh[..]; ... } block_iq3_s;
typedef struct { half d; uint16_t scales_h; uint8_t scales_l[..]; uint8_t qs[..]; } block_iq4_xs;
```

so `qs` sits at offset 2 and the block itself is only 2-byte aligned (its element type is `half`). The widest *legal*
load from `qs` is therefore **2 bytes**, which is exactly what `iq3_get_int_b2` does:

```c
static __device__ __forceinline__ int iq3_get_int_b2(const void *x, const int &i32) {
  const uint16_t *x16 = (const uint16_t *)x;
  return (x16[2 * i32 + 0] << 0) | (x16[2 * i32 + 1] << 16);
}
```

**Tried to fix it and crashed:** replacing the two adjacent 4-byte words of a group with one aligned 8-byte `uint2`
load is arithmetically valid (`iqs` is even, so `4 * iqs` is a multiple of 8) but *not* addressable: the base is
2-byte aligned. The server died at startup with `CUDA_ERROR_MISALIGNED_ADDRESS` before answering a single token
(`ERROR step - Model failed with error: CublasError(CUBLAS_EXECUTION_FAILED)`, `misaligned address` on every
follow-up call). Reverted; the reverted build re-verified green (0 misalignment errors, doc probe TPOT 37-47 ms).

The consequence explains M22.2's headline anomaly - **82 GB/s effective, 16% of peak**: a warp load instruction moves
32 lanes x 2 B = **64 B**, half of a 128 B transaction, before any other inefficiency. The kernel is not lazy, it is
issuing the widest load the layout allows.

## 4. What the rewrite actually has to be (the spec)

The only legal route to wide loads is to **stop reading the packed bytes in place**: stage each block into shared
memory (where alignment is ours to choose) and read it back as `uint4` - llama.cpp's `ggml_cuda_mmq` does precisely
this, and it is the one structural difference between our GEMV and their matmul that we have not tried.

Sketch, per dtype:

1. per block, the 4 warps cooperatively `memcpy` the block (98-136 B) into a shared staging slot: 2-byte loads, but
   **coalesced across lanes** so a warp instruction moves 128 B of *contiguous* data instead of 64 B of strided;
2. read back through an aligned `uint4` view (shared memory has no alignment penalty for 16 B);
3. decode as today, `__syncwarp()` only where a warp shares a slot - **not** across the block (M22.3 §14 hung the
   startup by putting a `__syncwarp()` behind a lane-dependent trip count);
4. four dtypes in 2.046 -> our 1.81 MB-per-expert order: IQ3_XXS, IQ2_S, IQ3_S, IQ4_XS.

Costs to watch: shared memory per block (4 slots x 136 B = 544 B, trivial), one extra `cp.async`-less copy pass, and
the fact that the shared read may just re-introduce the latency the L1 was already hiding. The 82 -> 500 GB/s question
is whether the copy pass is cheaper than the halved transaction width; that is the experiment.

## 5. Built it: shared-memory staging is 19% *worse*, and that pins the bottleneck on instruction count

Implemented §4 for IQ3_XXS (`MISTRALRS_MOE_SMEM=1`, env-gated, old path untouched): per warp, copy the 4 blocks of the
current iteration into shared with a **contiguous** `uint16_t` fill (32 lanes x 2 B = 64 B per instruction, no gaps,
98 B = exactly 49 words so the copy is alignment-legal), `__syncwarp()`, then decode from shared with the same
`vec_dot_iq3_xxs_q8_1`. Clean run - no misalignment, no errors, answers coherent.

| arm | `expert_dev`/step, depth pinned 3 |
|---|---:|
| baseline | 38.3 ms |
| **shared-memory staging (IQ3_XXS)** | **45.7 ms (+19%)** |

### What that falsifies, and what it establishes

The hypothesis behind it was per-instruction DRAM efficiency: one warp load instruction touches 4 blocks x 8 lanes x
2 B with stride 8 = 8 sectors of 32 B for 64 B of payload (~25%), which would have explained 82 GB/s. **45.7 ms says
that was wrong**: the gaps are absorbed by L1, because the *next* instruction (`l0 += 2`) reads the adjacent bytes of
the very same sectors. Per *block* the DRAM traffic is already 98 B exactly - perfect. Staging therefore bought
nothing and cost an extra pass plus shared traffic.

So the load phase is limited by **instruction count**, not bytes: 4 x `uint16` load instructions per 8 bytes of `qs`
per lane, i.e. **2 bytes per load instruction**. That is the 82 GB/s. And the width cannot be raised (finding 2): the
block base is 2-byte aligned because every block starts with `half d`.

### Therefore the one real fix is a repack, and here is its arithmetic

Give the block a **4-byte-aligned, qs-first layout** with a 100 B stride (98 -> 100 = **+2% bytes**):

| | today | after the repack |
|---|---|---|
| bytes per block | 98 | 100 (+2%) |
| `qs` alignment | 2 | 4 |
| load instructions per lane per 8 B of `qs` | **4 x uint16** | **2 x uint32** |
| warp load transaction | 64 B used of 8 sectors | 128 B, 4 sectors, full |
| load share of the expert kernel (<=42%) | 10.5 us/pair | ~5.3 us/pair |
| projected `expert_dev` | 38.3 ms | **~33.2 ms** |

That lands exactly on the gate, at +46 MB on the 2.3 GB cache (+2%), and it is *not* a kernel change: it is a change
to how an expert is written into its cache slot (a device-side repack on the existing staging path), plus a `_q4a`
vec_dot variant per IQ dtype that reads the aligned layout. Risk: the mmap *borrow* path (M19's Phase A) has no slot to
repack into, so borrowed experts either stay on the 2-byte path (two kernels, dtype+layout selected per hit) or the
borrow path is dropped for these dtypes.

**M22.4 status: open, gate not met (38.3 ms), one mechanism measured out (staging, +19%) and the next one specified
with numbers (aligned repack, ~33 ms).** The tree is pristine: the staged kernel and its launcher were removed, only
the `MISTRALRS_MOE_SKIP_DOWN` ablation switch remains on the fork.

## 6. Closed negative: the gate needs layout surgery, and that is a different kind of change

The repack from §5 is the only route left, and inspecting the seam says it is not a kernel change at all. An expert
reaches a cache slot as a byte-exact `memcpy_dtod_async` (`cached_layer.rs:832`), and the slot's `QTensor` view is a
`[n, blocks_per_row]` array of 98-byte blocks whose stride `slot_bytes_from_qtensor` computes. Giving blocks a 100-byte
aligned layout therefore touches, at once:

- `slot_bytes_from_qtensor` and every slot-size/free-memory computation (the 2.3 GB -> 2.35 GB ceiling, M20's ledger),
- the `QTensor` views over slot memory and their strides,
- the H2D/staging path that fills slots (a repack kernel instead of `memcpy_dtod`),
- **the mmap borrow path**, which has no slot to repack into and would need a second kernel + per-hit selection,
- and four `_q4a` vec_dot variants.

That is five coupled subsystems for one 14% kernel win, i.e. exactly the kind of change this repo's rules say not to
smuggle into a milestone - and the memory ceiling it perturbs is the one M20 spent a milestone proving is the binding
constraint (2.3 GB is the config ceiling; +2% of blocks eats 2 slots per 1358).

**Status: closed, negative.** No shipped change; the tree is pristine.
