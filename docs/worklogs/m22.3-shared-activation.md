# M22.3 — the expert GEMV reads its activation eight times: one shared-memory stage

Status: **closed** (2026-10-25). Seven experiments, one unmoved number: the expert kernels are 33-38 ms of a 63-75 ms
decode step (51-55%), and neither the block shape (2/4/8 warps: 40.2 / 38.3 / 44.4), the rows per warp, the activation
staging, nor the weight-read coalescing (43.9 / 46.4 ms) moves it. The reads are already coalesced
(`LANES_PER_BLOCK = 8` for the K-quants); the missing instrument is an in-kernel `clock64()` phase counter (no profiler
is available here: `ncu` exits 137, `SyncOnDrop` blocks per-stage events). The shipped configuration is untouched -
doc TPOT -6.4% against strata, `long`/`short` at parity. Parent: [m22.2-expert-kernel.md](m22.2-expert-kernel.md) §2-§8, [m22-tpot.md](m22-tpot.md) §15.
One mechanism: **stage the activation vector in shared memory, once per block**, so a block's output rows share it
instead of each re-reading it from global memory.

---

## 1. The number this milestone starts from

M22.2 measured, with CUDA events around the expert submissions: **33.0 ms of a 63.3 ms decode step is the expert
kernels** (52%), i.e. 0.69 ms per layer, moving ~56 MB per layer at an effective **82 GB/s - 16% of the card's
~500 GB/s**. Depth scaling said the kernel sits at an efficiency floor: more rows only lifted it to 120 GB/s.

## 2. Why: the traffic is three quarters activation, not weights

`moe_gemv_fused_gate_up_impl` (`kernels/indexed_moe/indexed_moe.cu:1797`) is what our resident path calls
(`launch_moe_gemv_fused_gate_up_*`). Its shape:

```cpp
constexpr int ROWS_PER_WARP = 2;   // 2 output rows per warp
constexpr int NWARPS = 4;          // 8 output rows per block
grid = (ceildiv(n, 8), topk, batch)
...
for (int r = 0; r < ROWS_PER_WARP; ++r) {          // outer over rows
  for (int kbx = ...; kbx < blocks_per_row; ...) { // inner over k blocks
    g_sum += vec_dot_q_cuda(&gate_w[kbx + row*blocks_per_row], &x[kby], kqs);
    u_sum += vec_dot_q_cuda(&up_w[kbx + row*blocks_per_row],   &x[kby], kqs);
  }
}
```

`x` (the quantised activation, `k_padded/32 x 34 B` = **2.7 KB** for k = 2560) is read **once per output row per
warp** - 8 times per block, and the same activation is re-read by every block of the layer's 80 blocks. Per
`(row, expert)` pair that is:

| traffic | bytes | share |
|---|---:|---:|
| activation (`x`) re-reads: 80 blocks x 8 rows x 2.7 KB | 1 728 KB | **72%** |
| gate+up weights: 640 rows x 2 projections x 540 B | 690 KB | 28% |
| **total** | **2 418 KB** | |

The weights are read exactly once - they are irreducible. **The activation is read 8x more than it needs to be, and it
is 72% of the traffic.** That is why the kernel sits at 16% of peak: it is not bandwidth-limited by useful bytes, it is
limited by re-reading the same 2.7 KB that is already in L2.

## 3. The mechanism

Load the activation into **shared memory once per block** (````__shared__ block_q8_1 xs[X_BLOCKS]````, 4.3 KB for the
largest k we serve), then have every row read from shared:

```cpp
const int x_blocks = k_padded / QK8_1;
if (x_blocks <= X_BLOCKS) {
  for (int i = tid; i < x_blocks; i += NWARPS * WARP_SIZE) xs[i] = x[i];
  __syncthreads();
  x = xs;
}
```

Expected traffic per pair: 2 418 KB -> **690 KB + 2.7 KB** (a **3.5x** reduction), which at the same effective
efficiency turns 82 GB/s of "useful bytes" into ~290 GB/s equivalent, i.e. the `expert_dev` 33 ms becomes ~10-13 ms.

| if the stage works as modelled | `expert_dev`/step | step | TPOT (doc, 2.6 tok/step) |
|---|---:|---:|---:|
| today | 33.0 ms | 63 ms | 35.8 ms |
| 2x | 16.5 | 46 | 26 |
| **3.5x (the traffic ratio)** | **10-13** | **40-43** | **15-17-22** |

The same edit applies to `moe_gemv_down_aggregate_impl` (`:1875`), whose input is the 640-wide intermediate (0.7 KB).

2. Implement the shared-memory stage in `moe_gemv_fused_gate_up_impl`, guarded by `x_blocks <= X_BLOCKS`, keeping the

## 6. Non-goals

- No change to which experts are chosen, to the cache, or to the speculation policy.
- No new dtype or new quantisation format.
- Not the prefill path: this kernel is the decode path's (M23 owns prefill).

## 7. Open questions

- **Is `x` already in L2?** 2.7 KB read 640 times per pair should be served by L2 at ~2 TB/s, which would make the
  re-reads cheap and the model wrong. The measured 82 GB/s says otherwise (the reads are not being coalesced well, or
  the working set of 640 rows x 2 projections evicts it). The measurement in step 1 settles it: if the traffic model
  is right, `expert_dev` scales with template `ROWS_PER_WARP`; if it is wrong, changing `ROWS_PER_WARP` will not move
  `expert_dev` at all.
- **Vector width**: the `block_q8_1` reads are 34-byte structs, i.e. misaligned by design; a `__ldg` on 16-byte
  chunks plus a shared-memory transpose may be needed to see the full benefit. That is a second, separate change.

## 8. Two kernel edits tried, both neutral-to-worse - and one measurement trap found (2026-10-24)

### What was tried

| arm | change | `expert_dev`/step | TPOT turn >= 2 |
|---|---|---:|---|
| baseline (§2) | - | 33.0 ms (55%) | 35.6-43.1 |
| **A: shared-memory activation** | `__shared__ block_q8_1 x_shared[96]`, staged once per block, rows read it there | **38.6 ms** | 35.5-46.8 |
| **B: 8 rows per warp** | `ROWS_PER_WARP` 2 -> 8 (gate+up) and 4 -> 8 (down) | **35.2 ms** | 34.9-49.7 |
| restored kernel | original code | 37.6 ms | 36.9-52.3 |

Neither edit helped. **But the comparison is not clean**, and that is the more useful finding:

- The arms ran with **automatic depth**, so their step mixes differ: a step with 6 drafts has 7 verify rows (7x the
  expert pairs) and one with 2 has 3. `expert_dev` moves 33 -> 38 ms on that alone, which is the same size as the
  effect being looked for. **A kernel A/B must pin `--mtp-n-predict`**, otherwise it measures the autotuner.
- So the honest verdict on A and B is **"no effect beyond the step-mix noise"**, not "worse". The shared-memory arm
  additionally says the activation is not a global-memory problem - it is 2.7 KB that L2 already holds, which
  contradicts §2's traffic model: **the 82 GB/s is not an activation-re-read problem.** The weights alone (690 KB of
  gate+up per pair, ~1.88 MB with down) at 23 us per pair is 82 GB/s, so the weight stream itself is the floor.

### The measurement trap

A third attempt - timing the four stages *inside* `indexed_moe_fused_decode` with CUDA events - produced
`quant_in 0.000 ms gate_up 0.000 ms quant_mid 0.000 ms` **and wrecked the run**: the step budget that normally shows
`staging_wait 3.4 ms` now showed **33.8 ms with 48 of 48 layers waiting over 200 us**, because `CudaEvent::elapsed_ms`
**synchronises both events**. Read inline, the probe drains the pipeline it is measuring. The correct design is the one
`stats::budget::dev` already uses: keep the events, read them at the *next step boundary*. Reverted.

## 9. A controlled baseline for kernel A/B (depth pinned) (2026-10-24)

`--mtp-n-predict 3` (4 verify rows per step, every step), doc probe, 3 runs, 60 steps:

```
expert_dev 38.3 ms of 75.5 ms (51%)
```

That is the number a kernel change must move. Two things about it:

- **51%, not the 52% of §2** - the share is stable across step mixes even though the absolute value is not, because
  both the expert time and the rest of the step scale with the row count.
- The *absolute* `expert_dev` at a pinned depth (38.3 ms for 4 rows) against the auto-depth arms (33.0 for ~2.5 rows
  average) is the step-mix effect quantified: **~5 ms of `expert_dev` per extra verify row**, which is the same slope
  §8 of M22.2 fitted (5.2 ms/row). So the two measurements agree, and the earlier cross-arm comparison in §8 was
  indeed measuring the mix.

### The next step, precisely

1. **A deferred per-stage timer**: events around `quant_in`, `gate_up`, `quant_mid`, `down` stored per call and summed
   at the step boundary (never read inline - §8). That names the owner of the 38.3 ms.
2. Then one edit at a time, **always with `--mtp-n-predict 3`**, compared against 38.3 ms: the plausible candidates are
   the `gate_up` warp tiling (CTAs per output row, K-split with a tree reduce) and dropping the `quant_mid` stage by
   keeping the intermediate in f32 for the down GEMV when it fits.
3. If `down` turns out to be the owner, the fix is different again (it is the atomicAdd aggregation, `ROWS_PER_WARP`
   4 and one `atomicAdd` per output row per expert - a candidate for a per-expert shared-memory reduce).

## 10. Per-stage timing is not obtainable through this FFI - the pointer guards drain the queue (2026-10-24)

The deferred design (§9 step 1) was built exactly as planned: `moe_stage::open/close` records four CUDA event pairs
inside `indexed_moe_fused_decode` (`mistralrs-quant/src/gguf/cuda.rs`), and `stats::budget::step_boundary` sums them
**at the next step boundary**, never inline. `--mtp-n-predict 3`, doc probe:

| stage | reported |
|---|---:|
| quant_in | **48.0 ms** |
| gate_up | 0.8 ms |
| quant_mid | 5.8 ms |
| down | 0.8 ms |
| calls per step | 4.4 |
| `expert_dev` (whole-call brackets) | 47.2 ms |

The numbers cannot be kernel times: quantizing a `[4, 2560]` f32 input to Q8_1 is a few microseconds, not 48 ms, and
`gate_up + quant_mid + down` times 4.4 calls per step (32.6 ms) does not reconcile with `expert_dev` (47.2 ms).

The cause is in the same function's own comments: the device pointers for every stage come from
`slice_ptr(..)`/`device_ptr()`, whose guards are **`SyncOnDrop`** - dropping one synchronises the stream. The *first*
bracket therefore absorbs the drain of everything the layer had queued (which is why `quant_in` looks 60x too large),
and every later bracket measures a queue that has already been emptied, at a granularity the GPU does not expose.
A correct per-stage timer would have to resolve the pointers outside the measured window, which changes the code path
being measured.

**Reverted** (the fork is back to its original `cuda.rs`/`mod.rs`; the only surviving instrument is the whole-call
`expert_dev`, which is what M22.2 validated and what §9's 38.3 ms baseline is).

### So how the next change gets attributed

Not per stage: by **ablation against the pinned baseline**. Each candidate is a build that removes or reshapes exactly
one stage and is compared to `expert_dev` 38.3 ms at `--mtp-n-predict 3`:

| ablation | what it isolates | expected signal |
|---|---|---|
| drop `quant_mid` (keep the intermediate in f32 and give the down GEMV an f32 activation path) | the second quantisation stage | if `expert_dev` does not move, quantisation is not the cost |
| `gate_up` with more CTAs per output row (K-split + tree reduce) | its occupancy | the only shape knob left that §8's two edits did not cover |
| `down` with a per-expert shared-memory reduce instead of `atomicAdd` | the aggregation | if `down` is the owner |
| a step with `topk = 4` instead of 10 (a different model) | per-pair cost vs per-layer fixed cost | separates the two terms the fit in §9 left coupled |

Each is one build and one 5-minute probe, and all of them are attributed by the same number - which is the point: the
milestone has a ruler (38.3 ms at a pinned depth) even though it does not have a profiler.

## 11. The ablation says `gate_up` owns all of it: 38.0 of 38.3 ms (2026-10-24)

`MISTRALRS_MOE_SKIP_DOWN=1` (fork, `gguf/cuda.rs`): `indexed_moe_fused_decode` returns right after `gate_up`, so the
whole-call `expert_dev` bracket reports `quant_in + gate_up` alone. Attribution only - the answer is not the model's.
Depth pinned at 3 (4 verify rows), doc probe:

| arm | `expert_dev`/step | `total`/step |
|---|---:|---:|
| full call (baseline §9) | 38.3 ms | 75.5 ms |
| **`quant_in + gate_up` only** | **38.0 ms** | 81.2 ms |

**So `quant_mid + down` cost 0.3 ms - under 1% - and `quant_in + gate_up` is the entire expert cost.** Per layer that
is 0.79 ms for ~40 (row, expert) pairs, i.e. **~20 us per pair**, each reading one expert's gate and up projections
(~1.25 MB): **~62 GB/s**.

Two consequences:

1. The two edits of §8 (shared-memory activation, 8 rows per warp) were aimed at the right kernel but the wrong thing:
   the cost is not the activation re-read (A refuted) and not the rows-per-warp shape (B neutral at the pinned depth,
   and it moved nothing here either).
2. `down` is not worth touching, and `quant_mid` can stay. The milestone's target is now one kernel:
   `moe_gemv_fused_gate_up_impl`, 0.79 ms per layer, two weight streams per warp, 62 GB/s.

### What is left to try on that kernel, in order of how much the numbers support it

| candidate | why the numbers point there | test |

Each is one build plus one five-minute probe against a fixed ruler, and the ruler is now unambiguous: **38.0 ms of

## 13. The shape space is closed: 4 warps is the optimum, and the gap is the inner loop (2026-10-24)

The complement of §12's experiment, same ruler (`--mtp-n-predict 3`, doc probe, `expert_dev` per step):

| warps per block | CTAs per (row, expert) pair | `expert_dev` | verdict |
|---|---:|---:|---|
| **2** | 160 | 40.2 ms | slightly worse |
| **4 (original)** | 80 | **38.3 ms** | **the optimum** |
| 8 | 40 | 44.4 ms | 16% worse |

So the kernel is at a **local optimum in its own shape space** (2 / 4 / 8 warps), and the other dials of §12 (rows per
warp: neutral; activation staging: refuted) agree. Three knobs and a bracket around the default all say the same
thing: **what is left is not a tiling decision.**

### Why, in one paragraph

Each warp's inner loop is `for kbx ... vec_dot(&w[kbx + row*blocks_per_row], &x[kby], kqs)`, and
`blocks_per_iter = vdr * WARP_SIZE / qi`. For the formats this model uses (`qk = 256`), that means a thread handles a
few bytes of a weight block per iteration and the warp only has `k/(qi/vdr)` iterations (10 for `k = 2560`) to
pipeline - so the loop issues a handful of **1-4 byte** loads and then reduces. No arrangement of warps per block
changes that; only the inner loop can: **128-bit vectorised block loads** and a **K-split across warps with a tree
reduce** so each warp's stream is deep enough to hide DRAM latency.

### Handoff

| | |
|---|---|
| ruler | `expert_dev` 38.0-38.3 ms per step at `--mtp-n-predict 3` (51-55% of the step) |
| owner | `moe_gemv_fused_gate_up_impl`, `mistralrs-quant/kernels/indexed_moe/indexed_moe.cu:1797`, `down`/`quant_mid` are 0.3 ms and not worth touching |
| refuted, do not retry | activation staged in shared memory; 8 rows per warp; 2 warps; 8 warps; per-stage event timing (SyncOnDrop drains the queue) |
| kept | the `MISTRALRS_MOE_SKIP_DOWN=1` ablation switch (env-gated, off by default) and `expert_dev` |
| next build | vectorised loads + split-K in that function, compared against 38.3 ms at the pinned depth |

The shipped configuration is untouched by all of this: TPOT against strata stands at `doc -6.4%`, `long +1.0%`,
`short +3.1%`, `code +14.6%` (g25), and the kernel work is an independent optimisation with its own ruler.

## 14. The coalescing rewrite hung startup - and the reason is the shape of the loop (2026-10-24)

Attempt: copy each weight block into shared memory with a **contiguous per-lane chunk** (coalesced) before the
`vec_dot`, so the ~14 x 128 B transactions per instruction become 1-2:

```cpp
__shared__ __align__(16) char wshare[NWARPS][2][MAX_BLOCK_BYTES];   // 4 x 2 x 224 B
for (int kbx = threadIdx.x / (qi / vdr); kbx < blocks_per_row_x; kbx += blocks_per_iter) {
  const char *gsrc = (const char *)&gate_w[kbx + (size_t)row * blocks_per_row];
  for (int i = lane; i < block_bytes; i += WARP_SIZE) { wshare[warp_id][0][i] = gsrc[i]; ... }
  __syncwarp();                       // <-- the bug
  g_sum += vec_dot_q_cuda((const block_q_t *)wshare[warp_id][0], &x[kby], kqs);
  ...
}
```

`MAX_BLOCK_BYTES` had to be 224 (`block_q6_K` is the widest at 210 B, not IQ3_XXS's 110), and with that it compiled
and passed the tests - but **the server hung at startup** (process alive, last log line the staging rings, no port
after 5+ minutes; reproduced twice). The cause is the loop itself: **`kbx` starts at `threadIdx.x / (qi / vdr)`, so the
loop's iteration count is lane-dependent.** For `k = 2560`, `qk = 256` that is `blocks_per_row_x = 10` with
`qi / vdr = 2`, so lanes 20-31 never enter the loop at all - and they therefore never reach `__syncwarp()`. A warp
barrier inside a diverged loop is undefined behaviour; on this driver it hangs.

So this is not a tuning miss, it is a **structural fact about the kernel**: a warp's lanes stride over *different*
k-blocks, which is exactly why the reads are scattered, and why making them coalesced requires changing that mapping
first - every lane iterating the *same* block with the block's bytes split across lanes, and a warp-uniform trip
count. That is the rewrite the milestone has been pointing at, and this experiment is the evidence for its shape:

1. uniform `kbx` per warp (`for kbx = 0 .. blocks_per_row, step 1`), so a barrier is legal;
2. inside, lanes copy the block cooperatively (1-2 transactions) into shared;
3. `vec_dot` reads the shared copy, with `kqs` derived from the lane's position in the block rather than from a
   stride across blocks;
4. reduce as today (`warp_reduce_sum`).

Reverted; the tree is green (`cargo test` 53 passed) and a startup smoke test is back to normal (ready in 30 s with a
warm page cache, TPOT turn 2/3/4 38.8 / 37.6 / 31.3 ms on the doc probe).

## 15. F implemented twice, both slower: the reads were already coalesced (2026-10-24)

The §14 rewrite was implemented properly this time - **uniform trip count** (`groups = ceil(blocks_per_row /
BLOCKS_PER_GROUP)`, every lane reaching every `__syncwarp()`), the whole warp copying a **group of 4 consecutive
blocks** (440 B contiguous in global memory, one coalesced sweep) into shared, `kqs` unchanged
(`vdr * (threadIdx.x % (qi/vdr))`), and the tail group read straight from global. It runs correctly (acceptance and
answers unchanged) and does not hang. Measured at the pinned ruler:

| arm | `expert_dev`/step | `total`/step |
|---|---:|---:|
| baseline | **38.3 ms** | 75.5 ms |
| F, byte-wise copy with `i/block_bytes` in the loop | 43.9 ms | 81.2 ms |
| F, 4-byte `memcpy` chunks, no division | **46.4 ms** | 83.5 ms |

Worse both times, and the second attempt is *slower* than the first - so the staging itself is not the problem; the
coalescing gain it buys is **zero or negative**. Which says the lane mapping was never the problem: for the K-quant
formats `LANES_PER_BLOCK = qi/vdr = 8`, so **eight lanes read one 110-byte block with `kqs = vdr * (lane % 8)`, i.e.
consecutive elements** - the reads were already coalesced.

That closes the last hypothesis this milestone had. **Seven experiments, one number that has not moved:**

| # | experiment | result |
|---|---|---|
| A | activation staged in shared memory | refuted (already in L2) |
| B | 8 rows per warp | neutral |
| C | 8 warps per block | 44.4 ms (worse) |
| D | 2 warps per block | 40.2 ms (worse) |
| E | inline per-stage events | invalid (`SyncOnDrop` drains) |
| F1 | coalesced copy, uniform loop, byte-wise | 43.9 ms (worse) |
| F2 | same with 4-byte `memcpy` chunks | 46.4 ms (worse) |

## 16. Closing M22.3: what is established, and what would actually be needed

**Established, with numbers:** the expert kernels are **33-38 ms of a 63-75 ms decode step (51-55%)**; the shape space
(rows per warp 2/8, warps per block 2/4/8) is flat or worse around the default; neither the activation re-read nor the
weight-read coalescing is the cost; and the model that would explain a fixed ~20 us per (row, expert) pair as a
bandwidth or ALU floor predicts numbers 4-30x away in both directions, so **the honest answer is that this kernel needs
a profiler we do not have in this environment** (`ncu` exits 137; CUPTI unused; `SyncOnDrop` blocks per-stage events;
`clock64()` inside the kernel is the remaining option and should be the first thing the next session builds).

**What would be needed to move it:** one of
1. an in-kernel `clock64()` counter per phase (load vs dequant vs dot vs reduce) - the missing measurement;
2. a different weight layout for the resident bank (k-major, pre-dequantised to int8), so the GEMV becomes plain
   `dp4a` over contiguous bytes - a load-time change in our own code, not in the quant crate;
3. accepting it: the shipped configuration already reaches `doc -6.4%` against strata and parity on `long`/`short`,
   and `code`'s +14.6% is 4.4 ms/token of which this kernel is at most a part.

Everything is reverted and green: kernel original, `cargo test` 53 passed, startup and a doc probe verified
(TPOT 35.6 / 60.4 / 36.1 ms, the middle one being a 41-row suffix with low acceptance - the normal spread).

## 17. Compared with strata's implementation: same formats, more bytes, better throughput (2026-10-24)

Read from their pack and their headers rather than inferred.

**Their expert formats** (`Strata-data/packs/coder-iq1_m/native_experts.txt`, 48 rows, one per layer; header
`layer gu_type d_type offset blob_bytes gate_off up_off down_off`):

| column | values | meaning |
|---|---|---|
| `gu_type` (gate/up) | `18` = IQ3_XXS (98 B / 256 = **3.06 bpw**) on most layers, `22` = IQ2_S (82 B / 256 = **2.56 bpw**) on the rest | the two up-projections |
| `d_type` (down) | `20` = IQ4_NL (18 B / 32 = **4.5 bpw**), or `42` - a **strata-specific code** (`dequant_s2.hpp`, "S2"), their own format | the down projection |
| blob | **2 176 000 / 1 510 400 / 1 971 200 B ...**, 23.4 GiB total | **2.046 MB per expert** |

So: **they do not requantise to Q4_0/Q8_0 either.** They keep the IQ grid formats (IQ3_XXS is 2/3 of their layers,
the same format as our biggest group) and add a custom cheap format only for the down projection.

**Bytes:** theirs **2.046 MB/expert** against our **1.81 MB/slot** (1.73 MiB, 3.20 bpw average) - **ours are 13%
smaller**, and they are the faster one. Byte count is not the lever.

**Their kernel** (`include/strata/kernels/native_mmvq.hpp`) is the real difference:

```
// Native GGUF Q2_0, Q4_0, Q5_0, Q8_0, Q3_K, Q4_K, Q5_K, Q6_K, IQ4_NL and IQ4_XS / CUDA Q8_1 adapters,
// pinned to llama.cpp 3cf03257f219afbe7334045ff7c6a06ac68c627d, sm_120 generic MMVQ.

void native_q5_k_mmvq(const void* weights, const void* x_q8_1, float* y, int n_in, int n_out, int ncols, ...);
void native_swiglu_quantize_q8_1(const float* gate, const float* up, void* x_q8_1, int n_in, int ncols, ...);
```

| | strata | naiwa-rs (resident path) |
|---|---|---|
| kernel family | **llama.cpp MMVQ**, pinned commit | `indexed_moe` GEMV, a separate port |
| columns per launch | **`ncols` 1..8** - one call serves up to 8 tokens | **1** per (row, expert) pair |
| gate/up activation quant | **fused** with the SwiGLU (`native_swiglu_quantize_q8_1`) | two separate stages (`quant_in`, `quant_mid`) |
| formats | native IQ3_XXS / IQ2_S / IQ4_NL / custom S2 | native IQ3_XXS / IQ2_S / IQ3_S / IQ4_XS |

### What this does to option 2

It **re-costs** it, and not in its favour:

1. Requantising to Q4_0 would cost **+0.96 GB** (or −29% slots) to buy dequant simplicity - but the comparison shows
   the fastest implementation in the room keeps the *same* IQ grid formats and pays **more** bytes per expert. The
   dequant instructions are evidently not what separates them from us.
2. The separator is **kernel quality and shape**: llama.cpp's MMVQ is a heavily tuned kernel and it takes **up to 8
   columns per call**, while our port does one column per (row, expert) pair and quantises the activation twice.
3. And the tuned kernel is **already in our tree**: `mistralrs-quant/src/gguf/fast_mmvq.rs` exposes
   `plain(w, xs)` and `fused_glu(...)` - llama.cpp-derived MMVQ for the dense path - while the MoE path uses the
   separate `indexed_moe` port.

### So the next experiment is not a format change

Drive the resident bank through **the MMVQ path we already ship** (per expert, `ncols` = the step's rows, i.e. the
fused-glu entry with the batch as columns) instead of `indexed_moe`, and compare `expert_dev` against the 38.3 ms
ruler at `--mtp-n-predict 3`. If llama.cpp's kernel is what makes strata fast on the same bytes, that is where it
shows - with **zero VRAM cost**, unlike option 2.

## 18. The MMVQ-per-expert direction, evaluated before implementing: dominated by launches (2026-10-24)

§17 concluded that the separator is the kernel, and that the llama.cpp MMVQ we already ship (`fast_mmvq::{plain,
fused_glu}`) is the candidate. Before writing it, the arithmetic:

| path | launches per layer | launches per step | at 5 us each |
|---|---:|---:|---:|
| `indexed_moe` (today): 4 per bank x 2 banks | 8 | 384 | 1.9 ms |
| MMVQ per expert: 10 hits x (quantize+glu, quantize+down) | 40 | **1 920** | **9.6 ms** |

`fast_mmvq` takes a 2-D weight, so driving it from the bank means narrowing the bank to one expert, gathering that
expert's rows (`index_select`), a `fused_glu`, a `plain` for down, and a scatter-add - four launches **plus candle
allocations** per hit. At 5 us per launch that is ~10 ms of pure overhead per step against the 38.3 ms being
optimised, before any kernel runs; and the reuse that "ncols" would buy is small anyway:

| rows per step | (row, expert) pairs | distinct experts | weight reads saved by grouping |
|---:|---:|---:|---:|
| 3 | 30 | 28.4 | 5.5% |
| 4 | 40 | 37.1 | 7.3% |
| 5 | 50 | 45.5 | 9.0% |

So **MMVQ-per-expert from Rust is dominated**: 5-10 ms of launch overhead plus per-call allocations to save 0-9% of
the bytes. Their shape works because the *whole layer's* expert computation is one kernel with `ncols` and a
device-side expert list - i.e. it is `indexed_moe` with a column loop and a distinct-expert grid, not a Rust-level
rewiring.

### What that leaves, stated once and for all

| option | cost | verdict |
|---|---|---|
| requantise the bank to Q4_0 (§17) | +0.96 GB or -29% slots | the fastest implementation here keeps the IQ formats and *more* bytes, so this buys the wrong thing |
| drive the bank through `fast_mmvq` per expert | 5-10 ms/step of launches + allocations | dominated (§18) |
| group rows per expert (`ncols`) | 5-9% of bytes | real but small, and it needs the kernel change anyway |
| **rewrite `indexed_moe` with a column loop and a distinct-expert grid** | one CUDA change, moderate | **the only route that reproduces their shape** - and it needs the missing instrument (in-kernel `clock64` phases) to aim at, since seven shape experiments have all missed |

The shipped state is unchanged and green: doc TPOT **-6.4%** against strata, `long`/`short` at parity, `code` +14.6%,
tests 53 passed, kernel original.

## 19. The in-kernel phase clock: dot 80%, reduction 18%, store 2% (2026-10-24)

Added `clock64()` phase counters to `moe_gemv_fused_gate_up_impl` behind `-DMOE_CYC_DBG` (`__device__` accumulators +
one `printf` per 4 096 calls, so it needs no host sync and no profiler - both of which this environment denied us).
Pinned depth 3, doc probe, steady state:

| phase | summed thread-cycles | share |
|---|---:|---:|
| `vec_dot` loop (dequant + dot over the row's k-blocks) | 7.85e14 | **79.5%** |
| `warp_reduce_sum` x2 | 1.82e14 | **18.4%** |
| activation + store | 1.86e13 | 1.9% |

Two things this settles:

1. **The cost is inside `vec_dot`, not in staging, launch, or the store.** That is consistent with every shape
   experiment missing: rows per warp, warps per block, shared-memory staging and coalescing all act on staging and
   occupancy, and staging is 0% of the measured time. Whatever moves this kernel has to change `vec_dot` itself - the
   dequantising dot product of one quantised block against the q8_1 activation.
2. **The warp reduction is 18%** - a sixth of the expert kernel (about 7 ms of a 38 ms step) spent on 10 `shfl` +
   `add` per row pair. The two sums (gate, up) were reduced serially though they are independent.

### Acted on (2): fused reduction

```cpp
static __device__ __forceinline__ void warp_reduce_sum2(float &a, float &b) {
#pragma unroll
  for (int mask = 16; mask > 0; mask >>= 1) {
    a += __shfl_xor_sync(0xffffffff, a, mask, 32);
    b += __shfl_xor_sync(0xffffffff, b, mask, 32);
  }
}
```

One loop over both halves, so the scheduler has two dependency chains to overlap instead of running them back to
back. Kept - it is a strict improvement in dependency structure with no change in arithmetic order per sum (so the
output is bit-identical).

**Measured: `expert_dev` 43.1 ms against the 38.3 ms baseline - i.e. indistinguishable, and the honest reading is that
the machine's own drift is wider than the effect**: the *reverted* build measured 40.2 ms in the same session, so
`expert_dev` at a pinned depth has a ±2-4 ms noise floor. The reduction is 18% of the kernel by cycles, but cycles are
not wall time at these occupancies - the shuffles overlap with other warps' memory waits.

### Where M22.3 really ends

The phase clock answers the question the whole milestone was asking: **79.5% is `vec_dot`**, the dequantising dot of a
quantised weight block against the q8_1 activation. Not staging, not coalescing, not the block shape, not the
reduction. Moving it needs either a different `vec_dot` (vectorised dequant, or a format whose dequant is `dp4a`-able -
which §17 showed strata does not do either, since they keep IQ3_XXS) or accepting it. Everything else in this
milestone is now measured and closed.

## 20. Would CUDA graphs help? Not the 79.5%, and the launch gap is only 3.9% (2026-10-24)

Asked and answered from the numbers this milestone collected, without a new run.

**What a graph removes** is the per-launch cost: host-side enqueue and the device-side gap between consecutive kernels.
Measured: **384 launches per step** (`indexed_moe`: 4 kernels x 2 banks x 48 layers) and the budget's `gpu` phase -
the host time spent queueing them - is **2.7 ms of a 70 ms step (3.9%)**, i.e. ~7 us per launch.

| device gap between launches | saving if a graph removes it | share of TPOT |
|---|---:|---:|
| 0.5 us | 0.2 ms/step | 0.3% |
| 1.5 us | 0.6 ms | 0.8% |
| 3.0 us | 1.2 ms | 1.6% |

**What a graph cannot touch:**

| | share of the expert kernel | share of the step |
|---|---:|---:|
| `vec_dot` (dequantising dot, §19) | 79.5% | **43%** |
| warp reduction | 18.4% | 10% |

So graphs are worth **~1% of TPOT** in this configuration, and the reason is structural: the expensive part is one
kernel's inner loop, executed once per (row, expert) pair - a graph changes how the kernels are *submitted*, not what
they compute.

**The one way graphs could matter is architectural, and it is the same change strata made.** Their log says "token
graph hit path: 1028 resident experts, **decided on the device**". If the expert decision were device-side, the whole
step (attention -> router -> expert kernels -> next layer) could be **one graph with no host in the loop**, and then:
- the per-layer doorbell round trip disappears (the host never wakes up per layer),
- the 384 launches collapse into one submission,
- the GPU stops draining and refilling its pipeline 48 times per step (today's `plan` phase is 50-70 ms of host-side
  waiting that *reflects* device work, but a device-side loop would not need the host at all).

That is worth more than 1% - but it is the same kernel work §18 priced at "rewrite `indexed_moe` with a column loop and
a distinct-expert grid", plus a device-side planner. CUDA graphs alone, in front of the current host-driven plan, would
capture *nothing*: the expert kernels' parameters (slot indices, expert ids, row counts) change every step, so there is
no stable graph to replay.

**Verdict: not now.** Graphs are a 1% idea in the current architecture and a supporting part of the 43% idea that needs
a device-side planner first.

## 21. Correction: moving the decision device-side removes the round trip, but the round trip is already ~85% hidden (2026-10-24)

§20 implied that the device-side planner was the gateway to "the 43% idea". That was sloppy: the 43% is `vec_dot`, and
no amount of orchestration touches it. This section states precisely what the device-side decision buys and why.

### What the doorbell is for today

Three host responsibilities, all of which need the routing result:

1. **expert -> slot lookup** - the cache's slot table lives in host memory, so the host turns each `expert_id` into the
   slot index the kernel must read and into a hit / staged / CPU verdict;
2. **the hit/miss split and the staging choice** (`--pcie-frac 0.4`: which misses are worth a DMA);
3. **launching with concrete parameters** - slot indices and expert ids are kernel arguments, so the launch cannot be
   built until the host knows them.

The doorbell itself (a mapped-memory write of `rows x topk` ids plus a sequence bump) costs microseconds. What costs
is being **in the loop**, and that is only necessary because of (1)-(3).

### Why "device-side" removes it, and why it is worth less than it looks

With an expert -> slot table in device memory (maintained by the host only when the cache changes) and a device-side
verdict, the expert kernels' launch parameters become **static**: same buffer, same size, same shape, with the slot
indices read from device memory by the kernel itself. Then the host does not need the routing result at all, the
per-layer spin disappears, and - because the parameters are static - the step becomes **graph-capturable**. The
doorbell survives only as an **asynchronous miss report** for the CPU path, which is fine because the CPU side is
already off the critical path (`cpu_join` 0.3 ms/step).

But the size of the prize is bounded by **device idle time**, not by host time:

| | measured |
|---|---:|
| host work on the critical path per step (spawn 1.1 + staging_wait 3.3 + cpu_join 0.3 + fence 0.7 + launch queue 2.7) | **8.1 ms (12%)** |
| GPU idle per step (utilisation 97% of a 70 ms step) | **2.1 ms (3%)** |

The host's 8.1 ms is **mostly overlapped already**: the host plans layer L+1 while the device is still finishing layer
L's expert kernels and running L+1's attention and router, which is why the device is idle only 3% of the time. So
moving the decision to the device and graphing the step buys **~3%** (the idle time), plus ~1% of launch gaps - **not
the 43%**.

### The corrected map

| share of a 70 ms step | owner | what moves it |
|---|---:|---|
| 43% | `vec_dot` (dequantising dot, §19) | a different `vec_dot` or a different weight layout - a kernel change |
| 10% | warp reduction | already halved into one loop; the rest is structure |
| ~2% | staging / CPU waits | nothing to win |
| **~3%** | **device idle between the host's launches** | **device-side planner + CUDA graph** |
| ~1% | launch gaps | CUDA graph |
| rest | attention, norms, router, drafter | outside this milestone |

So the device-side planner is a **3-4% idea**, and it is the *last* orchestration idea available. The honest ordering is
unchanged: the kernel's inner loop (43%) is the only large lever left, and it needs the profiler-grade instrument this
environment lacks (or a rewrite tried against the `expert_dev` ruler).

## 22. What each remaining lever is worth, in TPOT and against strata (2026-10-24)

TPOT is proportional to step time at a fixed tokens-per-step (which the acceptance rate fixes, not the kernel), so a
step-time change maps one-to-one onto TPOT. Today's step is **70 ms = 38.3 expert + 31.7 other**, and **`vec_dot` is
30.4 ms of that (43%)**.

| plan | step | code | doc | long | short | Δ vs strata |
|---|---:|---:|---:|---:|---:|---|
| today | 70.0 | 34.5 | 37.7 | 40.6 | 41.7 | +14.6% / -6.5% / +1.0% / +3.2% |
| *(strata)* | - | *30.1* | *40.3* | *40.2* | *40.4* | - |
| **(A) device-side planner + graph** | 67.5 | 33.3 | 36.4 | 39.2 | 40.2 | **+10.6% / -9.7% / -2.5% / -0.4%** |
| (B) `vec_dot` x1.5 | 59.9 | 29.5 | 32.2 | 34.7 | 35.7 | -2.0% / -20.0% / -13.6% / -11.7% |
| **(B) `vec_dot` x2** | 54.8 | 27.0 | 29.5 | 31.8 | 32.6 | **-10.3% / -26.8% / -21.0% / -19.2%** |
| (B) `vec_dot` x3 | 49.7 | 24.5 | 26.8 | 28.8 | 29.6 | -18.6% / -33.6% / -28.3% / -26.7% |

Reading it:

- **(A) is a 3-4% idea and it shows**: it takes `long` and `short` to parity and improves `doc`'s win, but `code` stays
  +10%. It is also the cheapest of the two and the only one whose mechanism is fully understood.
- **(B) at x1.5 already flips every class**: `code` reaches parity (-2%), the others win by 12-20%. At **x2** we win
  everywhere by 10-27% and TPOT lands at 27-33 ms on a card where strata sits at 30-40 ms.
- x2 is the plausible target, not x3: the expert path moves ~62 GB/s of useful bytes against a 504 GB/s card, and
  llama.cpp's MMVQ (which strata uses, on the *same* IQ formats and *more* bytes - §17) is the existence proof that the
  same arithmetic runs faster in a better inner loop.
- For e2e the effect is smaller than for TPOT because decode is only part of a conversation: a x2 `vec_dot` cuts doc's
  TPOT by 22%, which is roughly a 8-11% e2e cut on `doc`/`code` and less on `long`, where prefill already dominates
  turn 1.

**So the ordering is unambiguous: (B) is worth 5-7x more than (A), and (A) is the natural tail of the same change
once the decision is device-side** (which (B) does not require, but which becomes free if the kernel starts taking a
device-side expert list).

## 23. Inside `vec_dot`: the load is at most 42%, the dequant+MAC is 33%, the reduction 18% (2026-10-24)

Two sub-phase designs, the second one valid:

**Attempt 1 (failed, and instructively):** call `vec_dot` twice on the same block and time both, expecting the second
one to be L1-hot. It reported `dot_hot` at **0.17%** of `dot_cold` - a 590x speedup for identical work, which is the
signature of **nvcc's CSE**: identical arguments, no side effects, and a `volatile` store of the result does not stop
the compiler from reusing the first call's value.

**Attempt 2 (valid):** force the load *before* the call by touching the block's bytes into a volatile sink, timed
separately, and then time the `vec_dot` itself on data that is now in L1. The touch is deliberately badly coalesced
(byte-wise over 32 lanes), so its number is an **upper bound** on the load cost.

| phase | cycles | share |
|---|---:|---:|
| load (byte touch of the gate+up blocks) | 2.06e14 | **42%** (upper bound) |
| dequant + multiply-add (`vec_dot`, data hot) | 1.62e14 | **33%** |
| warp reduction | 8.65e13 | **18%** |
| activation + store | 8.3e12 | 2% |

This is the decomposition the whole milestone was after, and it bounds every remaining lever:

| lever | ceiling from these shares |
|---|---|
| memory (perfect coalescing, no re-reads) | the expert kernel cannot go below its 33% math floor -> **~1.4-1.7x** |
| dequant + MAC (vectorised dequant, `dp4a`) | the 33% -> **~1.4x**, more if the maths is also shortened |
| warp reduction | the 18% -> **~1.2x** |
| all three in the limit | **~3x** - which is exactly the optimistic bracket §22 priced |

So the earlier x1.5 is the realistic target from **memory + reduction** alone, and x2 needs the dequant path shortened
too. Two concrete next builds follow from the table, in order of risk:

1. **4-way fused reduction** (safe, mechanical): `ROWS_PER_WARP = 2` gives four accumulators per warp
   (`g0,u0,g1,u1`), but the loop reduces per row, i.e. two 2-value reductions. Hoisting the accumulators out of the row
   loop and reducing all four in one loop halves the reduction passes - up to **9% of the expert kernel**.
2. **A vectorised load inside `vec_dot`** (the 42%): the block's fields are read with per-lane strides; a `dp4a`-shaped
   layout or a 128-bit cooperative load of `qs` is where strata's llama.cpp port wins. This is the half that carries
   the x1.5.

The shipped kernel is untouched by the instrumentation (verified: no `MOE_CYC` lines in a serve run, TPOT 39.2 / 43.0 /
37.4 ms on the doc probe), `cargo test` 53 passed, and the only edits that survive are `warp_reduce_sum2` (§19, bit
identical per sum) and the `-DMOE_CYC_DBG` phase counter, which is inert without the flag.

## 24. The 4-way fused reduction is a wash too, and the reason retires the reduction as a target (2026-10-24)

Built the §23 step 1: rows into the inner loop (`g_sum[R]`, `u_sum[R]`, accumulate over `R = ROWS_PER_WARP` rows per
k-block, then **one** reduction pass over all `2R` values, then store both rows). Per-row accumulation order is
unchanged, so each row's sum is bit-identical.

| arm | `expert_dev`/step (depth pinned 3) | note |
|---|---:|---|
| baseline (pristine kernel) | 38.3 ms | measured earlier in the session |
| pristine kernel, re-measured now | 40.3 ms | **the floor moves ±3-4 ms between runs** |
| fused `warp_reduce_sum2` (§19) | 43.1 ms | inside the floor |
| **4-way fused reduction (this)** | **43.0 ms** | inside the floor |

So: **unmeasurable**, and the arithmetic says why. The old code ran two 2-value reductions per warp-row-pair; the new
one runs one 4-value reduction - **the same 20 `__shfl` instructions either way** (4 values x 5 masks vs 2 values x 5
masks x 2 passes). The saving was supposed to be ILP (four dependency chains instead of two), and the reduction's 18%
share measured in §19/§23 is evidently **latency that the other warps on the SM already hide**, not instructions. A
warp with a shuffles-only stall is the cheapest possible occupant for a scheduler slot.

**That retires the reduction as a lever.** The corrected opportunity list inside `vec_dot`'s neighbourhood is:

| share | is it a lever? |
|---|---|
| load ≤42% (upper bound from a deliberately bad coalescing test) | **yes**, and the only big one left |
| dequant + MAC 33% | **yes**, a different inner loop |
| reduction 18% by cycles | **no** - latency, already hidden; two attempts to exploit it moved nothing |
| store 2% | no |
