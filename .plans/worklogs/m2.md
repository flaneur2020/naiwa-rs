# M2 — per-layer MoE graph (resident path only)

**Status: IN PROGRESS** (started 2026-10-16). Progress scratch for `roadmap.md` M2.

## Goal (from the roadmap)

Capture the MoE segment (quantize → gate+up → quantize → down+aggregate) of **one layer** into
one CUDA graph and replay it, instead of ~60 host launches. Resident path only — no misses, no
PCIe. Judged by:

1. fully-resident config: greedy identical to eager;
2. one layer goes from ~60 launches to **1 launch, 0 spins**;
3. the one-time cost of ~150 captures is measured;
4. pad rows are excluded by `real_rows`.

Scaffolding, not target behavior: misses enter the graph in M3/M4 (architecture-v2 §6.2).

## Depends on

M1's `MoeDecodeCapture` (fork `729d2c64`) — the fixed-grid, fixed-buffer launch of the same four
kernels. M1's *engine* wiring was deliberately halted; M2 subsumes it (the capture path is the
engine path).

## Design

### The capture unit

`MoeDecodeCapture::run` already *is* the segment: 4 raw launches, fixed grid
`(⌈n/8⌉, max_topk, max_batch)`, all buffers owned and fixed. So capture = wrap those launches in
`stream.begin_capture` / `end_capture`. Per architecture-v2 §6.2: **our own narrow registry**, not
the fork's whole-step `cuda_graph.rs`.

cudarc 0.19.10 API (verified): `CudaStream::begin_capture(mode)`,
`CudaStream::end_capture(flags) -> Ok(Some(CudaGraph))` (it instantiates internally),
`CudaGraph::upload()`, `CudaGraph::launch()`.

### Input must be a fixed staging buffer

The quantize kernel reads the activation, and candle allocates activations per step → the address
would change per step, which a captured graph cannot tolerate. So `MoeDecodeCapture` owns a fixed
`staging: CudaSlice<f32>` of `[max_batch, hidden]`, and the caller copies the activation into it
(a **D2D memcpy, outside capture**) before each replay. This is exactly architecture-v2 §3.3.5's
"inputs must be pre-staged to fixed buffers".

### `quantize_input_q8_1_into` is capture-unsafe here

Its F32 path does `xs_contig.to_dtype(F32)` — an **allocation inside capture**, which
`check_capture_copy`/the memory pool do not permit. And its BF16/F16 path demands a half-typed
tensor. So the segment calls `quantize_q8_1(&staging, …)` **directly** (F32, no cast, no
allocation).

## Result — capture/replay of the segment works (kernel level)

`MoeDecodeCapture` now owns a fixed F32 `staging` buffer and a captured `CudaGraph`, and exposes
`stage` / `run` (eager) / `capture` / `replay`. `launch_segment` was factored so both paths run
identical launches.

**Evidence** (`cuda_moe_decode_capture_graph_replays_eager_identical`):

```
M2 capture/replay: diff A 0, diff B 0, A-vs-B 5968.8750
capture 3x2 max abs diff vs indexed: 0.000000
capture 5x5 max abs diff vs indexed: 0.000000
test result: ok. 2 passed   (full suite: 549 passed, 0 failed)
```

Replay is **bitwise** identical to the eager path for two different activations (diff 0, 0).
`A-vs-B = 5968` proves the graph reads the *current* staging contents — the pointers are baked
by the capture, the data is not. That is the property the whole per-layer design rests on.

## Gotchas found (each cost a failed run)

1. **Event tracking must be off while capturing.** First attempt: `CUDA_ERROR_STREAM_CAPTURE_INVALIDATED`.
   candle tracks events by default and `cuEventRecord` is illegal during capture. The fork's
   whole-step capturer already works around this (`disable_event_tracking_for_capture`); it is
   `pub(crate)` in `mistralrs-core`, which `mistralrs-quant` cannot import, so the same
   disable/restore is replicated in `capture`.
2. **The output accumulator must be zeroed *inside* the segment.** The down+aggregate kernel
   sums across topk blocks with `atomicAdd`. The eager `indexed_moe_fused_decode` got a fresh
   `alloc_zeros` per call, so this was invisible — but a replayed graph reuses one buffer, and
   the test caught the result being **doubled** (diff ≈ |A| = 975037). Fixed with a
   `cuMemsetD32Async` at the head of `launch_segment` (a capturable stream op). This bug was
   latent in M1.1's `MoeDecodeCapture` too; it only passed because each test object ran once.
3. **`quantize_input_q8_1_into` cannot be used in a capture.** Its non-BF16/F16 path does
   `to_dtype(F32)` — an allocation. Replaced by `quantize_q8_1` on the fixed F32 staging buffer.

## Still open for M2

- The engine does not use this yet: no `MoEGraphKey` registry, no per-layer graph, and the
  **launch count** criterion (~60 → 1 per layer) has not been measured on the engine.
- The engine's activation is BF16; staging is F32, so integration needs either a BF16 staging
  buffer (hits the fused `launch_quantize_q8_1_bf16`, no cast) or a one-off cast outside capture.
  Decide at integration time.
- One-time capture cost (~150 graphs) still unmeasured — it needs the engine's per-layer set.
