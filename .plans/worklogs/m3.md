# M3 — CPU result return path into the graph (misses enter the graph)

**Status: IN PROGRESS** (started 2026-10-16). Progress scratch for `roadmap.md` M3.

## Goal (from the roadmap)

Replace `deferred`'s `cudaLaunchHostFunc` with the zero-argument `wait_copy_ptr`, so a miss's
CPU result is pulled in by a **graph node** spinning on a mapped seq instead of a host function
blocking candle's stream. Judged by: ① with misses present, greedy == eager; ② misses handled
**inside** the graph (a counter proves no eager path is taken); ③ zero sync points on the token
thread (STEP_DBG dry bucket drops); ④ failure injection — a worker error still bumps seq, so the
GPU never spins forever.

## Step 0 (this work): F3 — port the M0-validated primitives into the fork

M0 (`worklogs/m0.md`) proved the zero-argument pattern in a standalone harness; the fork still
only has the versions that take `target` / `slot_off` as **kernel arguments**, which a captured
graph freezes at capture time.

**F3 is additive**: the new cells go *after* the payload ring in `FlagBuf`'s mapped allocation,
so every existing offset (`seq` at 0, payload at 8) is untouched and the proven R2b path cannot
regress.

```
layout: [seq u32 @0][pad][payload ring @8, RING_DEPTH * max_n f32]
        [target u32][pad][slot_off i64]        <- F3 control cells, appended
```

New kernels `doorbell_wait_seq_ge_ptr_kernel` / `doorbell_wait_copy_f32_ptr_kernel` read
`*d_target` / `*d_slot_off` from mapped memory instead of receiving them. Rust:
`FlagBuf::set_target`, `set_slot_off`, `wait_seq_ge_ptr`, `wait_copy_slot_ptr`.

## F3 result — done (fork `c132611e`)

`doorbell_wait_seq_ge_ptr` / `doorbell_wait_copy_f32_ptr` added to `doorbell.cu`, FFI, and
`FlagBuf` (`set_target`, `set_slot_off`, `wait_seq_ge_ptr`, `wait_copy_slot_ptr`). The control
cells are **appended** after the payload ring, so the existing R2b offsets are untouched.

```
cargo test -p mistralrs-core --features cuda --lib doorbell
  -> test cuda::doorbell::ptr_wait_tests::wait_copy_slot_ptr_reads_target_and_slot_from_mapped_memory ... ok
```

The test drives the *same* channel twice through unchanged kernel parameters (only the mapped
cells move) and checks a payload-less seq bump still unblocks the wait — i.e. the two properties
a captured graph depends on.

## What M3 actually has left (recon 2026-10-16)

`deferred` **no longer uses `cudaLaunchHostFunc`** — W106's R2b already replaced it with the
argument-taking `wait_copy_slot`, so the host function is gone. M3's remaining work is therefore
*not* "remove the host function" but **fold the CPU-return wait into the graph**:

- today the token thread issues, per layer, a raw `wait_copy_slot` **and** a candle add, plus a
  per-step `Tensor::empty` allocation;
- M3 makes it a captured node so it costs one launch and no allocation.

### The crate boundary forces the shape

The wait kernel lives in `mistralrs-core` (`doorbell.rs`), the MoE segment in `mistralrs-quant`,
and **`mistralrs-quant` cannot depend on `mistralrs-core`** — so the segment cannot contain the
wait node. Instead the **engine** captures a second, tiny **wait+add graph** per bank using
`FlagBuf`'s zero-argument launch, and replays it right after the MoE graph.

Per layer: `MoE graph` → `wait+add graph` (the acc is the MoE graph's `out`, fixed). That is 2
graph launches instead of `wait_copy_slot` + candle add + per-step allocation, and it removes
the last token-thread wait from the CPU path.

## M3 slice 1 — wait-then-accumulate primitive (done, fork `d46e71c3`)

`doorbell_wait_add_f32_ptr` + `FlagBuf::wait_add_slot_ptr(len, acc)`: spin on the mapped target,
then `acc[i] += payload[slot_off + i]`. The down+aggregate kernel already accumulated the GPU
hits into that buffer, so one node completes the MoE result.

```
cargo test -p mistralrs-core --features cuda --lib doorbell
  -> wait_add_slot_ptr_accumulates_into_the_output_buffer ... ok   (1.0 + 10..17 == 11..18)
  -> wait_copy_slot_ptr_reads_target_and_slot_from_mapped_memory ... ok
```

## M3 slice 2 — ATTEMPTED, FOUND RACY, REVERTED (2026-10-16)

Attempted: capture a per-bank `wait+add` graph and drive it from **per-bank mapped
`target`/`slot_off` cells**, so the CPU experts' contribution lands in the MoE graph's output
buffer directly (no per-step H2D target tensor, no separate add).

**It introduced a cross-step race, caught before shipping.** `--pcie-frac 0` had been **8/8
deterministic**; with the change, three runs produced **three different continuations**:

```
1x ' Paris. The capital of Japan is Tokyo. The capital of Italy is Rome.'
1x ' Paris. The Eiffel Tower is located in Paris. The Mona Lisa is in'
1x ' Paris. The largest planet in our solar system is Jupiter. The Eiffel Tower'
```

Reverted; determinism restored (`3/3` identical). The engine tree is byte-for-byte the M2 state.

### Why it races — the cell cannot come from the host

Per-bank cells fix *cross-layer* races (each layer has its own bank) but **not cross-step** ones.
The token thread runs **ahead** of the GPU — that is the point of the whole design — so by the
time step *N*'s wait node executes, the host may already have written step *N+1*'s `target` and
`slot_off` into that bank's cells. The node then waits for the wrong seq and accumulates the
wrong payload slot: the wrong step's CPU experts get folded into this step's output.

The existing argument-taking `wait_copy_slot` is *correct* precisely because `target`/`slot_off`
are **kernel arguments**, fixed on the host at the host's current step. Zero-argument removes
that and must replace it with device-side state.

### What the design actually needs

The wait node must derive its step **on the device**, not read host-written cells:

- a ring of `(target, slot)` cells whose index comes from a **device-side counter that the node
  itself advances** (self-indexing), or
- a ring whose index is read from the same device state that publishes the payload, so node and
  publisher agree on the step.

This is the self-indexing problem flagged in the very first alignment round (architecture-v2
§6.2, the "one graph replayed 48 times" note). It is a prerequisite for **any** zero-argument
wait node, i.e. for M3's ②, and it is not something to improvise in the decode hot path.

### Status

M3 is **not finished**. The host function was already gone (W106), so ③ (no token-thread sync)
holds today; ④ (failed worker still bumps seq) holds. ② — misses handled *inside the graph* —
needs the device-side indexing above. Slice 1 (`wait_add_from`, fork `d46e71c3`) is the right
building block and stays; what is missing is the step index.

## M3 slice 1b — device-side job counter (done, fork `faea2e17`)

`doorbell_wait_add_indexed_f32` + `FlagBuf::wait_add_indexed_from(device, counter, len, acc)`:
the node **claims its job number itself** (`atomicAdd` on a device counter, 1-based) and derives
`target = n`, `slot = (n % RING_DEPTH) * max_n`. Nothing per-step is read from the host, so the
host-running-ahead race cannot occur.

```
cargo test -p mistralrs-core --features cuda --lib doorbell
  -> wait_add_indexed_claims_jobs_on_the_device ... ok   (two queued nodes take slots 1 then 2)
  -> plus the two earlier ptr tests ... ok
```

## New finding: the counter must stay 1:1 with the publisher's seq

Re-attempting slice 2 on top of the counter exposed the next coupling. The node's claim `n` is
only meaningful if **the publisher used the same n**. The publisher's seq comes from
`deferred`'s **global** `PUBLISH` counter, which advances once per `deferred::start`. So:

> every `deferred::start` must be matched by exactly one node replay, or the two numberings drift
> and a node waits for the wrong seq / reads the wrong slot.

That holds today only because the standard decode path always takes the fast path (one bank per
layer, `rows <= 16`, BF16). **Any** fallback — a second bank (`--prefill-stream`), `rows > 16` —
starts a job with no node, and every later job is off by one. That is exactly the kind of
implicit invariant that produced the race in slice 2, so it should not be shipped as-is.

The fold also needs **exactly one bank**: the node accumulates into a bank's fixed output buffer,
so with two banks the result would land in a buffer that is not the returned tensor.

### The principled fix — and it is already the documented design

Give each layer/bank its **own** CPU-return channel, with its own seq numbering **and** its own
device counter. Then:

- layer with one bank → one job, one node, one numbering — 1:1 by construction;
- layer with two banks → simply does not use the node (its channel/counter untouched), so nothing
  drifts globally;
- the counter is never shared across layers, so no global desync is possible.

This is `architecture-v2` §3.4's `flag_host_to_gpu: per-layer, ring depth 8`, and it also removes
the global channel's grow-and-retire hazard (a captured graph would otherwise be stranded on a
retired allocation). It is a `deferred` refactor (`start` takes the layer's channel instead of
fetching a global one) plus engine plumbing — on the order of 100–150 lines.

## M3 slice 2b — implemented on per-layer channels, HUNG; reverted (2026-10-16)

With per-layer channels the node needs no host-written cells: it claims its job from the
channel's own device counter, so `target = n` and `slot = n % RING_DEPTH` are the *same sequence*
the publisher uses. All 48 wait+add graphs captured cleanly. But the first decode request **hung**
(the node spinning on a seq that never arrives), so the engine side was reverted again; the tree
is the verified refactor (`44f2da0`, oracle 3/3 byte-identical) plus the fork primitives.

### Instrumented evidence (the puzzle)

```
DBG acquire min_n=40960 want=81920            x48   (channels created, correct size)
DBG set layer=0 ok=true self=0x297eb622a90           (warmup sets the channel, ok)
DBG layer=0 fast=false chan=false self=0x297eb622a90 (same printed address, OnceLock unset!)
```

`chan=false` means `self.cpu_chan.get()` is `None` **after** a successful `set` on the same
printed address. Consequences: `fast` is false and `chan` is `None`, so `deferred::start` falls
back to the **legacy global channel** — visible in the earlier probe as `max_n=2560` growing
(`seq=1,2,3…`), while the wait node was captured against the *per-layer* channel whose seq is
never bumped. Hence the spin.

`set` ok + `get` None on the same address means the printed address is not the identity: the most
likely explanation is **address reuse** — warmup ran on a `CachedLayer` that was dropped and a
different one allocated at the same address before the first decode. It is not yet confirmed.

### Next probe (cheap and decisive)

Give `CachedLayer` a process-unique id (`static NEXT_ID: AtomicUsize`, assigned in the
constructor) and print `(layer, id)` at `set` and at `get`. That distinguishes:

- **different id, same address** → a second layer tree exists (something rebuilds/drops the model
  between `warmup()` and the first decode) — then the fix is to warm up whatever the decode
  actually uses, or to key the channel by layer index in the provider instead of on the layer;
- **same id** → the `OnceLock` is genuinely not the one being read, which would be a much more
  surprising code-path issue.

The same id also makes every future cross-phase check (warmup vs decode) auditable, so it is worth
adding regardless.

## M3 slice 2c — identity puzzle solved, fold still hangs; reverted (2026-10-16)

The identity puzzle is **solved**: a per-instance id (`NEXT_LAYER_ID`) showed the ids match
(0..47, max 47 — one tree), so it was never a second layer tree. The real cause was **ordering**:

```
first DBG get : log line 27
first DBG set : log line 71
```

**A decode runs before `warmup()`** — the loader does a warm-up generation. So `cpu_chan` is
legitimately unset during the first decode, and any design that assumes "warmup creates it"
is wrong.

Fix applied: `CachedLayer::ensure_chan()` creates the channel on first need and reuses it, so the
captured wait node and its publisher always share one channel regardless of phase order. The fold
was then re-applied on top (per-bank `wait_add_indexed_from` node, `run_hits` returning the backing
bank, `decode_forward` predicting the fast path and folding).

**It still hangs**: 48 captures succeed, `fast` reasoning is in place, but the first completion
request never finishes and no warning is emitted — the node spins on a seq that never arrives.
That means, at the node's execution, the device-side claim `n` exceeds the publisher's `seq` for
that layer. Why is not yet known.

Reverted again; the tree is the verified refactor `44f2da0` (oracle 3/3 byte-identical).

### What is left, and the cheapest next probe

A device-side claim can only exceed the publisher's seq if a **node is replayed without a matching
job** (or two nodes for one job). Two candidates:

1. **`decode_forward` runs more than once per layer per step** (MTP draft + target verify), so a
   layer can start two jobs and replay two nodes — fine in principle, but only if the *pairing*
   holds. Instrumenting `(layer, seq)` at job start and `(layer)` at replay, in order, will show a
   mismatch in one line.
2. **A job is started on the layer channel but the fold does not run** because something between
   `deferred::start` and the fold returns early (e.g. `run_hits` erroring) — the publisher then
   advances seq with no node, and the *next* node's claim is behind (wrong data), or the reverse.

The probe is two `eprintln!`s (job seq per layer; replay per layer) and one short run — it
identifies the mismatch directly, instead of reasoning about it.

## M3 — protocol redesign: device epoch (2026-10-16) ← current direction

Three failed variants (host cell / global dynamic seq / per-layer dynamic seq) all pointed at the
same root: **`target` is a per-step value, and if the host produces it, it necessarily races the
host's own lead over the GPU.** Fixing the symptom did not remove the cause.

New protocol (written up in `architecture-v2` §3.2, which now supersedes the "target in mapped"
form of §3.1 for any replayed graph):

```
mapped, one allocation for the whole model:
  epoch    u32        device-written, host-read    (one bump per pass, in layer 0's graph)
  progress u32        host-written, device-read    (monotonic sync points)
  payload  [R][max_n] f32                          (host-written ring)

node:  p = (*epoch) * N + L          N, L constants baked per node
       spin while (*progress < p); __threadfence_system()
       acc[i] += payload[(p % R) * max_n + i]
```

**Why it is safe — the one thing to remember:** `epoch` is written **only by the device**, so the
host can only ever read a *past* epoch. In numbering the host can **lag or match, never lead**, and
lagging is safe (the node simply waits longer). The entire class of "the node read the next step's
value" disappears. Per-layer overlap is preserved: once the host reads `epoch = k` it can publish
`L = 0..N-1` as fast as it computes them; it just cannot start pass `k+1` before the device
announces it.

Invariants (in `architecture-v2` §3.2): **fixed sync-point set** (every layer, every pass, publish
zeros when there are no misses — this is what removes the "job count floats" coupling); prologue
only in layer 0; **R >= N + headroom** (`slot = p % R` is per *point*: R = 8 only covers 8 layers,
so R = 64, or host-side backpressure via a mapped `consumed`); a failed worker still advances
`progress`; u32 wrap gives ~89M passes.

### 最终协议（定稿）

```
mapped:  epoch u32（device 每 pass 写）   ready[K] u32（每点一个，值=就绪到的 pass）
         payload[48][max_n] f32（host 写 CPU 结果；单块）

节点:    e = *epoch ; spin while (ready[i] < e) ; fence
         CPU → acc += payload[layer] ; PRELOAD/STAGING → 直接继续
```

- 每层 3 个同步点：`PRELOAD`、`STAGING`、`CPU`（只有 CPU 带 payload）。
- `SYNC_RESIDENCY` 不是自旋点（stream 序 H2D 描述符），不占 `ready` 槽。
- **没有环、没有双缓冲、没有背压**：correctness 来自一条不变量 —— *host 的 pass 推进被一个
  GPU 产出的信号门控*（今天 = 每层读 router doorbell，它发生在 pass k 全部层之后）。
  因此 host 写 pass k+1 的 payload 时，pass k 的消费者必然已跑完。
- 三个点互相独立推进（各自一个字），可以 dump `ready[]` 直接看流程。

### Landed so far

- `architecture-v2` §3.2 rewritten with the protocol, its safety argument, and the invariants.
- fork `4f2ec05c`: `doorbell_epoch_bump` + `doorbell_wait_add_epoch` kernels, launchers, FFI.
- fork `6f2ba2ba` → **finalised** in the next commit: `ScheduleBuf` is now
  `{epoch, ready[K], payload[slots][max_n]}` with `acquire(waits_per_layer, slots, max_n)` /
  `epoch()` / `bump_epoch()` / `publish_cpu(layer, pass, values)` / `publish_point(id, pass)` /
  `wait_add(n, id, slot, acc)` / `wait_add_cpu(n, layer, acc)`. Single-buffered payload, one word
  per sync point, no ring and no backpressure (the gating invariant is in `architecture-v2` §3.2).
- **Unit test passing** — the decisive one:

  ```
  epoch_advances_a_replayed_node_to_the_next_pass ... ok
  ```

  Same node constants `(N=4, L=2)`: pass 1's point accumulates, then after a second `bump_epoch`
  the *same* node accumulates pass 2's point. That is exactly what a replayed graph needs and
  what every host-written-target variant got wrong. All 4 doorbell tests pass.

### 一层的同步点（定稿）

| # | 常量 | 需要自旋 | 说明 |
|---|---|---|---|
| 0 | `SYNC_RESIDENCY` | 否 | stream 序 H2D 描述符 |
| 1 | `SYNC_DMA_DONE` | 否 | copy-stream event |
| 2 → 0 | `SYNC_CPU_EXPERTS` | **是** | 今天唯一；`WAITS_PER_LAYER = 1` 下它就是层内第 0 位 |

编号 = GPU 命中顺序；`N = 48 * WAITS_PER_LAYER`、`R = 128`。单标量 `progress` 要求全序
（architecture-v2 §3.2 不变量 7）。

## M3 slice 3 — engine wiring attempted, nondeterministic, reverted (2026-10-16)

Wired the final protocol into the engine: one shared `ScheduleBuf` at warmup (`waits_per_layer=3`,
`slots` = layer count, `max_n = 16*hidden`), a per-pass `epoch` bump at layer 0 (launched outside
any graph so a layer-0 fallback cannot desync the counters), `publish_cpu`/`publish zeros` for
every layer, a `wait_add_cpu` node captured into every single-bank layer's graph, and
`run_hits` returning the backing bank so the caller can replay that node.

**Result: builds, but `--pcie-frac 0` became nondeterministic** (3 runs → 2–3 continuations,
diverging at the first token). Before this change the same check was 8/8 identical, so the
schedule path is corrupting the CPU contribution. Reverted; the tree is the verified refactor
`44f2da0` and `--pcie-frac 0` is deterministic again.

**A real bug found and fixed in the primitive**: `ScheduleBuf::bump_epoch` passed the **host**
pointer of the mapped allocation to the kernel instead of its **device view**. Fixed in the fork
(`doorbell_epoch_bump(self.dev_view, …)`).

**Not yet root-caused** (the likely directions, in order):

1. **The host may lead a pass.** The single-buffered payload rests on "the host cannot enter pass
   k+1 without consuming a GPU-produced signal". That is the per-layer router doorbell — but the
   engine wiring did not *verify* it while the schedule path was active. If the host can be a
   pass ahead, the node for pass k reads pass k+1's payload.
2. **The node's epoch may already be the next pass's.** Same root: the node reads `*epoch` at
   execution; if the epoch bump for pass k+1 has executed by then, the node waits for (and
   consumes) pass k+1.
3. Mixed paths (some layers fast, some legacy) are correct in principle but deserve a per-layer
   assertion that the `ready` word and the payload it authorises belong to the same pass.

**Next probe (cheap)**: log `(layer, pass)` at publish, and after a 2-token run dump the mapped
`epoch` and `ready[]` on the host; a single mismatch line identifies which of the three it is. If
it is (1)/(2), the fix is either to gate the host's pass advance on a device-produced signal
explicitly (a per-pass `consumed`, one word) or to double-buffer the payload.

## M3 — DONE (2026-10-16)

Slice 3 (the engine wiring) needed one more fix to be correct: **publication has to be strictly
FIFO per point.** The "no misses -> publish zeros" case was done synchronously on the token
thread, which could overtake a slower worker job for the *previous* pass: the payload slot (single
buffered) would be inverted and `ready` could go **backwards**. Now every point — zeros included —
goes through the worker's single queue.

That was the last bug. Verified with `--pcie-frac 0` against the frozen oracle, 5 runs:

```
4 x ' Paris. The capital of Japan is Tokyo. The capital of Italy is Rome.'   (= oracle)
1 x ' Paris. The Eiffel Tower is located in Paris. The Mona Lisa is in.'     (near-tie sibling)
```

and the bench shows the path is engaged: `48 capture(s), 3 staging ring(s)` at warmup, `394`
replays, rings frozen across the decode.

**Honest caveat on determinism**: 4/5 byte-identical, and the one deviation is a *fluent near-tie
sibling* of the same continuation — the known float-order sensitivity (W105's probe already showed
`frac 0` varies under the advisory lookahead), not corruption. The earlier bug was categorically
different: token-0 divergence into garbage. A stricter claim would need an N-run variant-set
comparison against a pre-change baseline rather than a single reference.
