# M3 — CPU result return path into the graph (misses enter the graph)

**Status: IN PROGRESS** (started 2026-10-16). Progress scratch for `roadmap.md` M3.

## Goal (from the roadmap)

Replace `deferred`'s `cudaLaunchHostFunc` with the zero-argument `wait_copy_ptr`, so a miss's
CPU result is pulled in by a **graph node** spinning on a mapped seq instead of a host function
blocking candle's stream. Judged by: ① with misses present, greedy == eager; ② misses handled
**inside** the graph (a counter proves no eager path is taken); ③ zero sync points on the token
thread (STEP_DBG dry bucket drops); ④ failure injection — a worker error still bumps seq, so the
GPU never spins forever.

## Step 0 (this work): F3 — port the M0-validated primitives into the fork

M0 (`worklogs/m0.md`) proved the zero-argument pattern in a standalone harness; the fork still
only has the versions that take `target` / `slot_off` as **kernel arguments**, which a captured
graph freezes at capture time.

**F3 is additive**: the new cells go *after* the payload ring in `FlagBuf`'s mapped allocation,
so every existing offset (`seq` at 0, payload at 8) is untouched and the proven R2b path cannot
regress.

```
layout: [seq u32 @0][pad][payload ring @8, RING_DEPTH * max_n f32]
        [target u32][pad][slot_off i64]        <- F3 control cells, appended
```

New kernels `doorbell_wait_seq_ge_ptr_kernel` / `doorbell_wait_copy_f32_ptr_kernel` read
`*d_target` / `*d_slot_off` from mapped memory instead of receiving them. Rust:
`FlagBuf::set_target`, `set_slot_off`, `wait_seq_ge_ptr`, `wait_copy_slot_ptr`.

## F3 result — done (fork `c132611e`)

`doorbell_wait_seq_ge_ptr` / `doorbell_wait_copy_f32_ptr` added to `doorbell.cu`, FFI, and
`FlagBuf` (`set_target`, `set_slot_off`, `wait_seq_ge_ptr`, `wait_copy_slot_ptr`). The control
cells are **appended** after the payload ring, so the existing R2b offsets are untouched.

```
cargo test -p mistralrs-core --features cuda --lib doorbell
  -> test cuda::doorbell::ptr_wait_tests::wait_copy_slot_ptr_reads_target_and_slot_from_mapped_memory ... ok
```

The test drives the *same* channel twice through unchanged kernel parameters (only the mapped
cells move) and checks a payload-less seq bump still unblocks the wait — i.e. the two properties
a captured graph depends on.

## What M3 actually has left (recon 2026-10-16)

`deferred` **no longer uses `cudaLaunchHostFunc`** — W106's R2b already replaced it with the
argument-taking `wait_copy_slot`, so the host function is gone. M3's remaining work is therefore
*not* "remove the host function" but **fold the CPU-return wait into the graph**:

- today the token thread issues, per layer, a raw `wait_copy_slot` **and** a candle add, plus a
  per-step `Tensor::empty` allocation;
- M3 makes it a captured node so it costs one launch and no allocation.

### The crate boundary forces the shape

The wait kernel lives in `mistralrs-core` (`doorbell.rs`), the MoE segment in `mistralrs-quant`,
and **`mistralrs-quant` cannot depend on `mistralrs-core`** — so the segment cannot contain the
wait node. Instead the **engine** captures a second, tiny **wait+add graph** per bank using
`FlagBuf`'s zero-argument launch, and replays it right after the MoE graph.

Per layer: `MoE graph` → `wait+add graph` (the acc is the MoE graph's `out`, fixed). That is 2
graph launches instead of `wait_copy_slot` + candle add + per-step allocation, and it removes
the last token-thread wait from the CPU path.

## M3 slice 1 — wait-then-accumulate primitive (done, fork `d46e71c3`)

`doorbell_wait_add_f32_ptr` + `FlagBuf::wait_add_slot_ptr(len, acc)`: spin on the mapped target,
then `acc[i] += payload[slot_off + i]`. The down+aggregate kernel already accumulated the GPU
hits into that buffer, so one node completes the MoE result.

```
cargo test -p mistralrs-core --features cuda --lib doorbell
  -> wait_add_slot_ptr_accumulates_into_the_output_buffer ... ok   (1.0 + 10..17 == 11..18)
  -> wait_copy_slot_ptr_reads_target_and_slot_from_mapped_memory ... ok
```
