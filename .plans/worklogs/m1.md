# M1 — static address layout + descriptor-driven kernel (no graph)

**Status: DONE (2026-10-16).** Engine wiring landed in M2's step A. Progress scratch for `roadmap.md` M1.

## Goal (from the roadmap)

1. `load → 7-ring warmup`: create the 7 quant shapes' staging rings and all per-layer
   banks once, before any capture.
2. All `FlagBuf` / descriptor / staging buffers allocated at load; addresses fixed for
   the process lifetime.
3. `fused_moe_decode` becomes descriptor-driven ("read count → grid-stride over a
   descriptor array", F4).
4. **Judged under eager**: old host-computed launch geometry vs descriptor-driven is
   token-identical, with the hit set changing every step. No graph, no PCIe.

## Recon (2026-10-16)

**The F4 target is not `fused_moe_decode` (that is the *CPU* path).** The GPU path used
by qflash's `run_hits` is:

```
qflash expert_cache.rs:1145  fused_decode()          (marshals ids/weights, calls ↓)
  └─ mistralrs_quant::indexed_moe_fused_decode        gguf/cuda.rs:1586
       ├─ quantize_input_q8_1_into  → MOE_DECODE_Q8_WORKSPACE        (cuda.rs:1051)
       ├─ launch_moe_gemv_fused_gate_up_*   grid = (⌈n/8⌉,  topk, batch)
       ├─ quantize_q8_1            → MOE_DECODE_Q8_WORKSPACE
       └─ launch_moe_gemv_down_aggregate_*  grid = (⌈n/16⌉, topk, batch)
                                      out = dev.alloc_zeros(batch*hidden)   ← per call
```

Kernel sources: `mistralrs-quant/kernels/indexed_moe/indexed_moe.cu`
(`moe_gemv_fused_gate_up_impl` :1797, `moe_gemv_down_aggregate_impl` :1875,
launchers :2096 / :2183). FFI: `gguf/ffi.rs:701`, `:…`.

### Why capture is impossible today — three concrete violations

| # | Site | Problem |
|---|---|---|
| **V1** | `u8_workspace_ensure` / `f32_workspace_ensure` (`cuda.rs:104`,`:137`) | `len` is `f(batch, topk, dims)`. When it grows, the old `CudaSlice` is **retired and replaced** → the address changes. |
| **V2** | `let final_out = dev.alloc_zeros::<f32>(batch * hidden_size)?` (`cuda.rs:~1700`) | a fresh device allocation **every call**. |
| **V3** | `gate_up_outsize = batch * topk * intermediate_size` (`cuda.rs:1633`) | the f32 workspace size depends on the step's hit count → V1 again. |

Plus, from qflash: `Tensor::new(ids, device)` / `Tensor::new(weights, device)` per call
(`expert_cache.rs:1152`) — an allocation + H2D **per step**; this is the "descriptor" that
must become a persistent device buffer.

### The launch geometry is already value-driven → a fixed grid is reachable

The launchers compute the grid from the **kernel value arguments**:

```c
dim3 grid(1 + (n - 1)/ROWS_PER_BLOCK, topk, batch);   // fused gate+up
dim3 grid((n + ROWS_PER_BLOCK - 1)/ROWS_PER_BLOCK, topk, batch);  // down+aggregate
```

and the kernel indexes `task_id = current_batch * topk + current_topk`,
`expert_id = indices[task_id]`. So **passing `batch = max_batch, topk = max_topk`
makes the grid constant without any kernel change**; unused slots are simply computed
and discarded. This is plan option A realised with a sentinel/pad pattern.

### The one kernel gap that matters

- `moe_gemv_fused_gate_up_impl` has **no `expert_id` bounds check** (the *forward*
  variant `moe_gemv_gate_up_pair_impl` does, writing zeros). A sentinel
  `expert_id >= num_experts` would therefore read out-of-bounds weights.
- `moe_gemv_down_aggregate_impl` also has no guard, and it does not receive
  `num_experts` at all.

→ For M1 the pad is done the way qflash already does it: **pad with a valid slot index
and weight 0.0** (no OOB read, contributes 0 to the aggregate). Adding a real sentinel
guard (+ `num_experts` in the launcher/FFI signatures) is a later, optional refinement
that lets unused slots write zeros without keeping a "donor" slot alive.

## M1.1 — additive, capture-friendly decode (this session)

Design: a **new, additive** `MoeDecodeCapture` type that owns every buffer for one
(layer, max_batch, max_topk) and runs the four kernels with a fixed grid. The existing
`indexed_moe_fused_decode` is left untouched, so qflash's behaviour cannot regress.

```rust
pub struct MoeDecodeCapture {
    max_batch: usize, max_topk: usize,
    hidden: usize, intermediate: usize,
    k_padded: usize, k_down_padded: usize,
    q8:     CudaSlice<u8>,     // pre-sized for max_batch and max_batch*max_topk rows
    f32_ws: CudaSlice<f32>,    // max_batch*max_topk*intermediate
    out:    CudaSlice<f32>,    // max_batch*hidden   (fixed output, no alloc_zeros)
}
impl MoeDecodeCapture {
    pub fn new(gate_qt, up_qt, down_qt, max_batch, max_topk, dev) -> Result<Self>;
    pub fn run(&self, xs_flat, indices: &CudaSlice<u32>, weights: &CudaSlice<f32>, act) -> Result<()>;
    pub fn output(&self) -> Result<Tensor>;   // aliases `out`; valid until the next run
}
```

None of `new`'s allocations happen on the decode path → addresses are fixed, satisfying
M1 criterion ① by construction once the engine calls `new` at load.

Presence of a *deferred*, optional sentinel guard is recorded above.

## Verification (M1 criterion ②)

Extend the existing GPU unit test style
(`gguf/iq4xs/tests.rs:1113 cuda_indexed_moe_fused_decode_matches_the_cpu_kernel`):

- Build a random `MoeDecodeCapture` with `max_batch > BATCH`, `max_topk > TOPK`.
- Run the capture path with the real `BATCH × TOPK` prefix filled and every extra slot
  padded with a valid `expert_id` and weight `0.0`.
- Assert the first `BATCH` rows equal `indexed_moe_fused_decode(...)` with `BATCH, TOPK`.
- (Follow-up) a second arm with a *different* `max_batch/max_topk` must give the same
  result → proves the padded capacity is behaviour-invariant.

Runs with `cargo test -p mistralrs-quant --lib --features cuda`.

### Notes / gotchas found

- `QTensor` does **not** implement `Clone`, so `MoeDecodeCapture` does not own the
  weights; `run` takes `&QTensor` for gate/up/down (they are the layer's, and outlive
  the capture).
- One full-suite run showed `packed_affine::unsupported_k_tile_uses_canonical_dispatch`
  failing; it passes in isolation, passes with the change reverted, and passed on the
  next 3 full runs with the change. Pre-existing parallel-warmup flake, unrelated.

### What M1.1 does and does not close

- ② (descriptor-driven, eager-identical): **done** — and it required no kernel change,
  because the launchers already derive the grid from value arguments.
- ① (allocation-free, address-stable decode): **not yet** — `MoeDecodeCapture` fixes it
  for this call, but the engine does not yet use it, and the *global* workspaces
  (`MOE_DECODE_Q8_WORKSPACE` / `MOE_DECODE_F32_WORKSPACE`) can still grow. The 7-ring
  warmup and wiring the engine to `MoeDecodeCapture` are next.
- ③ (no graph/PCIe): held — nothing in M1.1 touches capture.

**Remaining M1 work — engine wiring plan** (scoped; the risky unknown is settled: `max_batch`)

- **Sizing.** `max_topk = num_experts_per_tok`; `max_batch = 16` — not a new guess: the engine
  already sizes the lookahead channel this way (`LookaheadChannel::new`: "`max_rows` must cover
  the LARGEST decode batch this layer will see", `max_rows.max(16)`, with the W106 overflow
  post-mortem). `rows > 16` keeps the old path — the allowed **row-bucket** fallback, unrelated
  to misses.
- **Where the capture lives.** `run_hits` groups hits by `Bank` and calls the free function
  `fused_decode(bank, …)` per bank; a `Bank` already carries its own `gate/up/down` QTensor
  slices, so a **per-bank** `MoeDecodeCapture` is the natural attachment (a per-layer one would
  need a bank→capture map for no benefit).
- **Persistent descriptors.** Next to each capture, a fixed `CudaSlice<u32>` (ids) and
  `CudaSlice<f32>` (weights) of `max_batch * max_topk`; each step the host writes the
  already-built `ids`/`ws` vectors into them with a stream-ordered `memcpy_htod`, replacing
  `Tensor::new(...)` (today: an allocation + H2D per call). Device buffer, not mapped: capture
  forbids H2D *inside* capture, but a memcpy on the stream **before** the graph launch is fine
  and inherently ordered — mapped is reserved for M3's CPU-result return path.
- **Creation.** In the existing post-load warmup (`warmup_rings`), so addresses are fixed before
  the first decode — same window as the staging rings.
- **Verification.** (i) byte-identical to the frozen `--pcie-frac 0` oracle
  (`harness/m1/reference.oracle.txt`); (ii) a counter asserting no capture/descriptor was
  created after warmup; (iii) the kernel-level bitwise test stays green.

Estimated ~150 lines across `expert_cache.rs` (+ a `memcpy_htod` on `CudaDevice`).

## Finding: the PCIe path is nondeterministic; `--pcie-frac 0` is bit-reproducible (2026-10-16)

We tried to freeze a token-level oracle from the baseline binary
(`harness/m1/capture_oracle.sh`: `serve`, fixed prompt, `temperature 0`, `--seed 0`). Greedy
turned out **not** to be bit-reproducible in every configuration, so we isolated it:

| config | runs | distinct outputs |
|---|---|---|
| `--pcie-frac 0.55`, default (spin pool) | 5 | **2** — 3× "The capital of Japan…" / 2× "The Eiffel Tower…" |
| `--pcie-frac 0.55`, single-thread rayon | 3 | 1 |
| `--pcie-frac 0` , default (spin pool) | 4 | 1 |
| `--pcie-frac 0` , single-thread rayon | 4 | 1 |

Every variant agrees on ` Paris.` and diverges on the next token — a near-tie whose argmax
flips. `temperature 0` removes *sampling* randomness but not float reduction order.

**Conclusions**

- **`--pcie-frac 0` is bit-reproducible: 8/8 across two dispatcher configs.** So an
  engine-level **byte diff** oracle *is* available for M1 and M2 (both are `frac 0` by scope).
  `harness/m1/reference.oracle.txt` is the canonical capture, taken at `frac 0`.
- **The nondeterminism belongs to the PCIe path** (`--pcie-frac > 0`) — and to its interaction
  with the spin pool (single-thread rayon at `frac 0.55` was stable in 3 runs, so the CPU
  parallel reduce is not sufficient on its own). Exact mechanism unknown: candidates are float
  order from the extra `atomicAdd` terms the DMA'd experts contribute to the down+aggregate
  kernel, or a staging-ring slot read racing a reuse. **Does not block M1/M2** (whose scope is
  `frac 0`), but must be characterized before M3/M4, which build directly on that path.
- Candidate future improvement (not required): make the engine deterministic — it would help
  every bench, not just the oracle.
