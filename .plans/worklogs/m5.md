# M5 — lookahead on its own thread, experts back on rayon

**Status: WIP on branch `m5-wip`, NOT merged** (2026-10-17). The configuration change is in place and
measured; two things block it: the hit rate is below the bar because a prediction job still *blocks*
on DMA, and one rare divergence is unexplained.

## Configuration (architecture §6.3, fixed — not a switch)

The W-era layout was reversed to the one §6.3 fixes:

| | before | after |
|---|---|---|
| expert batches | engine spin pool (`expert_pool.rs`, `install_moe_task_dispatcher`) | **rayon**, the fork's default |
| predictions | 4 threads, park/unpark per job, polling `expert_batch_idle` inside the job | **1 thread**, woken by events |

`expert_pool.rs` is deleted (−700 lines) together with three A/B knobs it carried
(`NAIWA_SPIN_POOL`, `NAIWA_POOL_WORKERS`, `NAIWA_HOST_WORKS`) — §6.4 forbids them and §6.3 already
fixed the answer. What is left of the pool's two useful ideas:

- **the gap**: predictions must not run beside an expert batch (W106: 10 ms/step slower). The batch
  runner now reports it itself — `deferred::BatchBusy` bumps a depth around every job and, on the
  last one, calls `lookahead::wake()`. Polling for the gap from inside a prediction is gone.
- **the queue**: bounded (64), drop on overflow, stale entries dropped by the job body.

## The thread

```
submit(job) ──push──► wake()  ─┐
BatchBusy::drop (last) ─wake() ─┴─► lookahead thread: drain while expert_batch_idle(), then park
```

No spinning for work: both real events (a prediction was submitted / a batch ended) unpark it, and
the 2 ms park timeout is only a lost-wakeup safety net. Nothing is lost when a job arrives during a
batch: the batch's completion wake brings the thread back, and the queue is the state.

## What it measures

`bench --pcie-frac 0.55 --prompt-len 512 --gen-len 8 --depth 4`, lookahead on:

| | W-era (pool + 4 threads) | M5 (rayon + 1 thread) |
|---|---|---|
| decode | 9.9 T/s, TPOT 101.4 ms | **12.3–12.8 T/s, TPOT 77.9–81.6 ms** |
| expert cache hit rate | 82.4% | **72.6–73.1%** ❌ (bar: 78%) |
| STEP_DBG dry | 2.03–2.13 ms/layer | 1.53–1.63 ms/layer |
| lookahead loads | 470 empty + 1017 over residents | 470 + 1024 (same absolute work) |
| dropped | 0 | 0 |

So the experts-on-rayon half is a clear win (−21% TPOT) and it *shortens each layer's window*, which
is why the hit rate falls. By criterion ① that is still a fail (below the W105 78% inflection).

### Why one thread is not enough *yet* — and it confirms the user's point

Split of a job (temporary instrument, 384 jobs, avg):

```
wait_publish 0.42 ms   +   prefetch 1.79 ms   =  ~2.2 ms per job
```

81% of the job is `prefetch_predicted` → `admit`/`replace` → `upload_in_place`, i.e.
`wait_for_readers` spins plus `CopyStream::upload` which **`stream.synchronize()`s**. So the
"lookahead" thread is *performing* the DMA, not issuing it. 48 jobs × 2.2 ms = 105 ms against a
78 ms pass: one thread structurally cannot keep up, which is exactly why the hit rate fell.

Team size, measured before settling on one thread (same build otherwise):

| threads | hit rate | TPOT |
|---|---|---|
| 2 | 76.5% | 79.9 ms |
| 4 | 78.4–80.3% | 77–81 ms |
| 6 | 78.0–79.0% | 79–82 ms |

More than 4 changes nothing (the waits overlap, the CPU does not). And with the gap gate removed
entirely: 79.1–80.2% at 6 threads — so the polling gate was never the bottleneck; the blocking DMA
is.

**Conclusion → M5b**: make the preload non-blocking (`CopyStream::queue_async`) and publish
`sync_id(layer, SYNC_PRELOAD)` on the copy stream, with a one-node per-layer gate replayed before
the layer's segment — the same shape as M4's `SYNC_STAGING` gate, and the piece M4 deferred. Then a
job is `wait_publish + matmul + issue` ≈ 0.6 ms, 48 jobs fit in ~29 ms of a 78 ms pass, and one
thread is sufficient. The drop policy must also gain a guarantee: a PRELOAD point is not advisory —
a dropped job that publishes nothing would leave the layer's gate spinning forever.

## M5c candidate: compute the prediction on the GPU

The whole predict chain exists only because the matmul is on the CPU:
`publish x to mapped` -> `host spins for it (0.42 ms/layer)` -> `CPU gemv 1 x hidden x E` -> preload.
That matmul is ~260k MACs: tens to hundreds of µs on one core, sub-µs on a GPU that is idle 98% of
the time.

```
layer L's stream work, BEFORE its MoE segment (the prediction only needs L's MoE *input*)
    gemv: logits = x_L @ router_{L+1}^T -> mapped logits (E f32 per row); threadfence_system; bump seq
lookahead thread
    spin the seq (doorbell pattern) -> read E floats -> host top-k (~1 us)
    -> issue the preload copies in the gap after the CPU-expert batch (unchanged)
```

Deletes: the activation publish kernel, the mapped activation channel (`LookaheadChannel`/`FlagBuf`
payload), the 0.42 ms/layer `wait_publish` spin, and the CPU matmul. Adds: router weights on the
device (~1 MB, uploaded at load — today `router` is a CPU `QTensor`), one tiny gemv per layer, a
mapped logits buffer, and a 128-value top-k on the host (keeping top-k on the host keeps the kernel
a plain gemv).

No "one layer ahead" needed: the prediction depends on L's *input*, so it can be a node before L's
own segment, and the ids land in mapped memory while the host is still doing L's top-k / expert
dispatch. The gap discipline for the preload copies is unchanged.

Order of work: M5b first (make the preload asynchronous and the hit rate >= 78%), then M5c as its own
commit with its own measurement (`wait_publish`/matmul probes at zero, hit rate not below 82%).

## Settled decisions (2026-10-17)

- **Layer 0 stays uncovered.** It has no predecessor to predict it, in `qflash-rs` and here alike
  (`registry.get(self.layer + 1)` only). Carrying its ids over from the previous pass was considered
  and dropped: it is 1/48 of the layers (~0.8 points of hit rate) and would add a `target_pass`
  second case. Prefill's `spawn_fill` plus the reactive paths (CPU experts, PCIe staging) cover it.
- **Predict and preload run after the CPU-expert batch of the layer finishes** — in the gap, not
  beside it. That is already the implemented discipline: the lookahead thread drains only while
  `deferred::expert_batch_idle()`, and the batch's completion wakes it (`BatchBusy::drop` → `wake`).
  W106 measured running beside the batch at 10 ms/step slower, and with rayon the batch wants every
  core.

## Layout: is there an attention window to hide the preload in?

The proposal was to put predict + preload *before* the CPU-expert / PCIe-frac section, overlapping the
layer's attention. The measurement says there is nothing to overlap:

```
TPOT 78 ms / 48 layers = 1.63 ms of host time per layer
STEP_DBG dry           = 1.53-1.63 ms per layer   -> the GPU is idle ~98% of the time
```

Decode is host-bound, so when the host enters `decode_forward` the GPU has already finished that
layer's attention and MoE and is *waiting*. Work issued at the top of the layer is therefore not
hidden: a DMA issued there is waited for, in full, by that layer's gate (measured: TPOT 78 → 103 ms).

What a preload can hide in is **the host's own work for the next layer** — which only exists if the
prediction is issued a layer early, on the prediction thread, the moment its ids are known. So the
layout that hides the DMA is:

```
layer L, top        publish L's activation -> prediction job for L+1        (already there)
prediction thread   wait_publish (0.42 ms) -> router matmul -> issue L+1's copies
                    -> publish SYNC_PRELOAD(L+1, pass) on the copy stream
                    [this overlaps the host's remaining work for L, ~1.6 ms]
layer L+1, segment  gate: spin until that point (normally already published)
```

The one exception is *layer 0*, which has no predecessor; there the ids can be carried over from the
previous pass (`pending` stamped with `target_pass = pass + 1`), which also has to be issued early.

## Rejected attempt: issuing the preload copies on the token thread

M5b try 1 moved the *copies* to the token thread (the prediction thread would only publish ids,
`queue_prediction`), so that the `SYNC_PRELOAD` publisher and the pass counter live on one thread and
a dropped prediction could never strand a gate. Implemented and measured:

```
hit rate 56.6-58.7%   TPOT 102.9-105.4 ms   loaded 0 into empty slots, ~745 over residents
```

Rejected, and the reason is structural: the copies then happen *at* the layer that needs them, so
the layer's gate waits for a DMA that was issued microseconds earlier — the preload latency moved
onto the critical path (TPOT 78 → 103 ms), and early empty-slot loads disappear (the drain at the
top of the layer sees an empty prediction). A preload must be issued roughly a layer *ahead*, which
means the prediction thread has to issue it.

So M5b's remaining problem is exactly one question: **who publishes `SYNC_PRELOAD` for a layer that
had no preload this pass?** Options:
1. the prediction thread publishes after its copies, and the gate is replayed *only* when the layer
   has preloads in flight (needs a per-layer in-flight flag, and `NAIWA_NO_LOOKAHEAD` then naturally
   replays nothing);
2. the prediction thread publishes, and the token thread publishes the same point when the
   prediction was dropped/late — two producers on one word, which the FIFO/level rules forbid;
3. a *second* point (`SYNC_PRELOAD_DONE`) written by the token thread on the copy stream right
   before the gate replay, so the gate waits for `min` of the two — more state, no clear win.

Option 1 is the one to build.

## Unresolved: one divergence in 12 runs

`--pcie-frac 0.55` + `NO_LOOKAHEAD`, run 2 of the first M5 batch produced
`' Paris. The Eiffel Tower is located in Paris.'` instead of the frozen reference. Not reproducible
in the 11 runs since (4 + 3 + 4, both `frac 0.55` and `frac 0`). The M4 build was clean in 16 runs,
but 1/12 vs 0/16 is not significant, so it is not yet attributable. Candidates, in order:

1. **Staging-slot reuse vs a host that runs ahead.** The ring is 16 slots per dtype for ~48 layers,
   so a slot is reused within a pass; the only protection is `fence.record_reads` (recorded after
   the segment is enqueued) plus `wait_for_readers`. If any path stages a slot without recording the
   fence, the repro is a *wrong-expert* read — which would look like a plausible but different
   continuation, exactly what was seen.
2. **The M4 point is a level, not an edge.** `ready[id] = pass` and a node accepts `ready >= epoch`,
   so a copy stream that is a pass ahead satisfies an older gate. Sound only because the fence
   orders the *overwrite*; worth proving under a faster step.
3. **Pre-existing, timing-only.** The step is 20% shorter, so a latent margin shrank.

Before M6 this needs a decisive test: run `frac 0.55` + `NO_LOOKAHEAD` n×50 and, if it reproduces,
dump `ready[]` and the staged expert ids per layer.
