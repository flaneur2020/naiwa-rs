# M6 — performance

> The graph-capture work is in [`m6-graph.md`](m6-graph.md) (renamed from `m6.md`). This file is the
> performance milestone: what the number is, where it goes, and the order in which to attack it.

## The number

| configuration | TPOT | tok/s | hit rate |
|---|---|---|---|
| `frac 0` + `NO_LOOKAHEAD` (deterministic, used by the oracle) | 80-85 ms | 11.6-12.4 | **19.7%** |
| production: `frac 0.55`, prediction thread on | 78-87 ms | 12.4-12.8 | **81-84%** |
| Strata, same model family, 4070 Ti SUPER 16 GB, `--spec 4 --mtp` | ~33 ms | **76.0** | - |
| Strata, IQ2_XS | ~26 ms | 97.9 | - |

Always report **TPOT *and* hit rate**, plus which of `NO_LOOKAHEAD` / the probe is on: the two
configurations differ by 4x in hit rate and they are not comparable. `NO_LOOKAHEAD` exists for byte-exact
gates, not for speed comparisons.

## Where one pass goes (measured, not estimated)

Sources: `NAIWA_STEP_DBG` (per-layer GPU idle vs GPU busy), `NAIWA_FUSED_DBG` (CPU MoE), and an `nsys`
kernel-duration sum over a full run (`frac 0.55`, prompt 512, 8 decode passes).

| stage | per pass | share | how it was measured |
|---|---|---|---|
| **GPU spinning at the sync points** | **47.4 ms** | 55% of GPU kernel time | `doorbell_wait_ready_kernel` 329 ms + `wait_copy_f32` 50 ms over 384/432 launches = 379 ms of 686 ms GPU time |
| GPU compute (MoE segments, attention, PLE) | 38.3 ms | 45% of GPU kernel time | remainder of the same 686 ms |
| **CPU expert compute** | **~19 ms** | ~20% of the pass | 264 us per (row, expert) pair x ~1.5 pairs/layer (84% hit) x 48 |
| host bookkeeping + launches + top-k readback | the rest, ~35 ms | - | `STEP_DBG dry` 1.55 ms/layer x 48 = 74 ms minus the CPU leg it contains |

The single most important line is `STEP_DBG busy_ms/layer = 0.000`: **the host and the GPU never overlap.**
Every layer the GPU finishes first and then *spins* until the host publishes, so the pass is
`host time + GPU compute`, not `max(host, gpu)`. That is why moving work off the host (P2) is worth more than
making kernels faster, and why the spin time is a *symptom*: it is exactly how late the host is.

### The handoff hypothesis was wrong - measured and refuted

`NAIWA_RET_DBG` (in `deferred`) splits a miss job into "waiting for the worker" and "the CPU gemv + publish":

```
RET_DBG queue_us 12.6-28.4   compute_us 399.5-467.9   total_us 413.7-480.5
```

So the submit -> worker wake -> compute -> publish chain is **~440 us end to end, with only 13-28 us of queueing**.
There is no hidden 0.5 ms of handoff overhead; the CPU leg is 440 us of real work and nothing else.

Cross-checking the GPU spin by configuration (nsys, kernel durations):

| config | total GPU kernel time | spin | what spins |
|---|---|---|---|
| `frac 0` (cold cache, 19.7% hit) | 412 ms | 126 ms (31%) | `doorbell_wait_copy_f32` **1354 us/launch**, 93 launches; **zero** `wait_ready` (no gates exist without a copy stream) |
| `frac 0.55` (84% hit) | 686 ms | 379 ms (55%) | `wait_ready` **858 us/launch** (384) + `wait_copy_f32` 115 us (432) |

So the spin is two different things at the two ends of the hit-rate range:

- **cold cache**: the legacy CPU-return path (`wait_copy_f32`) at **1.35 ms per call** - more misses per layer than one
  worker returns in the time the GPU takes for the hits, so the CPU leg is on the critical path;
- **warm cache**: the gates at **0.86 ms**, which at 84% hit are dominated by **staging DMA** (2 MB per staged
  expert) and the preload copies, not by the CPU return - the CPU job is only 440 us and starts 20 us after
  submission.

### Can the staging DMA move a layer earlier? No - but it can move *inside* the layer

The user's instinct is right: a staged miss is produced by **this layer's own routing** (the top-k that
decides the miss set does not exist before the layer runs), so there is nothing to copy a layer in advance.
What the lookahead already prefetches one layer ahead is the *prediction*; the misses are by definition the
part the prediction got wrong, and they are only known when the real top-k lands.

What *is* available is a different overlap: **the hit experts do not need the staged data.** Today the
staging gate sits at the head of the segment, so the GPU waits ~0.86 ms *before doing any work*, even though
the hit experts (84% of the selection, ~0.8 ms of GPU work per layer) could run during the DMA. Moving the
wait to just before the *miss* nodes would hide most of the DMA behind the hit compute:

```
today:   [gate: wait staging 0.86 ms][hits + misses 0.80 ms]          -> 1.66 ms/layer
proposed:[hits 0.6-0.8 ms][gate: wait staging ~0.1 ms][misses 0.1-0.2 ms] -> ~0.95 ms/layer
```

For `MoeDecodeCapture` this is a structural change: the segment currently launches the indexed MoE over the
whole selection with the staged experts already in the ring, so splitting it means capturing the hit-only
part and the miss part separately (two graphs per layer, or one graph with the wait node in the middle - the
latter needs the per-layer sync id as a *node parameter*, which is the `cuGraphExecKernelNodeSetParams`
trick already noted for the gates).

Worth ~38 ms/pass if the hits really are 0.8 ms of the segment's 0.8 ms - measure the hit/miss split of the
segment first (`NAIWA_STEP_DBG`'s busy time per layer is the ceiling on what can be hidden).

That changes the lever for the shipping configuration: it is **DMA latency of the staged misses** (issue them
earlier / fewer bytes per copy), not the CPU handoff. For a cold cache the lever is the CPU leg (more misses
than the worker can retire).

**The GPU spin is the CPU leg's *latency*, not the host's bookkeeping.** The graph is
`segment (hits, GPU) -> wait_add (spins until the CPU publishes)` , so the hit experts are already overlapping
the miss experts - that is the whole point of the M3 CPU-return node. What the numbers say is that the overlap
*is not long enough*:

| measure | value |
|---|---|
| per-gate spin (`wait_ready`, 329 ms / 384 launches) | **0.86 ms** |
| per-`wait_copy_f32` spin (50 ms / 432) | 0.12 ms |
| CPU expert compute per layer at 84% hit (~1.5 pairs x 264 us) | **0.39 ms** |
| GPU hit work per layer (38.3 ms / 48) | 0.80 ms |

The GPU finishes the hits in ~0.8 ms and then waits another 0.86 ms for the CPU, while the CPU's own gemv is
only 0.39 ms. So **~0.5 ms per layer is handoff latency, not compute**: submit -> wake the `cpu-experts`
thread -> `wait_publish` -> upload -> publish the point. Three consequences:

1. a faster CPU gemv is worth at most ~19 ms a pass, and only if the handoff shrinks with it;
2. the levers that matter are the ones that cut *latency*: publish the point as soon as the last expert is
   done rather than at the end of the batch, avoid one wakeup (submit directly to the worker that will run
   it), and start the CPU job before the GPU segment is queued (the host already knows the miss set);
3. splitting work further (e.g. GPU taking more experts) would only help if it makes the two sides *finish
   together*, which is a latency question again.

Corollary for the CPU leg: at 84% hit it is ~19 ms a pass, which is **not** the biggest item - the top-k
readback spin and the per-layer bookkeeping around it are. Cutting CPU expert time alone (a faster gemv)
would move ~19 ms; cutting host lateness moves the whole 47 ms of spin.

Sweep of the CPU locality knob (`NAIWA_RUN_ROWS`, 16 decode tokens): 8 -> 81.9 ms, 32 -> 80.4 ms,
**64 -> 78.8 ms** (84.3% hit), so 64 is the better default on this box; THP already covers the stacks
(`thp_fault_alloc` grows by ~25.6 GB during a run = the working set, so pages are 2 MB, and
`AnonHugePages` is only 0 at the end because the process has exited).

## Hit rate: v2 matches the old engine; the low number was `NO_LOOKAHEAD`

Same command, same model, same cache (`frac 0.55`, prompt 512, gen 32, prediction thread on):

| engine | TPOT | tok/s | hit rate | prediction loads |
|---|---|---|---|---|
| qflash-rs (eager, the frozen oracle) | 80.8 ms | 12.4 | **85.1%** (10931/12847) | 470 empty + 3171 swaps |
| naiwa-rs v2 | **77.9 ms** | **12.8** | **84.4%** (10832/12838) | 470 empty + 3154 swaps |

So 19.7% was never a regression - it is what `NO_LOOKAHEAD` gives (prediction off, only the miss-driven
admissions and the background fill populate the cache). Production hit rate is identical to the old engine
within 0.7 points, and v2 is 3.6% faster per pass.

The prediction design itself is the **same code lineage in both**:

1. layer L's activation is published into L's mapped slot by a stream-ordered kernel; a worker thread reads
   it and matmuls it against **layer L+1's own router** (on the CPU, no device round trip);
2. the predicted set is the **union of every row's top-k** by votes (`union_by_votes`), i.e. the experts
   most rows want first;
3. admission: into empty slots freely; over an LRU resident at most `MAX_LOOKAHEAD_SWAPS x rows` times
   (a wrong prediction costs a slot, not correctness);
4. independently, `spawn_fill` fills remaining empty slots with `fill_candidate` = the unreserved expert
   with the highest hit count - the cache keeps filling when predictions stop.

Where the ceiling is: the expert working set is 25.9 GB against 2 GB of cache, i.e. ~8% of it fits, and
the measured 84-85% comes from the top-k being highly skewed per layer. The knobs left are
`MAX_LOOKAHEAD_SWAPS` (more churn per step), predicting two layers ahead (more lead time for the DMA), and
seeding `hit_counts` from the router's rank instead of only from actual hits so the background fill does not
chase its own tail.

## What is already ruled out - do not re-litigate

| idea | verdict | evidence |
|---|---|---|
| bigger expert cache | **negative** | 2 GB 80.8 ms vs 4 GB 84.7 ms; working set is 25.9 GB against 12 GB, so slots barely change the miss count while every admission copies 2.1 MB. KV cache is not the constraint (118 MB at 4 k) |
| GPU kernel work | pointless | GPU idle ~98% of the pass |
| whole-step CUDA graph | impossible | the host is irreducibly in the loop per layer: staging is host-issued and decided from that layer's top-k (`m6-graph.md`) |
| attention-region capture | small | 1-4 ms of an 82 ms pass |
| batching the CPU expert gemv | **already done** | `CpuExperts::forward -> fused_moe_decode(..all ids..)` is one call, not per expert |

## Plan, in order

### P0 - deterministic memory (DONE)

Both NaN sources were uninitialised buffers: the schedule payload (`cudaHostAlloc`, `4044e8a`) and the
paged KV blocks (`Tensor::empty`, `0e8c8462`). Failure rate 2-3/5 -> 1/5 -> **0/6**. Without this every
timing was untrustworthy and the oracle could not be byte-exact for the right reason.

### P1 - split the 1.6 ms/layer (next action, cheap)

`NAIWA_FUSED_DBG=1` already prints the CPU MoE cost (`us/call`, `us/pair`, `us/expert`, `gap_us/call`).
Run one decode with it at `frac 0` and at `frac 0.55` and write down:

- host bookkeeping per layer (read the top-k back, compute the miss set, issue the DMA, write the payload),
- CPU gemv per layer (`us/call`),
- the gap between calls (`gap_us/call`), which is the host's own share.

Those three numbers decide P2 and P4. Do not start either without them.

### P2 - take the miss decision off the host

Today the token thread, per layer: spins for the top-k, hashes the ids into a resident map, builds the copy
list, writes the payload. Move that to a small device kernel that emits a **compact miss list + count** in
mapped memory; the host then only reads the list (no set math, no per-id branching) and queues the copies
(the copies must stay host-issued - that is not negotiable).

Gates: `frac 0` byte-exact; launch count per step unchanged; host time per layer down (P1's numbers are the
baseline); hit rate unchanged.

### P3 - MTP end to end (the only x2.5)

State: the head is local (`~/bench-rel/mtp/mtp-component.gguf`) and loads via `--mmproj`; the schedule-size
bug is fixed (`fd2e6f1`); steady-state drafting works at prompt 8 (2-row pass, 106 ms); it still faults at
prompt 512 **inside `drafter_prefill_chunk`**, before any drafter forward runs.

Cost side, measured: a 2-row pass is **+29%** (82 -> 106 ms), so depth 1 needs >65% acceptance to break
even. That is *because* the pass is host-bound; P2 and P3 multiply each other.

Gates: `--mtp` output == no-MTP output byte-exact (speculation must not change greedy text); then TPOT and
**accepted drafts per pass** (the engine reports them) at `frac 0` and `frac 0.55`.

### P4 - rayon saturation of the CPU leg

`RAYON_NUM_THREADS` on one decode: if 8 vs 16 changes nothing, the CPU leg is not the constraint and only P2
is left; if it does, size it.

### P5 - the graph work

Only after the above, and only for what is left in `m6-graph.md` (attention-region capture, ~1-4 ms).

## Measurement protocol (non-negotiable)

1. **Medians of >= 3 runs**, not single runs: the machine varies by ~5%.
2. Report **TPOT + tok/s + hit rate + the exact flags**.
3. Any correctness claim: `frac 0` + `NO_LOOKAHEAD` **byte-exact against `harness/m1/reference.oracle.txt`**.
4. Any memory/liveness claim: run it **>= 6 times** and count failures (that is how the NaN was found: 0/6
   after the fix against 2-3/5 before).
5. A probe that changes behaviour must be named in the result line.
