# M6 — performance

> The graph-capture work is in [`m6-graph.md`](m6-graph.md) (renamed from `m6.md`). This file is the
> performance milestone: what the number is, where it goes, and the order in which to attack it.

## Historical record: where the "27 tok/s" came from

`~/code/qflash-rs/.plans/spin-pool-doorbell.md` (2026-10-14) records a 256-token head-to-head:

> ours **27.5 tok/s**, strata 41.0 tok/s, gap 1.49x ... current round ~105-111 ms

and `worklog.md` W90 records how it was reached: "np=2 19.6 -> **25.2 tok/s**" after the fused CPU decode,
with two further ingredients in that plan: `RAYON_NUM_THREADS` raised from candle's 6 (physical cores) to
10-12, and long generations (256 tokens) so the measurement is steady state.

Re-run today on this box with the same binary and this 60 GB model:

| qflash-rs, gen 64, cache 2 | tok/s | TPOT | hit |
|---|---|---|---|
| `frac 0`, MTP np2, rayon 10 | **11.9** | 84.1 ms | 65.9% |
| `frac 0.55`, MTP np2 | 9.9 | 101.0 ms | 86.8% |
| `frac 0.55`, no MTP | 13.1 | 76.5 ms | 83.7% |

So the recorded 25-27 is **not reproducible with this model on this card**: it needs a hit rate the 2 GB
cache cannot give here (65.9% at `frac 0`), and its MTP gain came from a config where the CPU leg, not the
PCIe staging, was the constraint. What *is* reproducible is that MTP only pays when the extra rows stay
resident - which is exactly the v2 result below (MTP 2 at `frac 0.05` / cache 4 = **20.9-23.4 tok/s** against
15.9 without). v2 is therefore already at or above qflash-rs's recorded best, and qflash-rs is slower than v2
at every configuration measured today.

## What the benchmark measures, and the per-round numbers

`recv_measurement` (`commands/bench.rs`) takes `ttft = first_token - request_start` and
`decode_duration = last_token - first_token`, with `decode_intervals = expected_tokens - 1`. TPOT is
`decode_duration / decode_intervals` and the reported T/s is `intervals / decode_duration`, so **prefill is
excluded** (it is the separate `TTFT` row). With speculation one pass yields more than one token, so TPOT
stops describing a pass - `NAIWA_STEP_DBG` now also prints `ROUND_DBG` (wall time between layer-0 marks,
i.e. per pass):

| configuration | round p50 | min/max | TPOT | tok/s | tokens/round |
|---|---|---|---|---|---|
| no MTP, `frac 0.55`, cache 2 | **63.2 ms** | 59.4 / 143 | 63.3 ms | 15.8 | 1.0 |
| MTP 2, `frac 0.55`, cache 2 | **108-111 ms** | 81 / 184 | 65.6 ms | 15.2 | ~1.65 |
| MTP 2, `frac 0.05`, cache 4 | **94-96 ms** | 80 / 144 | 47.9 ms | **20.9** | ~2.0 |

So a speculative round costs ~1.5x a plain pass but returns ~2 tokens: the win is real only once the cache is
large enough that the extra rows do not all fall to the CPU (`frac 0.05` + cache 4 is the best found:
20.9 tok/s against 15.8 without speculation). At `frac 0.55` / cache 2 speculation is a **net loss**.

## The bench's default prompt was depressing MTP acceptance

`bench` builds its prompt from synthetic token ids (`1000 + i % 2048`) unless `--prompt-file` is given, so the
model's continuation is arbitrary and the drafter's guesses rarely match. With a predictable prompt (a small
Python `fib` program plus "write the next functions in the same style"), same config (MTP, `frac 0.05`,
cache 4, split on):

| prompt | round p50 | TPOT | tok/s | tokens/round | MTP head |
|---|---|---|---|---|---|
| synthetic ids, np2 | 92.7 ms | 55.3 ms | 18.1 | 1.68 | **2.81 ms** (1.6 rows) |
| **predictable, np2** | 100.9 ms | 39.7 ms | **25.2** | **2.54** | 3.23 ms (1.8 rows) |
| **predictable, np3** | 110.3 ms | 37.9 ms | **26.4** | **2.92** | 1.86 ms (1.6 rows) |

So acceptance was the missing factor, not the engine: 1.68 -> 2.54 tokens per round is the whole gap, and
np3 on predictable text reaches **26.4 tok/s** - which is the "27 tok/s" that was remembered. Every earlier
comparison in this file used the synthetic prompt and therefore understated MTP by ~40%.

### Where the time goes when np increases

np2 -> np3, same prompt and config, gen 96 (two runs; the earlier gen-128 pair is in the table above and is
slightly more favourable, so treat these as the same measurement within noise):

| | round p50 | tok/s | tokens/round | selections | misses/round | segment replays |
|---|---|---|---|---|---|---|
| np2 | 97.3 ms | 24.9 | 2.42 | 3 rows | **281** | 1970 |
| np3 | 118.9 ms | 22.9 | 2.72 | 4 rows | **382** | 1765 |

The round grows 22% while tokens/round grows only 12%, so at np3 the extra depth is a **net loss here** (it
was a small win in the gen-128 pair - the difference is acceptance, which is why np3 has to be chosen per
workload rather than fixed).

Attribution of the +21.6 ms:

1. **The CPU leg, ~70% of it.** One more verify row is one more full selection, so misses per round go
   281 -> 382 (+36%) at ~79% hit. They arrive as ~2 extra experts per layer inside an already-running fused
   CPU job, and the job is on the critical path through the CPU-return wait: ~200 us x 48 layers ~ 10 ms.
2. **The GPU segments, most of the rest.** The segments grow with rows (sub-linearly, which is why depth
   still pays at all): +~6-8 ms.
3. **Not the graph machinery**: no new bucket, no extra capture - the capture counter actually fell (fewer
   rounds), so the segment is being replayed at the same bucket.
4. **Not the head**: it stays at ~2-3 ms per round.

So each extra draft row is paid for mainly by **more experts on the CPU**, which is the same currency as the
hit rate - the lever that made 4 GB and `frac 0.05` the best config. Deeper drafting therefore wants either a
bigger cache (fewer misses per row) or fewer rows per verify.

The MTP head itself costs **1.9-3.2 ms per round** (it is a full extra block whose 512 experts are
host-resident by design), i.e. 2-3% of a round - worth knowing, not the bottleneck.

### Correction: the waits are a long tail, not the typical case (report medians, not means)

The same nsys run, sorted by duration instead of summed:

| kernel | n | **p50** | p90 | max | mean |
|---|---|---|---|---|---|
| `wait_copy_f32` (CPU payload) | 301 | **69 us** | 680 us | **104 ms** | 767 us |
| `wait_ready` (staging gate) | 760 | **11 us** | 39 us | 2.3 ms | 80 us |

So the pipeline the design asks for **is already the steady state**: the staging gate is 11 us (the DMA is
covered by the residents) and the CPU payload is 69 us (the CPU leg finished under the residents and staged
compute). The earlier "858 us" and "767 us" figures were **means pulled up by a few outliers** - one CPU wait
of 104 ms, almost certainly the first decode step after prefill when the worker is still retiring a prefill
job. The lesson is the same one the NaN hunt taught: on this workload, report p50/p90, not the mean.

Remaining work implied by the distribution, in order: the p90 tail (680 us / 39 us) and the single 104 ms
outlier, i.e. **prefill-to-decode handover**, not steady-state overlap.

### Can the launches themselves overlap? Yes - the serialisation is the routing round trip

Launch issue **already** overlaps the GPU: while the GPU runs layer L's kernels, the host issues layer L+1's.
That is why 0.2 ms of issue cost does not simply add to the round. What genuinely does not overlap is the
**round trip inside every layer**:

```
GPU: router gemv -> top-k kernel        (data the rest of the layer depends on)
  |  host must observe it
host: spin on the ring -> split -> issue DMA -> launch residents/staged/gates
  |
GPU: the rest of the layer
```

The host cannot issue layer L's remaining work before it sees L's routing result, and the GPU cannot run that
work before the host issues it. 48 of those per pass is the structure that makes `STEP_DBG`
`busy_ms/layer = 0.000`: by the time the host gets back to the GPU, the GPU has nothing left to do.

So "overlap the launches" is not the question; the question is **how much of that round trip is host work and
how much is the GPU's own router+top-k latency**. The `NAIWA_DISPATCH_USE` flip removed the host's hashing and
the top-k readback and the round did not move (77.4 vs 78.0 ms), which says the host share is small and the
round trip is mostly the GPU's router+top-k plus the serialisation it forces - i.e. it is *inherent* to a
per-layer router unless the routing is predicted. Which is what the lookahead already does for *loading*
(85% hit) but not for *execution*.

Ways to actually shorten it, in principle:

| idea | why it is hard |
|---|---|
| start the residents before the router finishes | the resident set depends on the router |
| run two layers' routers ahead | layer L+1's router needs L's MoE output |
| device-side everything (no round trip) | the copies must be host-issued (no device-initiated H2D), so the host stays in the loop by construction |
| make the round trip shorter | it is already ~20 us of host time; the rest is the router's own latency |

The one thing a second thread *can* overlap is the copy issue (independent of the chain), worth tens of
microseconds.

### Is the host's CUDA path serial? Can it be asynchronous?

Two different things get conflated here, and only one of them is a problem:

1. **Device side: already asynchronous.** Every launch returns immediately and the work is queued on a
   stream; the GPU consumes it while the host keeps running. Nothing to fix.
2. **Host side: the *issue cost* is serial on the calling thread.** Each `cuLaunchKernel` burns 3-7 us of
   *that thread* (measured here: `cuLaunchKernel` ~5-6 us, `cudaLaunchKernel_ptsz` 6-15 us), so 30-40
   launches per layer = 0.2-0.24 ms of pure submission time. A second *thread* can enqueue concurrently (the
   driver serialises per context internally), but only for work that is genuinely independent of the layer
   chain - which in this engine is just the staging copies, i.e. tens of microseconds.

So the only way to cut the host issue cost is **fewer calls per layer**:

| approach | effect | measured cost |
|---|---|---|
| CUDA graph capture of a region | N launches -> 1 | `cuGraphLaunch` 12-15 us, so it pays once it replaces >=3 launches |
| merging small ops in the fork | fewer launches | depends on the op chain |
| a second issuing thread | only for independent work (the copies) | tens of us - not worth it |

That is exactly why the earlier build-break-even rule was "capture when a segment has many launches": a
one-node graph is a *loss* (12-15 us versus 5-6 us), a 30-node attention region is the big win.

### The three-way overlap the design wants, and where it stands

The intent is that per layer three producers run at once: **GPU on the cached experts**, **DMA for the
staged share of the misses**, **CPU for the rest of the misses**. The order in the code already matches that:

```
host: split -> queue DMA (copy stream) -> submit the CPU job -> launch residents
GPU :  [residents] -> wait(SYNC_STAGING) -> [staged] -> wait(CPU payload) -> add
```

and the measurements say:

| pair | state |
|---|---|
| DMA vs residents | **overlapping**: staging wait 858 -> 80 us |
| CPU job vs everything | starts 13-14 us after submit and finishes in 390-530 us (`NAIWA_RET_DBG`) |
| CPU payload vs the GPU | **still 767 us of waiting** - and that number is suspicious |

The last row does not fit: the job is submitted *before* the residents launch, publishes within ~540 us, and
the GPU does not reach the CPU wait until ~550 us later. A wait of 767 us is about **one layer of the
pass**, which looks like the payload kernel waiting for the *next* job's seq rather than this one's - i.e. a
slot/`publish_seq` pairing problem in the legacy channel (`deferred::start(...).upload()`), not a CPU speed
problem. First thing to check next: print the `(slot, publish_seq)` the upload waits on against the ones the
job was created with, per layer.

Physical caveat worth keeping in mind: the three producers are **bandwidth-coupled** - the DMA reads the same
host DRAM the CPU gemv reads - so perfect overlap cannot make all three free; the CPU leg measured 390-530 us
where the same gemv alone is ~440 us, i.e. the interference is real but small.

The staging wait collapsed **10x** - the residents really do cover the DMA now. What it exposed is the
**CPU return**, which became the dominant wait (231 ms): the CPU add node sits after the staged experts, so
it now pays for everything the residents and the DMA did. That is the next thing to move (issue the CPU job
earlier / give it its own overlap), and it is worth ~0.77 ms per layer.

## Where a verify round goes, and what to attack (analysis)

Steady state, last 8 rounds: **63.1 ms** per round with one row, **85.4 ms** per round with a 3-row verify
(MTP 2 at `frac 0.05` / cache 4, ~2 accepted). Per layer: 1.31 ms single-row, 1.78 ms verify.

Budget per layer (single row, from the probes already taken):

| item | per layer | source |
|---|---|---|
| GPU kernel time (segments + attention + PLE) | **0.81 ms** | 310 ms of decode kernels / 384 layer-steps |
| waits at the gates | 0.08 ms | `wait_ready` p50 11 us + `wait_copy_f32` p50 69 us |
| **host, serialised against the GPU** | **~0.42 ms** | 1.31 - 0.81 - 0.08, and `STEP_DBG busy = 0.000` |

Overlap scorecard - three of the four pairs are already good, one is not:

| pair | state | number |
|---|---|---|
| DMA vs residents | good | staging gate p50 **11 us** |
| CPU misses vs residents+staged | good in steady state | payload p50 **69 us**; tail p90 680 us |
| staged compute vs residents | serial by construction (same stream) | fine: staged is a small share at `frac 0.05` |
| **host vs everything** | **none at all** | `busy_ms/layer = 0.000` - the GPU always finishes first |

So the biggest single direction is **the host serialisation: ~0.42 ms/layer, i.e. ~20 ms of a 63 ms round**,
and it grows with the verify row count (three rows of selections to place, more copies to issue, more ids to
walk). A verify round only amortises it because it carries two tokens.

Ranked directions:

0. **Correction to the item below**: a dedicated copy thread does **not** recover the ~20 ms. The token thread
   never blocks on the copies (the graph's gate does), so a second thread that issues them removes only the
   issue + publish itself - tens of microseconds per layer. The ~0.42 ms/layer of host time is not the copy
   path and, per the `NAIWA_DISPATCH_USE` experiment, not the top-k readback or the id hashing either (that
   flip was neutral). What is left is **the tens of kernel launches per layer** outside the captured
   segment (attention, PLE, router, gates): at ~6 us per launch, 30-40 launches is 0.2-0.24 ms/layer, which
   is the shape of the number. The lever is therefore *fewer host calls*, i.e. capturing the attention
   region, not a worker thread.

1. **Take the host out of the layer loop** (was the biggest, now demoted by the correction above): the device already produces
   `(row, id, weight)` lists (`dispatch_topk`, tested, byte-exact behind `NAIWA_DISPATCH_USE`); what is left on
   the host is *issuing* the copies and launching the graphs. Route the copy issue to a **dedicated thread**
   that mirrors the M5 lookahead thread (it wakes on the dispatch seq, issues the copies for the layer,
   publishes `SYNC_STAGING`), so the token thread only does `cuGraphLaunch`. Prize: most of the 20 ms, and it
   scales with rows (which is exactly where the verify round loses).
2. **GPU compute, 0.81 ms/layer**: this is the MoE segments themselves. Nothing cheap left - it would be
   quantisation or kernel work, so it is the *floor* of the round, not the lever.
3. **Acceptance rate**: at `npredict 2` we accept ~2 of 3 rows. Round time grows sub-linearly with rows
   (63 -> 85 ms for 3x the rows), so more acceptance is nearly free throughput; `npredict 3` measured worse
   (83.5 ms, 12.0 tok/s at the old config) but that was before the cache/split tuning, so it is worth one
   re-check at `frac 0.05` / cache 4.
4. **The p90 tail** (680 us CPU waits, one 104 ms handover): real but rare; it hurts TTFT and jitter, not
   steady T/s.

## Where one pass goes (measured, not estimated)

Sources: `NAIWA_STEP_DBG` (per-layer GPU idle vs GPU busy), `NAIWA_FUSED_DBG` (CPU MoE), and an `nsys`
kernel-duration sum over a full run (`frac 0.55`, prompt 512, 8 decode passes).

| stage | per pass | share | how it was measured |
|---|---|---|---|
| **GPU spinning at the sync points** | **47.4 ms** | 55% of GPU kernel time | `doorbell_wait_ready_kernel` 329 ms + `wait_copy_f32` 50 ms over 384/432 launches = 379 ms of 686 ms GPU time |
| GPU compute (MoE segments, attention, PLE) | 38.3 ms | 45% of GPU kernel time | remainder of the same 686 ms |
| **CPU expert compute** | **~19 ms** | ~20% of the pass | 264 us per (row, expert) pair x ~1.5 pairs/layer (84% hit) x 48 |
| host bookkeeping + launches + top-k readback | the rest, ~35 ms | - | `STEP_DBG dry` 1.55 ms/layer x 48 = 74 ms minus the CPU leg it contains |

The single most important line is `STEP_DBG busy_ms/layer = 0.000`: **the host and the GPU never overlap.**
Every layer the GPU finishes first and then *spins* until the host publishes, so the pass is
`host time + GPU compute`, not `max(host, gpu)`. That is why moving work off the host (P2) is worth more than
making kernels faster, and why the spin time is a *symptom*: it is exactly how late the host is.

### The handoff hypothesis was wrong - measured and refuted

`NAIWA_RET_DBG` (in `deferred`) splits a miss job into "waiting for the worker" and "the CPU gemv + publish":

```
RET_DBG queue_us 12.6-28.4   compute_us 399.5-467.9   total_us 413.7-480.5
```

So the submit -> worker wake -> compute -> publish chain is **~440 us end to end, with only 13-28 us of queueing**.
There is no hidden 0.5 ms of handoff overhead; the CPU leg is 440 us of real work and nothing else.

Cross-checking the GPU spin by configuration (nsys, kernel durations):

| config | total GPU kernel time | spin | what spins |
|---|---|---|---|
| `frac 0` (cold cache, 19.7% hit) | 412 ms | 126 ms (31%) | `doorbell_wait_copy_f32` **1354 us/launch**, 93 launches; **zero** `wait_ready` (no gates exist without a copy stream) |
| `frac 0.55` (84% hit) | 686 ms | 379 ms (55%) | `wait_ready` **858 us/launch** (384) + `wait_copy_f32` 115 us (432) |

So the spin is two different things at the two ends of the hit-rate range:

- **cold cache**: the legacy CPU-return path (`wait_copy_f32`) at **1.35 ms per call** - more misses per layer than one
  worker returns in the time the GPU takes for the hits, so the CPU leg is on the critical path;
- **warm cache**: the gates at **0.86 ms**, which at 84% hit are dominated by **staging DMA** (2 MB per staged
  expert) and the preload copies, not by the CPU return - the CPU job is only 440 us and starts 20 us after
  submission.

### This ordering is inherited, not a v2 regression

The user's question - "wasn't the previous architecture written exactly like this?" - is right, and the
code says so. qflash-rs's `decode_forward` does the same three things in the same order:

```rust
if self.pcie_frac > 0.0 { self.stream_pcie(&mut misses, &mut hits)?; }   // staged -> hits
let acc = self.run_hits(&hits, &x2d, act);                                // one fused launch
```
and qflash's `stage_misses` ends with `scratch.done.wait_on(&self.slot_device)` - a
`cudaStreamWaitEvent` per streamed expert, **before** `run_hits`. So in the eager engine the hits also waited
for the DMA; M4 only replaced those per-expert events with one captured gate node (same ordering, fewer host
calls). The overlap idea below is therefore **new work**, not a property we lost:

- neither engine runs the residents before the DMA;
- both publish a seq the host spins on (the ring), and both return CPU results through a graph node.

Corollary: "GPU idle 98%, 55% of kernel time spinning at the gates" is inherited from the eager design, which
is why it was never visible before this milestone measured it.

### Why the hits wait for the DMA: the staged experts are merged into the hits list

The hit experts do **not** read the staging ring - but they are gated on it, because `stream_pcie` does this:

```rust
let staged = self.stage_misses(cs, misses, hits);   // queue the copies ...
// publish SYNC_STAGING on the copy stream
// (and `stage_misses` *injects* the staged experts into `hits` as extra Hit entries)
...
if self.staging_enabled() { self.replay_gate(SYNC_STAGING)?; }   // gate at the segment head
let acc = self.run_hits(&hits, &x2d, act);                        // hits + staged, one fused launch
```

So the DMA gate is where it is because `run_hits` is called **once for both groups**: the staged experts were
folded into `hits`, and the single fused launch cannot start until the ring is filled. That is the whole cause.

### What option 2 actually is (and a correction)

Reading `Bank::create_capture` (`expert_cache.rs:1269`) shows the CPU-return node is **not** inside the
segment graph: `cap.capture(...)` captures the experts, and a *second* one-node graph is captured right
after it -

```rust
let launched = sched.wait_add_cpu(&gate_device, mb * hidden, layer, acc);   // inside its own window
```

- and replayed separately (`waitadd_replay()`). So the mechanism for "a wait node, captured, with a layer
  constant baked in" **already exists in the code**. That is exactly what option 2 reuses:

> Capture the segment as `[resident experts][wait_ready(layer, SYNC_STAGING)][staged experts]` in one
> window, and delete the separate staging-gate replay. The wait then sits where the ring is first read, the
> residents hide the DMA, and the per-layer gate launch disappears.

The per-layer id can be **baked at capture time**, because captures are already per layer
(`warmup: 48 capture(s)`, one per layer, `create_capture(..., self.layer as u32, sched)`), not shared per
shape. No `cuGraphExecKernelNodeSetParams` is needed - my earlier note on that was wrong for this path.

The real work is inside `MoeDecodeCapture`: it currently takes one expert list and produces one fused
launch, so it has to accept **two groups with the wait between them** (residents and staged), which is a
fork-side descriptor change, plus the engine dropping `replay_gate(SYNC_STAGING)`.

**The naive split's NaN is therefore *not* explained by a double-added CPU node** - that node is a separate
graph and was still replayed once. The cause is still open; the first thing to check is `fast`
(`capture_will_serve`) flipping, because with staged entries removed from `hits` the "single bank served
everything" test sees a different expert list and may choose the schedule path where the ring path was
correct.

**A naive split NaNs, and my first explanation of it was wrong.** I implemented the split (staged experts in
their own list, `run_hits(residents)` before the gate, gate, `run_hits(staged)`) and `frac 0` stayed
byte-identical, but `frac 0.55` produced `NaN logits` immediately. The cause is structural: since M3 the
**CPU-return node is captured *inside* the segment graph** (`bank.waitadd_replay()` replays a graph that
spins for the CPU payload and adds it to the accumulator). Replaying that graph a second time for the staged
group spins on the same point twice and **adds the CPU contribution twice** - wrong values, and with the
payload gate consumed twice it also races. So the split is not a reordering; it needs either

1. **a second captured graph per bank** (residents only, no waitadd node), replayed before the gate, with the
   existing graph kept for the staged group; or
2. **the wait node moved inside the captured graph**, between the resident experts and the staged ones, so
   the engine replays *one* graph per layer and the spin sits where the ring is first read - which needs the
   per-layer `SYNC_STAGING` id as a graph node parameter, because a bank's graph is shared by every layer of
   its shape (the `cuGraphExecKernelNodeSetParams` trick).

Option 2 is the better design (one launch, the gate where it belongs) and option 1 is the smaller diff. Both
are fork-side graph work, so this is the next milestone's first task.

The fix, in the code's own terms (`run_hits` already takes several banks and an `add` accumulator, so a second
call composes by addition):

1. `stream_pcie` should **return** the staged entries instead of pushing them into `hits` (it already
   computes them; the push is one line);
2. `decode_forward` calls `run_hits(&hits)` **before** the gate - the residents only, no ring data;
3. then `replay_gate(SYNC_STAGING)`, then `run_hits(&staged)` and add - the launch that actually needs the ring.

Two details that decide the shape:

- the `fast`/`waitadd` path keys off `capture_bank` being the *single* bank that served the call; with two
  calls there are two candidates, so the CPU-return point has to be attributed to the call that owns it
  (the staged call is the one whose result the CPU adds to);
- the fence loop (`buf.fence.record_reads`) must cover the staged slots after the *second* call, not before.

That is a ~60-line change in one function plus a signature change on `stream_pcie`, and it buys up to the
hit half of the segment (<= 0.8 ms/layer, ~38 ms/pass) without touching any kernel or graph.

### Can the staging DMA move a layer earlier? No - but it can move *inside* the layer

The user's instinct is right: a staged miss is produced by **this layer's own routing** (the top-k that
decides the miss set does not exist before the layer runs), so there is nothing to copy a layer in advance.
What the lookahead already prefetches one layer ahead is the *prediction*; the misses are by definition the
part the prediction got wrong, and they are only known when the real top-k lands.

What *is* available is a different overlap: **the hit experts do not need the staged data.** Today the
staging gate sits at the head of the segment, so the GPU waits ~0.86 ms *before doing any work*, even though
the hit experts (84% of the selection, ~0.8 ms of GPU work per layer) could run during the DMA. Moving the
wait to just before the *miss* nodes would hide most of the DMA behind the hit compute:

```
today:   [gate: wait staging 0.86 ms][hits + misses 0.80 ms]          -> 1.66 ms/layer
proposed:[hits 0.6-0.8 ms][gate: wait staging ~0.1 ms][misses 0.1-0.2 ms] -> ~0.95 ms/layer
```

For `MoeDecodeCapture` this is a structural change: the segment currently launches the indexed MoE over the
whole selection with the staged experts already in the ring, so splitting it means capturing the hit-only
part and the miss part separately (two graphs per layer, or one graph with the wait node in the middle - the
latter needs the per-layer sync id as a *node parameter*, which is the `cuGraphExecKernelNodeSetParams`
trick already noted for the gates).

Worth ~38 ms/pass if the hits really are 0.8 ms of the segment's 0.8 ms - measure the hit/miss split of the
segment first (`NAIWA_STEP_DBG`'s busy time per layer is the ceiling on what can be hidden).

That changes the lever for the shipping configuration: it is **DMA latency of the staged misses** (issue them
earlier / fewer bytes per copy), not the CPU handoff. For a cold cache the lever is the CPU leg (more misses
than the worker can retire).

**The GPU spin is the CPU leg's *latency*, not the host's bookkeeping.** The graph is
`segment (hits, GPU) -> wait_add (spins until the CPU publishes)` , so the hit experts are already overlapping
the miss experts - that is the whole point of the M3 CPU-return node. What the numbers say is that the overlap
*is not long enough*:

| measure | value |
|---|---|
| per-gate spin (`wait_ready`, 329 ms / 384 launches) | **0.86 ms** |
| per-`wait_copy_f32` spin (50 ms / 432) | 0.12 ms |
| CPU expert compute per layer at 84% hit (~1.5 pairs x 264 us) | **0.39 ms** |
| GPU hit work per layer (38.3 ms / 48) | 0.80 ms |

The GPU finishes the hits in ~0.8 ms and then waits another 0.86 ms for the CPU, while the CPU's own gemv is
only 0.39 ms. So **~0.5 ms per layer is handoff latency, not compute**: submit -> wake the `cpu-experts`
thread -> `wait_publish` -> upload -> publish the point. Three consequences:

1. a faster CPU gemv is worth at most ~19 ms a pass, and only if the handoff shrinks with it;
2. the levers that matter are the ones that cut *latency*: publish the point as soon as the last expert is
   done rather than at the end of the batch, avoid one wakeup (submit directly to the worker that will run
   it), and start the CPU job before the GPU segment is queued (the host already knows the miss set);
3. splitting work further (e.g. GPU taking more experts) would only help if it makes the two sides *finish
   together*, which is a latency question again.

Corollary for the CPU leg: at 84% hit it is ~19 ms a pass, which is **not** the biggest item - the top-k
readback spin and the per-layer bookkeeping around it are. Cutting CPU expert time alone (a faster gemv)
would move ~19 ms; cutting host lateness moves the whole 47 ms of spin.

Sweep of the CPU locality knob (`NAIWA_RUN_ROWS`, 16 decode tokens): 8 -> 81.9 ms, 32 -> 80.4 ms,
**64 -> 78.8 ms** (84.3% hit), so 64 is the better default on this box; THP already covers the stacks
(`thp_fault_alloc` grows by ~25.6 GB during a run = the working set, so pages are 2 MB, and
`AnonHugePages` is only 0 at the end because the process has exited).

## Hit rate: v2 matches the old engine; the low number was `NO_LOOKAHEAD`

Same command, same model, same cache (`frac 0.55`, prompt 512, gen 32, prediction thread on):

| engine | TPOT | tok/s | hit rate | prediction loads |
|---|---|---|---|---|
| qflash-rs (eager, the frozen oracle) | 80.8 ms | 12.4 | **85.1%** (10931/12847) | 470 empty + 3171 swaps |
| naiwa-rs v2 | **77.9 ms** | **12.8** | **84.4%** (10832/12838) | 470 empty + 3154 swaps |

So 19.7% was never a regression - it is what `NO_LOOKAHEAD` gives (prediction off, only the miss-driven
admissions and the background fill populate the cache). Production hit rate is identical to the old engine
within 0.7 points, and v2 is 3.6% faster per pass.

The prediction design itself is the **same code lineage in both**:

1. layer L's activation is published into L's mapped slot by a stream-ordered kernel; a worker thread reads
   it and matmuls it against **layer L+1's own router** (on the CPU, no device round trip);
2. the predicted set is the **union of every row's top-k** by votes (`union_by_votes`), i.e. the experts
   most rows want first;
3. admission: into empty slots freely; over an LRU resident at most `MAX_LOOKAHEAD_SWAPS x rows` times
   (a wrong prediction costs a slot, not correctness);
4. independently, `spawn_fill` fills remaining empty slots with `fill_candidate` = the unreserved expert
   with the highest hit count - the cache keeps filling when predictions stop.

Where the ceiling is: the expert working set is 25.9 GB against 2 GB of cache, i.e. ~8% of it fits, and
the measured 84-85% comes from the top-k being highly skewed per layer. The knobs left are
`MAX_LOOKAHEAD_SWAPS` (more churn per step), predicting two layers ahead (more lead time for the DMA), and
seeding `hit_counts` from the router's rank instead of only from actual hits so the background fill does not
chase its own tail.

## P2 spec: dispatch on the device, three producers in parallel

Goal: per layer, **resident experts (GPU), staged experts (DMA) and miss experts (CPU) run at the same time**,
and the host stops doing per-id set math. What can move to the device is the *decision*; the copies and the
CPU gemvs must still be started by the host (no device-initiated H2D), so the device's job is to publish a
compact, ordered list that the host consumes without touching ids.

### State

| item | where | updated |
|---|---|---|
| `resident: [u32; 8]` per layer (256 experts -> bitmap) | device, one contiguous array | host writes it **stream-ordered** right after an admission/eviction commits (low frequency), so any pass that reads it sees a bitmap that matches the slots it will read |
| `hits: [(slot, w)]`, `stream: [e]`, `cpu: [e]` + counts | device **and** mapped host copies | by the dispatch kernel, per layer per pass |
| `slot_table` | existing ring + bank slots | unchanged |

### Kernel

```
dispatch_topk(ids, weights, rows, top_k, bitmap_l, frac_num, frac_den,
              hits_out, hits_n, stream_out, stream_n, cpu_out, cpu_n)
```
- resident bit set -> append `(slot_from_bitmap, w)` to `hits_out` (the slot is a pure function of the bit
  index, so no host table lookup);
- otherwise -> a miss; misses sorted by descending weight (or by first-appearance, deterministic), the first
  `frac_num/frac_den` go to `stream_out`, the rest to `cpu_out`;
- counts go to mapped memory, so the host reads 3 `u32`s and then the ids it needs - no hashing, no per-id
  branching, one small memcpy of the list.

### Order inside the layer's graph (option 2 from above)

```
[resident experts]                                 <- starts immediately, no wait
wait(SYNC_STAGING)                                 <- DMA lands under the resident compute
[staged experts]                                   <- add
wait(SYNC_CPU_EXPERTS)                             <- the CPU part lands under both
add CPU payload                                    <- existing CPU-return node
```

`SYNC_CPU_LIST` is a fourth point per layer (the host may read the lists); it is published by the dispatch
kernel, i.e. the same launch that produces the lists, so the host wakes on it exactly as it does today on the
top-k ring.

### Why the three overlap

| producer | starts when | blocked by |
|---|---|---|
| residents | the graph launches | nothing - their slots are read-only and fenced |
| DMA | the host reads `stream_n` and issues the copies | `SYNC_CPU_LIST` (the list) |
| CPU misses | the host submits the job | `SYNC_CPU_LIST` |
| the point that ends the wait | `SYNC_STAGING` / `SYNC_CPU_EXPERTS` | their producer finishing |

So the layer's cost becomes `max(resident compute, DMA, CPU gemv) + staged compute`, instead of
`DMA + resident + staged + CPU`.

### Sub-steps, each independently verifiable

- **S1 - lists on the device.** `dispatch_topk` + mapped counts; the host stops building `hits`/`misses`. Gate:
  `frac 0` byte-exact, and the doorbell top-k readback disappears (structural: no `wait_and_read` per layer).
- **S2 - graph split (option 2).** Residents before `SYNC_STAGING`, staged after; delete the separate gate
  replay. Gate: `frac 0` byte-exact, `frac 0.55` against the two-variant set, and the `wait_ready` spin per
  launch falls (it was 858 us/layer).
- **S3 - measure the overlap.** `NAIWA_STEP_DBG`'s `busy_ms/layer` should stop being 0.000 - that number is the
  proof the host and GPU finally overlap. Target: TPOT <= 55 ms at 84% hit.

### Invariants that must not break

1. publication per point stays **strictly FIFO** (single-buffered payload, monotonic `ready`);
2. the bitmap must never claim an expert whose slot is not yet published (a stale bit is a *wrong result*, not
   a miss) - so it is written only after the slot's publish, stream-ordered;
3. the fence loop still covers every slot the graph read, on every path (hits, staged, cpu).

## Plan, in order

### P0 - deterministic memory (DONE)

Both NaN sources were uninitialised buffers: the schedule payload (`cudaHostAlloc`, `4044e8a`) and the
paged KV blocks (`Tensor::empty`, `0e8c8462`). Failure rate 2-3/5 -> 1/5 -> **0/6**. Without this every
timing was untrustworthy and the oracle could not be byte-exact for the right reason.

### P1 - split the 1.6 ms/layer (next action, cheap)

`NAIWA_FUSED_DBG=1` already prints the CPU MoE cost (`us/call`, `us/pair`, `us/expert`, `gap_us/call`).
Run one decode with it at `frac 0` and at `frac 0.55` and write down:

- host bookkeeping per layer (read the top-k back, compute the miss set, issue the DMA, write the payload),
- CPU gemv per layer (`us/call`),
- the gap between calls (`gap_us/call`), which is the host's own share.

Those three numbers decide P2 and P4. Do not start either without them.

### P2 - take the miss decision off the host

Today the token thread, per layer: spins for the top-k, hashes the ids into a resident map, builds the copy
list, writes the payload. Move that to a small device kernel that emits a **compact miss list + count** in
mapped memory; the host then only reads the list (no set math, no per-id branching) and queues the copies
(the copies must stay host-issued - that is not negotiable).

Gates: `frac 0` byte-exact; launch count per step unchanged; host time per layer down (P1's numbers are the
baseline); hit rate unchanged.

### P3 - MTP end to end (the only x2.5)

State: the head is local (`~/bench-rel/mtp/mtp-component.gguf`) and loads via `--mmproj`; the schedule-size
bug is fixed (`fd2e6f1`); steady-state drafting works at prompt 8 (2-row pass, 106 ms); it still faults at
prompt 512 **inside `drafter_prefill_chunk`**, before any drafter forward runs.

Cost side, measured: a 2-row pass is **+29%** (82 -> 106 ms), so depth 1 needs >65% acceptance to break
even. That is *because* the pass is host-bound; P2 and P3 multiply each other.

Gates: `--mtp` output == no-MTP output byte-exact (speculation must not change greedy text); then TPOT and
**accepted drafts per pass** (the engine reports them) at `frac 0` and `frac 0.55`.

### P4 - rayon saturation of the CPU leg

`RAYON_NUM_THREADS` on one decode: if 8 vs 16 changes nothing, the CPU leg is not the constraint and only P2
is left; if it does, size it.

### P5 - the graph work

Only after the above, and only for what is left in `m6-graph.md` (attention-region capture, ~1-4 ms).

## Measurement protocol (non-negotiable)

1. **Medians of >= 3 runs**, not single runs: the machine varies by ~5%.
2. Report **TPOT + tok/s + hit rate + the exact flags**.
3. Any correctness claim: `frac 0` + `NO_LOOKAHEAD` **byte-exact against `harness/m1/reference.oracle.txt`**.
4. Any memory/liveness claim: run it **>= 6 times** and count failures (that is how the NaN was found: 0/6
   after the fix against 2-3/5 before).
5. A probe that changes behaviour must be named in the result line.
