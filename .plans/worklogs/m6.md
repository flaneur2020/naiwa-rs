# M6 — performance

> The graph-capture work is in [`m6-graph.md`](m6-graph.md) (renamed from `m6.md`). This file is the
> performance milestone: what the number is, where it goes, and the order in which to attack it.

## The number

| configuration | TPOT | tok/s | hit rate |
|---|---|---|---|
| `frac 0` + `NO_LOOKAHEAD` (deterministic, used by the oracle) | 80-85 ms | 11.6-12.4 | **19.7%** |
| production: `frac 0.55`, prediction thread on | 78-87 ms | 12.4-12.8 | **81-84%** |
| Strata, same model family, 4070 Ti SUPER 16 GB, `--spec 4 --mtp` | ~33 ms | **76.0** | - |
| Strata, IQ2_XS | ~26 ms | 97.9 | - |

Always report **TPOT *and* hit rate**, plus which of `NO_LOOKAHEAD` / the probe is on: the two
configurations differ by 4x in hit rate and they are not comparable. `NO_LOOKAHEAD` exists for byte-exact
gates, not for speed comparisons.

## Hit rate: v2 matches the old engine; the low number was `NO_LOOKAHEAD`

Same command, same model, same cache (`frac 0.55`, prompt 512, gen 32, prediction thread on):

| engine | TPOT | tok/s | hit rate | prediction loads |
|---|---|---|---|---|
| qflash-rs (eager, the frozen oracle) | 80.8 ms | 12.4 | **85.1%** (10931/12847) | 470 empty + 3171 swaps |
| naiwa-rs v2 | **77.9 ms** | **12.8** | **84.4%** (10832/12838) | 470 empty + 3154 swaps |

So 19.7% was never a regression - it is what `NO_LOOKAHEAD` gives (prediction off, only the miss-driven
admissions and the background fill populate the cache). Production hit rate is identical to the old engine
within 0.7 points, and v2 is 3.6% faster per pass.

The prediction design itself is the **same code lineage in both**:

1. layer L's activation is published into L's mapped slot by a stream-ordered kernel; a worker thread reads
   it and matmuls it against **layer L+1's own router** (on the CPU, no device round trip);
2. the predicted set is the **union of every row's top-k** by votes (`union_by_votes`), i.e. the experts
   most rows want first;
3. admission: into empty slots freely; over an LRU resident at most `MAX_LOOKAHEAD_SWAPS x rows` times
   (a wrong prediction costs a slot, not correctness);
4. independently, `spawn_fill` fills remaining empty slots with `fill_candidate` = the unreserved expert
   with the highest hit count - the cache keeps filling when predictions stop.

Where the ceiling is: the expert working set is 25.9 GB against 2 GB of cache, i.e. ~8% of it fits, and
the measured 84-85% comes from the top-k being highly skewed per layer. The knobs left are
`MAX_LOOKAHEAD_SWAPS` (more churn per step), predicting two layers ahead (more lead time for the DMA), and
seeding `hit_counts` from the router's rank instead of only from actual hits so the background fill does not
chase its own tail.

## What is already ruled out - do not re-litigate

| idea | verdict | evidence |
|---|---|---|
| bigger expert cache | **negative** | 2 GB 80.8 ms vs 4 GB 84.7 ms; working set is 25.9 GB against 12 GB, so slots barely change the miss count while every admission copies 2.1 MB. KV cache is not the constraint (118 MB at 4 k) |
| GPU kernel work | pointless | GPU idle ~98% of the pass |
| whole-step CUDA graph | impossible | the host is irreducibly in the loop per layer: staging is host-issued and decided from that layer's top-k (`m6-graph.md`) |
| attention-region capture | small | 1-4 ms of an 82 ms pass |
| batching the CPU expert gemv | **already done** | `CpuExperts::forward -> fused_moe_decode(..all ids..)` is one call, not per expert |

## Plan, in order

### P0 - deterministic memory (DONE)

Both NaN sources were uninitialised buffers: the schedule payload (`cudaHostAlloc`, `4044e8a`) and the
paged KV blocks (`Tensor::empty`, `0e8c8462`). Failure rate 2-3/5 -> 1/5 -> **0/6**. Without this every
timing was untrustworthy and the oracle could not be byte-exact for the right reason.

### P1 - split the 1.6 ms/layer (next action, cheap)

`NAIWA_FUSED_DBG=1` already prints the CPU MoE cost (`us/call`, `us/pair`, `us/expert`, `gap_us/call`).
Run one decode with it at `frac 0` and at `frac 0.55` and write down:

- host bookkeeping per layer (read the top-k back, compute the miss set, issue the DMA, write the payload),
- CPU gemv per layer (`us/call`),
- the gap between calls (`gap_us/call`), which is the host's own share.

Those three numbers decide P2 and P4. Do not start either without them.

### P2 - take the miss decision off the host

Today the token thread, per layer: spins for the top-k, hashes the ids into a resident map, builds the copy
list, writes the payload. Move that to a small device kernel that emits a **compact miss list + count** in
mapped memory; the host then only reads the list (no set math, no per-id branching) and queues the copies
(the copies must stay host-issued - that is not negotiable).

Gates: `frac 0` byte-exact; launch count per step unchanged; host time per layer down (P1's numbers are the
baseline); hit rate unchanged.

### P3 - MTP end to end (the only x2.5)

State: the head is local (`~/bench-rel/mtp/mtp-component.gguf`) and loads via `--mmproj`; the schedule-size
bug is fixed (`fd2e6f1`); steady-state drafting works at prompt 8 (2-row pass, 106 ms); it still faults at
prompt 512 **inside `drafter_prefill_chunk`**, before any drafter forward runs.

Cost side, measured: a 2-row pass is **+29%** (82 -> 106 ms), so depth 1 needs >65% acceptance to break
even. That is *because* the pass is host-bound; P2 and P3 multiply each other.

Gates: `--mtp` output == no-MTP output byte-exact (speculation must not change greedy text); then TPOT and
**accepted drafts per pass** (the engine reports them) at `frac 0` and `frac 0.55`.

### P4 - rayon saturation of the CPU leg

`RAYON_NUM_THREADS` on one decode: if 8 vs 16 changes nothing, the CPU leg is not the constraint and only P2
is left; if it does, size it.

### P5 - the graph work

Only after the above, and only for what is left in `m6-graph.md` (attention-region capture, ~1-4 ms).

## Measurement protocol (non-negotiable)

1. **Medians of >= 3 runs**, not single runs: the machine varies by ~5%.
2. Report **TPOT + tok/s + hit rate + the exact flags**.
3. Any correctness claim: `frac 0` + `NO_LOOKAHEAD` **byte-exact against `harness/m1/reference.oracle.txt`**.
4. Any memory/liveness claim: run it **>= 6 times** and count failures (that is how the NaN was found: 0/6
   after the fix against 2-3/5 before).
5. A probe that changes behaviour must be named in the result line.
