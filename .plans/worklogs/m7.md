# M7 — reduce the per-token cost of speculative decode

> Prerequisite reading: [`m6.md`](m6.md) for the round budget and [`perf-vs-strata.md`](../perf-vs-strata.md)
> for the comparison with Strata. M7 changes nothing about correctness gates: `frac 0` + `NO_LOOKAHEAD` stays
> byte-exact against `harness/m1/reference.oracle.txt` after every commit.

## Headline: with a predictable prompt this configuration reaches 40 tok/s

Prompt: "Continue the list with the next numbers, one per line, no commentary." followed by 1..12. Same
configuration (MTP, `frac 0.2`, cache 4, split on, predictable text):

| depth | round p50 | tok/s | tokens/round | **ms/token** |
|---|---|---|---|---|
| np2 | 82.0 ms | 33.8 | 2.77 | 29.6 |
| np3 | 94.1 ms | 38.7 | 3.64 | 25.8 |
| **np3, gen 256** | 98.1 ms | **40.0** | 3.92 | **25.0** |
| np4 | 107.4 ms | **40.9** | 4.40 | **24.4** |

**24-30 ms/token, i.e. the M7 target (<= 35 ms) is met on this workload**, and 40 tok/s is at the level of
Strata's recorded 41.0 on a 16 GB card. The comparison that matters is per *text class*: a code-continuation
prompt gives 25-26 tok/s (2.5-2.9 tokens/round) and this counting prompt 38-41 (3.6-4.4), because acceptance
is the whole game - the round only grows ~15% from np2 to np4 while the tokens per round grow 60%.

### np8 in numbers (narrow format)

One round = 185 ms, 8.0 tokens:

```
一轮 185 ms
├ GPU 计算    40 ms  22%
├ host 发射   70 ms  38%
├ 等 CPU      47 ms  25%  p50 611us
├ 等 DMA      27 ms  15%  p90 1.0ms
└ copy 流     97 ms  重叠, 53% 占空
```

One layer = 3.85 ms:

```
每层 3.85 ms
host ┃████████ 1.46  切分/发拷贝/launch
gpu  ┃████ .84      常驻段 + staged 段
     ┃░░░ .61       等 CPU payload
     ┃░ .01         等 DMA
copy ┃███████ 2.0   预载+staging（重叠）
cpu  ┃███ .9        专家 gemv（重叠）
```

What overlaps:

```
重叠 ✅
· copy 流 ← 所有东西
· CPU gemv ← 常驻段/staged

串行 ❌
· 等 CPU payload
· 等 DMA
= 40% 的轮（np2 时只有 20%）
```

Read it as: the GPU only computes 40 ms of a 185 ms round; the
round is host launches plus two waits, and the waits grow with
depth.

### CPU gemv vs DMA: different resources, neither saturated

They do **not** contend for PCIe - the CPU gemv never touches the
link, it reads host DRAM. What they share is the **host DRAM**,
because both read the same expert stacks.

Measured at np8:

```
PCIe（host→VRAM）
  平均  6.4 GB/s
  繁忙 12.8 GB/s
  上限 ~25 GB/s      → 26-50%

host DRAM（专家栈读取）
  CPU gemv  4.0 GB/s
  DMA 读源  6.4 GB/s
  合计     10.4 GB/s
  上限  35-40 GB/s   → 26-30%
```

So at np8 both are at ~1/4 to 1/2 of what the machine can do:
the limit is **serialisation**, not bandwidth.

**But they do contend for DRAM, and the contention grows with
depth** - both sides read the expert stacks, and the demand is
proportional to the verify rows:

```
          host DRAM 占峰值
np2         ~5 GB/s    ~13%
np8       10.4 GB/s    ~28%
np15      18.5 GB/s    ~50%   ← 随机读效率只有 ~50%，已贴近实际上限
```

Evidence that np8 has not hit it yet: one CPU job goes
850 us (3 rows) -> 1354 us (9 rows), i.e. **1.6x for 3x the
rows** (`NAIWA_RET_DBG`), and the per-expert cost stays in the
200-270 us band. That is clean sub-linear scaling, not a
bandwidth wall - which is why np8 still gains and np15 (whose
demand is ~50% of peak, with random-read efficiency around 50%)
does not.

Is the CPU gemv still the big item? It is the biggest single piece
of *work* (82 ms/round of gemv), but only 47 ms of it is exposed;
the biggest *exposed* item is the host launch chain (70 ms).

## np8 breakdown: the waits grow from 20% to 40% of the round

nsys over the last two rounds of an np8 run (counting prompt, `frac 0.2`, cache 4, split; 42.8 tok/s,
87.3% hit, round ~185 ms):

| item | per round | share | detail |
|---|---|---|---|
| GPU compute (segments, attention, PLE) | 40.3 ms | 22% | was 23.2 ms at np2 (3 rows) |
| **CPU-payload wait** | **46.6 ms** | **25%** | p50 **611 us** (176 us at np2), p90 1.6 ms, max 3.5 ms |
| **staging wait** | **27.5 ms** | **15%** | p50 11 us but p90 **1.06 ms** |
| host launch chain + sampler | ~70 ms | 38% | grows with rows: 9 selections to place per expert list |
| copy stream (overlapped) | 97 ms | 53% duty | 2374 MiB over 370 ms = 6.4 GB/s average, 12.8 while busy |

So the depth sweep's shape comes from here: **every extra draft row grows the CPU job and the DMA**, and the two
waits go from 24 ms (np2: 20.7 + 3.3) to **74 ms** (np8) - 40% of the round. Acceptance still wins up to np8
because the extra token costs ~18 ms while saving 23 ms, but past np8 the waits eat the gain.

That also says where deep drafting needs help, in order: **the CPU-payload wait** (46.6 ms at np8, p50 611 us -
the job is now 2-3x bigger than the resident compute that could cover it) and then the staging tail
(p90 1.06 ms). M7.2's honest options (fewer experts, more cover) are the only ones left, and at np8 "more cover"
means a larger `frac` - which at np3 was already past its optimum at 0.2, so the CPU-payload wait has to be
attacked by shrinking the job (hit rate) rather than by covering it.

## How to raise the effective bandwidth

Ranked, with the reason each one can (or cannot) move the needle at np8:

1. **Move the read to VRAM: stage more, on a second GPU stream.** This is the big one. PCIe is at
   **6.4 of ~25 GB/s (26%)** while host DRAM is at 28% of its practical ceiling, and VRAM reads are ~500 GB/s.
   So the machine has 4x headroom on the link and none of it helps, because the staged segment is queued
   *after* the residents on the same stream - raising `frac` therefore lengthens the round (measured: 0.4 and
   0.6 both lose). Putting the staged segment on **its own stream** makes it concurrent with the residents (the
   two are independent: residents read their slots, staged read the ring), which is what would let `frac` rise
   and shift reads off DRAM.
2. **Interleaving the stacks - refuted by a microbenchmark, and it revealed something bigger.**
   `harness/m7/pack_layout.c` reads 200 random experts (2 MB each) with 6 threads, once from three far-apart
   0.7 MB regions (the current layout) and once from one contiguous 2 MB block per expert:

```
split  3 regions: 14.7 ms  28.6 GB/s
packed 1 region : 14.7 ms  28.6 GB/s     -> 1.00x, no difference
```

   So the layout does not matter: at 0.7 MB per region the DRAM row activation is already amortised. But the
   same loop shows a **pure read reaches 28.6 GB/s** while the engine's gemv achieves **7.4 GB/s** on the same
   bytes. **The CPU leg is compute-bound, not memory-bound** - it is unpacking quantised blocks and doing the
   dot products, at roughly a quarter of the rate a plain read sustains. Every "raise the bandwidth" idea
   (layout, prefetch, huge pages, pinning) is therefore beside the point for the CPU leg; the lever is the
   kernel itself (fewer instructions per byte, or more cores actually busy in the dot products).

3. **Warming the CPU experts into L3 - tried, and it hurts.** `NAIWA_CPU_PREFETCH` sweeps the byte ranges of
   the predicted CPU-only experts in the lookahead thread (one byte per 64 B line, so a DRAM read rather than a
   copy) on the theory that three experts (6.3 MB) fit in the 32 MB L3. Measured at np8: `compute_us`
   1376 -> **1481** and 44.1 -> 38.4 tok/s, i.e. worse. The likely reason: the concurrent PCIe preload streams
   through the same cache and evicts the warmed lines before the gemv reads them, so the work is paid twice.
   Kept behind the env flag as a refuted experiment.

3. **Repack the CPU expert stacks interleaved (gate|up|down contiguous per expert).** One expert is currently
   **three** far-apart regions (gate, up and down are three separate stacks), so a single expert read costs
   three random 0.7 MB touches. Interleaving them into one 2.1 MB block per expert turns that into one
   contiguous read - better TLB and DRAM row behaviour, and one prefetch stream instead of three. Load-time
   repack of the CPU copy; measurable with `NAIWA_RET_DBG`'s `compute_us` alone.
4. **`RUN_ROWS` sweep, done: no further gain.** Measured at np8 (`compute_us`): 32 -> 1641 us, **64 -> 1354 us**,
   128 -> 1467 us. 64 is the optimum; larger runs lose because the rows of one expert stop fitting the caches.
5. **Fewer bytes per expert on the CPU** (lower quant for the CPU-resident copies) would move the number
   directly but changes numerics, so it is out - the oracle is byte-exact by construction.

## The metric

Per-token cost = **round time / tokens per round**. Both halves are levers, and they trade against each other:

```
np2, frac 0.2, cache 4, predictable prompt:  round ~104 ms, 2.2 tokens/round  -> 47 ms/token (21.0 tok/s)
np2 best round (gen 96, frac 0.2):            90.4 ms                         -> 23.3 tok/s
np3:                                         109.9 ms, 2.7-2.9 tokens/round  -> 23.3 tok/s
no MTP (1 token/round):                       63.2 ms                        -> 15.8 tok/s
```

Target for M7: **<= 35 ms/token (>= 28 tok/s)** without losing the `frac 0` oracle, by shrinking the round
while holding acceptance.

## M7.1 - order the copy stream: staging first, preload after

Staging is on the critical path; the preload is speculative and can always be delayed. Today both share one
copy stream, so a staging copy can queue behind a burst of 2.1 MB preloads - invisible at `frac 0.2` (11 us
waits) but the binding constraint at `frac 0.4` / np3.

Do: a second copy stream for the preload, or a "no preload while staging is outstanding" gate.
Gate: staging wait p50 stays ~10 us at `frac 0.2` **and** does not grow at `frac 0.4`/np3; round p50 no worse;
`frac 0` oracle unchanged.

## M7.2 - hide the CPU payload (the 20%): what it actually means

The numbers that define the problem: the CPU leg does **~41 ms of gemv per round** (163 ms per four rounds,
~850 us per job), yet only **20.7 ms per round** shows up as waiting. So most of it already overlaps - the
residents and the staged segment run while the CPU computes. What does *not* fit is the **tail**: with three
or four verify rows a job is 0.85-1.0 ms, while the GPU work queued before the CPU-add node is only
~483 us (residents) + a small staged share, so the last ~400-500 us per layer is exposed.

Three ways to close it, cheapest first:

**(a) WRONG - reordering the CPU-add earlier cannot help; it removes cover.** The wait has to stay *last*
because the CPU contribution belongs to this layer's output, which the next layer consumes: the MoE output feeds
L+1's attention, and the fork's router runs *inside* `moe.forward` after attention, so a CPU add deferred to the
next layer would land too late (after that layer's router and after its attention had already read `res`). And
moving the wait *earlier* into this layer means the staged segment queues behind it, so the exposed time grows
rather than shrinks. What covers the wait can only be **more GPU work before it** or **a shorter CPU job**:

- more GPU work before the wait = a larger staged share, which is exactly why `frac 0.2` beat `frac 0.05` at
  np3 (and why 0.4/0.6 then lost: the PCIe cost overtakes the coverage gain);
- a shorter CPU job = (b) below, or splitting it = (c).

So (a) is dropped; the corrected list is (b) speculate the CPU gemv in the gap, (c) split the job so only the
tail is waited on, and (d) tune the staged share, which is the `frac` sweep already done.

**(a, original sketch, kept for the record) Reorder: put the CPU-add node before the staged segment.** The CPU result does not depend on the staged
experts, so `[residents] -> [CPU add] -> [staging gate] -> [staged]` exposes only what the residents did not
cover, and lets the staged segment absorb the tail. ~5 lines on top of the S2 split.
Caveat: it changes the order of the two additions, so `frac 0` stays byte-exact (no staged segment there) but
`frac 0.55` may gain a rounding variant - it has to be checked against the two-variant set, not byte-exact.

**(b) WRONG TOO - the CPU cannot precompute the values, only the ids.** The MoE of layer L takes
`h = mlp_hc.mix(xn)` where `xn` comes out of that layer's *attention*, so layer L's MoE input activation does
not exist until layer L runs. The lookahead predicts L's experts from **L-1's** activation, which is why it can
answer "which experts" but never "what they compute". So the gap can be used to *stage weights* (what the
preload does) but not to run the CPU gemv - the multiplication has no operand yet.

What that leaves for the CPU wait, in order of feasibility:

| lever | mechanism | note |
|---|---|---|
| **fewer experts on the CPU** | hit rate / `frac` / cache size | already at the optimum found (`frac 0.2`, 4 GB) |
| **a faster per-expert gemv** | **intra-expert parallelism**: `gate` and `up` are two independent gemvs over the same input, and `down`'s output rows split cleanly across threads. `fused_moe_decode` currently runs them serially inside one task, so one stream gets ~8 GB/s while the machine can aggregate 35-40 | fork-side, `fused_cpu.rs`; the one lever that is not yet used |
| more cover before the wait | a larger staged share | measured: helps until PCIe overtakes (0.2 is the optimum) |

The intra-expert split is the honest version of M7.2: same total bytes, but read with 2-4 streams instead of
one, which is exactly the shape of the bandwidth measurement (per-pair 8 GB/s against a 35-40 GB/s machine).

**(b'') Intra-expert parallelism: already implemented, and not the limit.** Reading `fused_cpu.rs`:
`gate_up` dispatches `par_tasks(pairs.len() * inter.div_ceil(run_rows()))` - with one pair and
`inter = 1536`, `run_rows() = 64` that is **24 tasks**, each reading 64 rows of both the gate and the up stack;
`down_sum` dispatches `par_tasks(rows * hidden.div_ceil(run_rows()))`, i.e. 120 tasks at 3 rows. The work is
already split far below the core count, so "split gate and up across threads" has no headroom.

What the numbers say instead: a job of ~3 pairs takes ~850 us and reads 3 x 2.11 MB = 6.3 MB, i.e. **7.4 GB/s
for the whole job with 24-72 tasks live** - far below the machine's 35-40 GB/s. So the limit is **DRAM
behaviour on 2 MB random reads** (the three pairs are three unrelated 2 MB regions in a 26 GB space), not
thread count. That is the same conclusion as the earlier bandwidth analysis, now with the code checked.

Consequence: the CPU leg can only be reduced by **fewer experts** (hit rate, `frac`, cache - all at their
optimum) or by **more cover** before the wait (larger staged share, capped by PCIe). There is no parallel
headroom left to win.

**(b, original sketch, refuted above) Speculative CPU compute in the gap.** The lookahead already predicts layer L+1's
experts *and* already has layer L+1's input activation at that moment (the prediction matmuls it against the
router). For predicted experts that will not be resident, the CPU can therefore run **the expert gemv itself**
in the gap - the same gap the preload uses - and stash the result keyed by expert id. When the real routing
lands, the CPU job shrinks to the *unpredicted* misses (~15% of them at 85% hit), i.e. from ~0.85 ms to a few
hundred microseconds, which then hides under the residents.
Cost: the wasted work when the prediction is wrong (it runs in an otherwise idle gap, so it is nearly free),
plus a per-layer stash and a hit check. This is the CPU-side twin of the preload and reuses its job.

**(c) Split the job** (fallback if (b) is too invasive): submit the routing-known part immediately and append
the stragglers, so the wait covers only the tail rather than the whole job.

Gates for either: CPU-payload wait p50 <= 80 us at np2/np3 (from 176), round p50 <= 95 ms at np2, the `hit
rate` / `ROUND_STATS` split unchanged, `frac 0` byte-exact.

## M7.2 - old sketch

The CPU job is submitted before the residents launch, so it *should* hide, but with three verify rows it takes
~2x longer and lands after the staged segment. Two ways:

1. **Speculative CPU work**: reuse the lookahead prediction - for predicted experts that are *not* resident,
   the CPU can run their gemv in the gap, and if the real routing agrees the result is already there. This is
   the CPU-side analogue of the preload (the prediction is 85% right, so this pays whenever a miss was
   predicted).
2. **Split the job**: submit the *resident-side* misses first (they are known as soon as the routing lands)
   and let the last few stragglers join late, so the wait covers only the tail.

Gate: CPU-payload wait p50 <= 80 us at np2 (from 176), round <= 95 ms; `frac 0` oracle unchanged; miss
accounting (`hit rate` line) unchanged.

## M7.3 - `--lookahead-swaps`: done, and it is a real knob

Added as a proper flag (`--lookahead-swaps N`, default 2, `0` allowed) rather than an env switch, threaded
from the CLI through `install_cpu_moe` into the cache provider and each layer. Sweep, np2 / `frac 0.2` /
cache 4 / predictable prompt, gen 96:

| `--lookahead-swaps` | hit rate | round p50 | tok/s | swaps over residents |
|---|---|---|---|---|
| **0** | 26.5% | 133.9 ms | 18.3 | **0** |
| **1** | 75.6% | 91.2-95.7 ms | 24.4 | 5530 |
| **2** (default) | 81.5% | 91.5-93.9 ms | 26.2 | 9000 |

`0` is catastrophic (a predicated expert can only ever fill an *empty* slot, so once the cache is full the
lookahead stops working and the hit rate collapses to 26%), `1` is within ~7% of `2` and halves the PCIe
traffic, and `2` is the best throughput. So the knob is useful for trading traffic against hit rate - which is
exactly the resource the timeline said was contended - but the default is right.

## The CPU expert stacks are already pinned - and higher `frac` is a dead end

Checked before changing anything: the cache path already pins every layer's stacks
(`pin_expert_stacks` runs unconditionally after the huge-page advice); a debug run prints
`layer 0 stacks: 564 MiB on huge pages, 568 MiB pinned`. So the staging DMA source is page-locked already,
and 12.8 GB/s while busy is what pinned Gen4 x16 gives for this mix (the nsys average copy is 453 KiB, because
payload/KV copies are mixed in with the 2.1 MB expert copies).

Raising `frac` on top of that, np3, cache 4, predictable prompt:

| `frac` | round p50 | tok/s | staged % of selections | PCIe per 4 rounds | CPU gemv per 4 rounds |
|---|---|---|---|---|---|
| **0.2** | **109.9 ms** | **23.3** | 7.1 | 600 MiB | 163 ms |
| 0.4 | 110.9 ms | 23.1 | 10.3 | 1440 MiB | 190 ms |
| 0.6 | 125.5 ms | 22.8 | 14.5 | 1946 MiB | 138 ms |

So it is a dead end past 0.2: the CPU leg does shrink (190 -> 138 ms of gemv) but PCIe traffic triples and the
staged segment is serial after the residents, so the round **grows**. The optimum is where the CPU saving and
the DMA cost cross, and that is ~0.2 at np3 with a 4 GB cache.

## M7.3 - stop the preload from thrashing the resident set

Measured in the same window: `lookahead loaded 470 into empty slots, 2380 over residents` - the prefetch
replaces residents five times more often than it fills empty slots, which is 5 GB of PCIe traffic per run for
a hit rate that is already 78-88%. Sweep `MAX_LOOKAHEAD_SWAPS` (currently 2) and the fill policy, measuring
hit rate *and* round time: the goal is fewer swaps at the same hit rate.

Gate: same hit rate (+-1 point) with <= half the swaps; round p50 improves; `frac 0` oracle unchanged.

## M7.4 - capture the attention region (the host floor)

20.2 ms of the round is the host launch chain (30-40 launches/layer outside the segments). `m6-graph.md` has
the resident-input work done (cos_sin + every metadata map + per-layer lists) so this is the next step there:
capture `attn_hc.mix/inject` + the mixer per layer. Expected ~10 ms off the round.

Gate: `frac 0` oracle byte-exact, `cuGraphLaunch` per step up by 48, host launch count down by ~30/layer.

## M7.5 - make acceptance a property of the workload, not of a flag

Measured tokens/round: 1.68 (synthetic prompt) -> 2.54 (predictable, np2) -> 2.92 (np3), and np3 is a net
loss when acceptance does not rise with it. The engine already has an adaptive depth (`--mtp-n-predict` omitted);
M7 should measure it against a fixed np per prompt class and pick one policy, so that "depth" is not a knob a
user has to get right.

Gate: on two prompt classes (code continuation, prose), the chosen policy is within 5% of the better of
np2/np3 fixed, in tokens/round at equal round time.

## Order and expected effect

| step | expected | risk |
|---|---|---|
| M7.1 copy ordering | enables M7.2/M7.3 at higher `frac` | low |
| M7.2 hide CPU payload | **-15..-20 ms/round** (~47 -> 39 ms/token) | medium (prediction reuse) |
| M7.3 preload thrash | -5..-10 ms/round + less PCIe | low |
| M7.4 attention capture | -10 ms/round | medium (`m6-graph.md` state) |
| M7.5 acceptance policy | +10-20% tokens/round | low |

Doing M7.2 + M7.3 + M7.4 together is the path to ~35 ms/token; each is independently verifiable with the
`frac 0` oracle plus the `ROUND_DBG` p50 and the `hit rate`/`lookahead` lines.

## Measurement protocol (unchanged from M6)

1. `--prompt-file` with a predictable prompt (the synthetic benchmark prompt depresses acceptance by ~40%).
2. Report **round p50** (robust) plus tokens/round; tok/s alone is not comparable across runs.
3. >= 3 runs for any claim, >= 6 for a liveness claim (that is how the NaN was found).
4. `frac 0` + `NO_LOOKAHEAD` byte-exact for every change; `frac 0.55` against the two-variant set.
