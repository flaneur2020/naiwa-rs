# M7 — memory throughput

## Status (2026-10-18)

**Throughput reached** (counting prompt, high acceptance, `--depth 4`):

```
np3 gen256   40.0 tok/s   25.0 ms/token
np8          43.3 tok/s   23.1 ms/token
np8 + swaps1 39.6 tok/s   165.5 ms round  (-11% vs swaps2)
no MTP       15.8 tok/s
code text    25-26 tok/s   (acceptance 2.5-2.9 instead of 8)
```

**The three links, and how much of each we use:**

```
link                 used         ceiling     share
host DRAM (dots)     8.2 GB/s     28.6        29%
host DRAM (one round) 14.5 GB/s    28.6        51%   <- at np8, incl. all traffic
PCIe busy            12.8 GB/s    ~25          50%
PCIe average          6.4 GB/s    ~25          26%
VRAM                 unused       ~500          0%   <- the biggest unused link
```

**Where the bytes go in one np8 round: 2.68 GB**

```
CPU experts   745 MB  28%   host DRAM read
staged       1000 MB  37%   host DRAM read + PCIe write
preload       935 MB  35%   PCIe (prediction)
```

**Conclusion: we are limited by *how fast we can consume* bytes, not by
byte supply.** The link with 4x headroom (PCIe) is half used, VRAM is
idle, and the CPU dots consume DRAM at 2.5 GB/s per core against a
11 GB/s per-core read ceiling - they are instruction-bound.

## Measured before doing it: the second stream is worth only ~3 ms

I profiled `frac 0` against `frac 0.2` at np8 before touching the stream plumbing, over the same
370 ms steady-state window:

| | GPU kernels | of which waits | GPU compute | tok/s |
|---|---|---|---|---|
| `frac 0` (no staging at all) | 100.5 ms | 26.5 ms | **74.0 ms** | 36.6 |
| `frac 0.2` | 228.9 ms | 148.2 ms | **80.8 ms** | **42.8** |

So the staged segment itself only adds **~3.4 ms per round** of GPU compute. Making it concurrent with the
residents would therefore buy ~2% of the round - **not worth a cross-stream change** in candle's allocator and
stream semantics. Dropped from the plan.

The same table says something much more interesting: at `frac 0.2` the **waits are 148 ms of 370 ms (40%)**
versus 26.5 ms at `frac 0`, even though `frac 0` puts *more* experts on the CPU (10392 misses vs 6223). The CPU
job is not bigger per layer at `frac 0.2`, yet it waits longer - because the staging/preload DMA is streaming
through the same host DRAM and slows the CPU gemv down (the contention the earlier bandwidth arithmetic
predicted). That is why `frac` has an optimum at 0.2 rather than "as much as PCIe allows": the two paths fight
over DRAM, and the CPU leg loses.

**Consequence for the plan: the lever is the CPU dot's efficiency, not moving more bytes.**
Raising its per-core rate (2.5 -> 5-10 GB/s) shortens every job, shrinks the wait, *and* reduces the time the CPU
leg spends contending with the DMA.

## To maximise bandwidth utilisation, in order

1. **Unlock the unused link: stage more, on a second GPU stream.**
   PCIe 26% average, VRAM ~0%. The staged segment is queued after the
   residents on one stream, so raising `frac` lengthens the round
   (measured at 0.4/0.6). On its own stream those bytes move at VRAM
   speed and DRAM reads drop.
2. **Make the dots consume DRAM faster.** 2.5 GB/s/core on Q4_K against
   11 GB/s for a plain read: the per-super-block scale/min decode and
   the per-job activation quantisation are the gaps. Doubling this turns
   the CPU leg from 1.35 ms to ~0.7 ms per job, which fits under the
   residents and removes most of the 47 ms/round CPU wait.
3. **Stop moving bytes that buy little: the preload is 35% of traffic.**
   `--lookahead-swaps 1` already measured -11% round time at np8.
4. **Re-measure at a real context** (`--depth 2048`): every number here
   is decode at a 4-token context, i.e. MoE-dominated with a trivial KV.

## The kernel itself: a faithful llama.cpp port, so the gap is elsewhere

Read `candle-core/src/quantized/avx.rs::vec_dot_q4k_q8k`: it is the llama.cpp AVX2 kernel - the 6-bit
scale/min unpack via `KMASK1/2/3`, `_mm256_shuffle_epi8` with a **static** `K_SHUFFLE` table, then
`maddubs`+`madd` over the super-blocks with two accumulators (`acc` for the quants, `acc_m` for the mins).
There is no scalar prologue to fix and no obviously missing instruction; candle also dispatches Q2_K/Q3_K/Q5_K/
Q6_K/Q4_0/Q8_0 to the same family (`has_avx2_fma()`), which is what our Q4_K/Q3_K/Q2_K experts use.

So the arithmetic on paper does not match the measurement:

```
one output row of gate (K = 2048)
  = 8 super-blocks x ~40 SIMD ops   ~= 320 ops
  x 512 rows x 3 projections        ~= 490k ops per expert
  at ~3 IPC / 3.5 GHz               ~= 47 us per expert
measured                            = 264 us per expert   (5.6x off)
```

and the thread scaling is just as odd:

```
1 thread   2.45 GB/s     (12.4 MB job in 5057 us)
8 threads  8.90 GB/s     (3.6x, per-thread drops to 1.1)
```

Two suspects remain, and only a micro-benchmark can separate them:

1. **cache behaviour**: each output row touches a fresh 1152 B of weights; 512 rows walk 590 KB per projection,
   so if the hardware prefetcher does not follow (or the Q8 activation of the row is re-fetched from L2 per
   row), the dot becomes a memory-latency kernel rather than an instruction-bound one;
2. **SMT/DRAM interference** at 8 threads (6 physical cores): per-thread rate halves, so the aggregate only
   reaches 8.9 GB/s.

Next step (cheap, decisive): add a `#[cfg(test)]` bench **inside candle** (we own the fork) that times
`vec_dot_q4k_q8k` on one synthetic expert's rows, single-threaded, and reports GB/s next to a pure read of the
same bytes. That number says whether to attack the loop or the memory behaviour - and it is the last unknown in
the CPU leg.

## Ruled out (measured, do not retry)

```
stack interleave   1.00x either way (harness/m7)
L3 warming         slower (PCIe streams evict it)
huge pages         already 2 MB
pinning            already page-locked
RUN_ROWS           64 optimal (32: 1641us, 64: 1354, 128: 1467)
thread count       8 optimal, 10 was the old default (SMT adds nothing)
lower-bit CPU       breaks the byte-exact oracle
```

## The three links, measured

| link | measured | ceiling | used |
|---|---|---|---|
| **host DRAM, pure read** (`harness/m7/pack_layout.c`, 6 threads) | **28.6 GB/s** | ~35-40 GB/s | ~75% (that is the practical ceiling) |
| **host DRAM as the CPU experts see it** (fused Q4_K dots, 8 threads) | **8.2 GB/s** | 28.6 GB/s | **29%** |
| the same dots, **one thread** | 2.5 GB/s per core | - | instruction-bound, not bandwidth-bound |
| **PCIe** (gen4 x16), while the copy stream is busy | **12.8 GB/s** | ~25 GB/s | ~50% |
| PCIe, averaged over a round (53% duty cycle) | 6.4 GB/s | ~25 GB/s | 26% |
| **VRAM** | ~500 GB/s | - | ~0 - nothing is computed there that could be |

## What moves in one round (np8, counting prompt, `frac 0.2`, cache 4)

| item | experts/round | bytes | share of host reads |
|---|---|---|---|
| CPU misses (host DRAM read) | 353 | 745 MB | 28% |
| staged experts (host DRAM read + PCIe write) | 473 | 1000 MB | 37% |
| **preload / prediction copies (PCIe)** | 443 | **935 MB** | 35% |
| **total** | 1269 | **2.68 GB per round** | 100% |

Over a 185 ms round that is **14.5 GB/s of host DRAM traffic** - i.e. 51% of the 28.6 GB/s the machine can
actually sustain. So at np8 we are **half way to the DRAM ceiling**, and the ceiling arrives at about
np15 (measured: 18.5 GB/s of demand, and np15 is where the depth sweep turns over).

## The four levers, ranked

### 1. Stop paying for the preload (935 MB/round, 35% of all traffic)

`--lookahead-swaps` exists now (`0..N`, default 2) and the prediction replaces residents ~5x more often than it
fills empty slots. Measured at np8 (counting prompt, `frac 0.2`, cache 4, gen 96):

| swaps | hit rate | swaps over residents | round p50 | tok/s | CPU us/job | staged MiB / 4 rounds |
|---|---|---|---|---|---|---|
| 1 | 83.8% | 3817 | **165.5 ms** | **39.6** | 316.6 | 963 |
| 2 | 86.8% | 5968 | 185.8 ms | 38.1 | 350.1 | 935 |
| 3 | 88.2% | 5690 | ~180 ms | 43.2 | 321.3 | 887 |

So `1` gives the shortest round (**-11%** against the default 2) at a 3-point hit-rate cost, and the gain is
**not** from PCIe bytes (963 vs 935 MiB - the same) but from the CPU leg (317 vs 350 us/job) and from removing
stalls: every `replace` has to wait for the slot's readers (`wait_for_readers`) before overwriting it, so fewer
swaps is fewer stalls on the lookahead and fill paths, not less traffic. `3` buys hit rate back without paying
much, and the tok/s column is noisy because tokens/round varies run to run.

Recommendation: default `1` for deep drafting, `2` for shallow (that is what the np2 sweep preferred by a
narrower margin).

### 2. Move reads to VRAM: stage more, on a second stream

PCIe is at 26% average / 50% peak while VRAM sits idle, so the machine has link headroom that the current
schedule cannot use: the staged segment is queued **after** the residents on one stream, so raising `frac`
(measured 0.4, 0.6) lengthens the round. Put the staged segment on its **own stream** (the two segments are
independent - residents read bank slots, staged read the ring) and `frac` can rise, shifting read bytes from
host DRAM (29% used) to VRAM (unused).

### 3. Make the dots faster per byte (the CPU side's real limit)

Per core the Q4_K dot sustains 2.5 GB/s against 11 GB/s for a plain read at the same thread count, so it is
**instruction-bound**; the aggregate saturates at 8.2 GB/s with 8 threads and does not improve at 10 (SMT
siblings add nothing - the default is now capped at 8). The remaining kernel work is the per-super-block scale
and min decode, plus sharing the row's Q8_K quantisation across the layer's experts.

### 4. Do not chase the rest

Ruled out with measurements: interleaving the stacks (1.00x either way), warming predicted experts into L3
(slower - the concurrent PCIe streams evict them), huge pages (already 2 MB), pinning (already page-locked),
`RUN_ROWS` (64 is optimal: 32 -> 1641 us, 64 -> 1354, 128 -> 1467), and lower-bit CPU copies (breaks the
byte-exact oracle).

## Two different "depths" - keep them apart

The word shows up twice and they are unrelated:

| flag | meaning | used in our runs |
|---|---|---|
| `--depth <N>` (bench) | **decode context length**: the decode measurement runs with N tokens of context. The `--prompt-len` case is the *prefill/TTFT* measurement | `--depth 4`, i.e. every decode number in these worklogs was measured at a **4-token context** |
| `--mtp-n-predict <N>` | **draft depth**: draft tokens proposed per round, so the verify pass has N+1 rows. This is what "np8 / depth 8" means in the tables above | 2-15 |

Consequence worth remembering: at `--depth 4` attention is trivial, so our TPOT numbers are **MoE-dominated** and
do not include a realistic KV read. A decode at `--depth 2048` (same model, same flags) would add the attention
work and, at some point, make the GPU compute term matter. Any claim about "the round is host/MoE bound" is
therefore specific to short contexts and should be re-measured at 2-4k before being applied to long-context
serving.

## Protocol

- **Traffic**: `NAIWA_ROUND_STATS=1` prints hit% / staged% / cpu% / staged_MiB / cpu_ms every 4 rounds.
- **PCIe**: `nsys` memcpy activity (`count`, `bytes`, busy time) in a steady-state window.
- **CPU**: `NAIWA_RET_DBG` (`compute_us` per job) and `NAIWA_FUSED_DBG` (us/pair).
- **Ceiling**: `harness/m7/pack_layout.c` for a pure read; always compare a change against that, not against
  the theoretical peak.
- Whole-run claims need >= 3 runs, liveness claims >= 6, and `frac 0` + `NO_LOOKAHEAD` stays byte-exact.
