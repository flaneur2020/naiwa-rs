# M3.1 — move the doorbell out of the fork into the engine

**Status: DONE** (2026-10-16).

## Why

The fork's doorbell (`mistralrs-core/src/cuda/doorbell.{rs,cu}` + the FFI decls) has **no consumer
inside the fork** — the only reference is `pub use cuda::doorbell;` in `lib.rs`. Every real user
lives in this engine: `deferred.rs`, `expert_cache.rs` (incl. `ScheduleBuf`), `copy_stream.rs`.

So the fork carries ~1.5k lines that exist only for v2. Moving them here:

- keeps the fork delta to what it genuinely must own (F1/F2/F4/F5),
- puts a still-evolving protocol where it is changed (M4 is about to add to it),
- costs a CUDA build step in this crate (`build.rs` + `cudaforge`, a registry crate — no new
  toolchain).

## Why it is safe even for M6

The whole-step graph (M6) lives in the fork's `pipeline/cuda_graph.rs`. If a PLE wait node had to go
into *that* graph, one might think the fork needs the doorbell again. It does not: **capture is
per-stream, not per-crate.** Any code that enqueues on the stream inside the capture window is
recorded, whoever it belongs to — and the M6 emitter is implemented here (the F2 provider
callback), so this crate can enqueue its own node into the fork-driven capture.

## Layout

```
src/doorbell/mod.rs      Rust API: DoorbellBuf, FlagBuf, ScheduleBuf, the sync-point ids + tests
src/doorbell/ffi (mod)   the extern "C" declarations, scoped to this module
src/doorbell/doorbell.cu the kernels
build.rs                 cudaforge -> libnaiwadoorbell.a, gated on the cuda feature
```

Consumers switch from `mistralrs_core::doorbell::X` to `crate::doorbell::X`.

## Steps

1. Land the module + build.rs + consumer paths; build and run the doorbell tests here
   (`cargo test --lib doorbell`).
2. Gate: `--pcie-frac 0` + `NAIWA_NO_LOOKAHEAD=1` still byte-identical to the frozen oracle (5/5).
3. Only then remove the files, the FFI decls, the `pub use` and the build.rs entry from the fork,
   and confirm the fork still builds.

## Result

- `src/doorbell/mod.rs` (1246 lines) — `DoorbellBuf`, `FlagBuf`, `ScheduleBuf`, the `SYNC_*` ids and
  the five unit tests; the `extern "C"` surface is a module-private `mod ffi` with the 14 doorbell
  declarations, so nothing above it is unsafe.
- `src/doorbell/doorbell.cu` (419 lines) — the kernels, unchanged.
- `build.rs` — `cudaforge` on `src/doorbell/*.cu` → `libnaiwadoorbell.a`, gated on the `cuda`
  feature; same flags as the fork's build, `rerun-if-changed` on the directory so it does not
  rebuild every time. `cudaforge = "=0.1.6"` added under `[build-dependencies]`.
- `main.rs` gains `mod doorbell;`; the 14 consumers switch to `crate::doorbell::…`.

**Fork side**: `cuda/doorbell.{rs,cu}` deleted, the 14 `doorbell_*` FFI declarations stripped from
`cuda/ffi.rs`, `pub mod doorbell;` and the `lib.rs` re-export removed. The fork builds without them
(`cargo build -p mistralrs-core --features cuda`).

### Evidence

--pcie-frac 0 + NAIWA_NO_LOOKAHEAD=1, 5 runs
