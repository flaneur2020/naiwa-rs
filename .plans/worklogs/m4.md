# M4 — the PCIe leg enters the graph (`SYNC_STAGING`)

**Status: DONE** (2026-10-17). The 55% leg now signals DMA completion *inside* a captured node;
the host enqueues no stream wait per streamed expert.

## What was wrong before

`stream_pcie` queued each staged expert's copies on the copy stream and then, **per streamed
expert**, called `scratch.done.wait_on(&slot_device)` — a `cudaStreamWaitEvent` on candle's stream,
issued by the token thread. The DMA was already asynchronous; only the *completion signal* was a
host call. M4 turns that into a doorbell point published by the copy stream itself.

## Design

**A per-layer DMA gate.** Each layer gets one captured graph whose single node is
`doorbell_wait_ready(ready[id], epoch)`, `id = sync_id(layer, SYNC_STAGING)`. It is replayed
immediately before the layer's MoE segment, so a node on candle's stream spins until the copy
stream has published the point, and only then may the segment's kernels read the staging slots.

Why the gate lives on the layer and not on the scratch bank's graph: **the staging ring is shared
by every layer of its shape** (`ScratchKey`), so its capture is one graph for many layers and
cannot carry a per-layer id. The gate bakes the id, owns no buffers, and costs one node — 48 of
them at warmup, ~0 memory. This is also why the scratch bank keeps a single wait-free capture: the
capture count stays independent of the miss/hit split (criterion ②).

**Producer side.** After queueing a layer's copies, `stream_pcie` publishes
`publish_point_on(copy_stream, id, pass)` — `cuStreamWriteValue32` on the copy stream, a stream
memory op ordered after the copies: no kernel, no host wait, no event. `CopyStream::queue_async`
is the copy call that records **no** completion event at all; `CopyDone` is now used only by the
prefill stream. The publish happens on every path (nothing staged, staged, or failed) because the
gate is replayed every pass — a point left unpublished would spin forever.

**One predicate governs three sites.** Capture the gate, publish the point, replay the gate — all
behind `CachedLayer::staging_enabled()` (`pcie_frac > 0 && copy_stream.is_some()`). This is not
cosmetic: `copy_stream` exists at `--pcie-frac 0` too (the cache banks are filled from it), so the
first version captured and replayed a gate whose point nothing published, and **`frac 0` hung**.
The frac-0 run caught it; the predicate is the fix, and the reason all three call `cudaStreamWaitEvent`
sites now share one condition.

**Fallback.** If the gate cannot be captured at warmup, the *same* node is launched warm (one host
call per layer, the same price as the `cudaStreamWaitEvent` it replaces) — one protocol either way,
counted as `staging_eager_waits`, which must be 0.

## Judged by (roadmap M4)

| Criterion | Result |
|---|---|
| ① hit + PCIe + CPU == eager | greedy output identical to the frozen oracle: **5/5 at `frac 0.55`**, 2/2 at `frac 0` (and 3/3 before the change — the equivalence reference) |
| ② no recapture for any miss combination | captures all happen in the post-load warmup: **48 gates + 48 bank segments (+48 CPU-return nodes)**, `warmup: 48 capture(s), 3 staging ring(s) fixed`; `M1: ring set frozen across the decode` |
| ③ `frac` is only a bandwidth knob | `frac 0` → no gate captured or replayed, 0 ring, identical output; `frac 0.55` → 2365–2423 misses DMA'd (~5 GiB), same output |

Structural counts from `bench --pcie-frac 0.55 --gen-len 8`:

```
M4 DMA gate: 48 captured at warmup, 384 replayed; 0 gate wait(s) launched warm (must be 0)
             -> 384 = 48 layers x 8 passes, i.e. exactly one gate per layer per pass
--pcie-frac: 2365 misses DMA'd to the GPU (4978 MiB)
M2 capture: 342 MoE segment(s) replayed as 1 graph launch
```

## Must-fail control (M0's lesson: right answers are not evidence)

Publishing a **stale** stamp (`pass - 1`) so the node can never pass: the serve run **hangs** and
is killed at the 200 s timeout (`harness_exit=124`). Reverted. So the spin is live and
load-bearing — the gate is not a no-op that happens to produce correct tokens.

## `SYNC_PRELOAD` — why it is not a spin point (yet)

The lookahead/preload DMA is issued by `upload_in_place` → `CopyStream::upload`, which is
**synchronous**: it returns after the copies land, on the lookahead/fill worker, never on the token
thread. The slot is published into `st.published` only after it has landed, so the ordering edge is
the per-step residency descriptor (`SYNC_RESIDENCY`), which is host-written and not a spin point.
There is nothing for the graph to wait for, so `SYNC_PRELOAD` stays unrealised.

It becomes load-bearing exactly when the preload stops blocking — M5's dedicated thread with
`queue_async`. The template is already here: publish `sync_id(layer, SYNC_PRELOAD)` on the copy
stream after the preload copies, and give the layer's resident capture the same one-node gate
(`wait_ready` before the segment's compute). The resident capture is already per layer, so no
new keying is needed.
